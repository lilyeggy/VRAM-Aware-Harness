先定调：横评不是选美

面试开场先说这句："架构选择只在具体目标下才有意义——本地体验、治理、远程隔离、长期记忆或最小内核，各家的工程重心不同。"不做谁更强的总分排名，做'同一责任各自如何兑现'的对照——这句话本身就是加分项。

五分钟对比剧本：三家明星框架

① Claude Code —— 治理层最强辨识度

记忆/上下文CLAUDE.md → rules → skills 分层组装；subagent 用独立上下文承接委派，防主会话污染
工具治理permission modes（allow/ask/deny）+ hooks 生命周期自动化——动作前后可插入组织控制点
一句话总结"把上下文来源和动作权限都做成显式、可分层、可覆盖的配置系统"；面向编码工作流，长期人格与多租户远程不是它的核心抽象

② Hermes Agent —— 记忆与技能进化

记忆机制持久 MEMORY.md / USER.md：跨会话保留身份与事实；状态外化到文件系统的代表实现
技能学习Skills 可由 Agent 自己创建并改进——"执行→总结→技能化"的自我改进回路；多入口（CLI/消息渠道/cron）共用同一个 Agent 身份
一句话总结"把一次工具成功抽取成未来可复用的程序性记忆"；代价是治理面扩大——技能写入和后台任务都需要审批与审计

③ OpenClaw —— Gateway 多渠道架构（2026-08 已核实的最新口径）

定位跑在自己设备上的个人 AI 助理，为单一操作者设计；在 WhatsApp/Telegram/Slack/Discord/iMessage 等现有渠道里见面
架构核心Gateway 是本地控制面：统一管理 sessions、tools、events 和渠道连接；Control UI / CLI / TUI 都连到它
安全边界主会话的工具默认直接跑在宿主机上，除非显式配置 sandboxing——官方安全指南明确要求暴露前读 runbook。这是与你项目最大的对照点！
扩展生态Tools / Skills / Plugins + ClawHub 市场；Companion 节点提供语音、Canvas、摄像头等设备侧能力
⚔️
对比反杀（背下来）

"OpenClaw 默认宿主执行、单操作者信任模型——这正确定位了它是个人助理。而我的项目服务的是互相不信任的多租户：非 root 只读容器、cap drop ALL、默认无网络、每 Attempt 独立沙箱加证据三元组。信任模型决定隔离设计，这不是谁做得好谁做得差，是命题不同。"
