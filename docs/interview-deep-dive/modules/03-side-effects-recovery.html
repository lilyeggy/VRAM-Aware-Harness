03

副作用记账与崩溃恢复

Agent 不是聊天机器人——它的 bash 会真删文件。进程在工具执行到一半时崩溃，重启后这个工具该重放吗？

隐喻：支票双联存根

出纳每动一笔钱都要留底：先把「我准备转 500 元」的存根压在玻璃板下，转账成功后再盖「已完成」章。银行倒闭重启后，看到只有存根没有章的交易怎么办？答案藏在四步流程里：

1
写存根：PREPARED

动手前先把意图持久化——「我准备执行这个工具」。此刻什么都没改变，但账上已经有了这一笔。

2
盖章：SUCCEEDED

真实执行完成后，结果与检查点在同一个事务里落库。从此这笔调用有了不可抵赖的最终结论。

3
重启盘点：发现无章存根

银行（进程）倒闭重启后，扫描账本：那些只有 PREPARED 没有 SUCCEEDED 的「孤儿存根」就是全部疑点。

4
分类处置：绝不盲目重转

纯查询（READ_ONLY）就安全重做；说不清影响的（UNKNOWN）就冻结等人工。宁可慢，不可错。

🏛️
这不是新发明：双复写（Write-Ahead Intent）

「先持久化意图，再执行，最后确认」正是数据库 WAL（预写日志）与分布式事务 2PC（两阶段提交）的共同思想。你的 Agent Harness 和 PostgreSQL 用的是同一个直觉。

两个三元组：整个机制的数据模型

ToolEffect · READ_ONLY只读不改世界——重放一万次也无害
ToolEffect · IDEMPOTENT_WRITE声称幂等的写——注意是「声称」，后面有它的大戏
ToolEffect · UNKNOWN_EFFECT说不清影响——bash 脚本、发邮件都在这里，默认嫌疑犯
Status · PREPARED存根已写，动作未发——崩溃恢复最关心的状态
Status · SUCCEEDED / FAILED已有终局结论的调用，重启后无需任何处置

核心决策函数：谁能自动重放？

恢复安全性的核心不是 Checkpoint 本身，而是副作用分类。整个系统的安全边界浓缩在下面这一个函数里——注意 IDEMPOTENT_WRITE 的下场：

CODE · src/tools/tool-execution.ts 
export type ToolEffect = 
    | "READ_ONLY"
    | "IDEMPOTENT_WRITE"
    | "UNKNOWN_EFFECT";
 
export type ToolExecutionStatus = 
    | "PREPARED"
    | "SUCCEEDED"
    | "FAILED";
 
export function canAutomaticallyReplay(
    status:ToolExecutionStatus,
    effect:ToolEffect,
):boolean{
    if (status !== "PREPARED"){
        return false;
    }
 
    switch(effect){
        case "READ_ONLY":
            return true;
        case "IDEMPOTENT_WRITE":
            // “写入被声明为幂等”本身不足以证明外部系统会使用稳定幂等键。
            // 在 ToolExecution 持久化并校验真实幂等证据前保持 fail closed。
            return false;
        case "UNKNOWN_EFFECT":
            return false;
    }
}
白话

先定义效果三分法：只读、声称幂等的写、说不清的写。类型即文档——三种可能穷尽，没有第四种。

执行状态也是三态：存根（PREPARED）、成功、失败。两个三元组组合出全部审计场景。

决策函数登场：输入「停在哪个状态 + 属于哪类效果」，输出一个布尔值——能不能不经人批准直接重放。

第一道闸：只有 PREPARED 才考虑重放。SUCCEEDED 有结果缓存可直接返回，FAILED 有错误结论——都不是「待处理」。

READ_ONLY 是唯一绿灯：读操作不改变世界，重放天然无害。

全场最精彩的一行：IDEMPOTENT_WRITE 也是红灯！注释给出了理由——「写入被声明为幂等」只是工具作者的口头声明，不是证据。

外部系统是否真的用稳定幂等键去重，控制面无法验证；在拿到持久化的真实幂等证据之前，保持 fail closed——不确定就拒绝。

UNKNOWN 更不用说：连影响都描述不清的操作，绝不允许机器擅自重来。

💡
面试金句：声明 ≠ 证据

「写入被声明为幂等」本身不足以证明外部系统会使用稳定幂等键。恢复安全性靠的不是乐观假设，而是把不确定当成危险——这就是 fail-closed 与 fail-open 的分野。

ToolGateway.execute：顺序就是安全

所有工具调用的必经之路。盯住顺序：策略检查 → 查历史 → PREPARED 落库 → 最后才 invokeTool。每换一次顺序，都会打开一种新的漏洞。

CODE · src/tools/tool-gateway.ts（节选） 
    async execute(
        input:ExecuteToolInput,
        invokeTool:() => Promise<unknown>,
    ) : Promise<unknown>{
        // 策略检查必须发生在 PREPARED 写入和真实副作用之前。
        this.policyGuard?.assertAllowed(input);
 
        const history = this.store.getByToolCall(runId,toolCallId);
        let preparedExecution : ToolExecution;
 
        if (history === null){
            preparedExecution = {
                id : crypto.randomUUID(),
                runId,
                toolCallId,
                toolName:input.toolName,
                arguments:input.arguments,
                effect:input.effect,
                status:"PREPARED",
                result:null,
                errorMessage:null,
                createdAt:new Date().toISOString(),
                finishedAt:null,
            }
            this.store.prepare(preparedExecution);
        } else {
            switch(history.status){
                case "SUCCEEDED":
                    return history.result;
                case "FAILED":
                    throw new Error(`工具执行失败:${history.errorMessage}`);
                case "PREPARED":
                    if (
                        !canAutomaticallyReplay(
                            history.status,
                            history.effect,
                        ))
                        {
                            throw new Error(
                                `不允许自动重放：${history.effect}`,
                            );
                        }
                    // 允许重放时复用原来的执行记录，
                    // 不能再次调用 store.prepare()，否则会违反唯一约束。
                    preparedExecution = history;
                    break;                    
            }
        }
白话

execute 接收两样东西：要执行什么（input），以及怎么真正执行（invokeTool 回调）——网关掌握流程，Runtime 提供动作。

第一行就是铁律：策略守卫 assertAllowed 必须跑在最前面——在任何记账、更在任何副作用之前。没授权的事，连存根都不配写。

第二步查历史：这个 toolCallId 是否已经有记录了？正常执行这里是空，崩溃恢复时这里就有故事。

无历史 = 全新调用：开始构造完整的执行记录——谁发起的（runId）、调用的是什么（toolName）、参数原样封存。

effect 与 status 一并落库：效果分类是调用方申报、策略审批过的，此刻固化成账面事实。

status 定格为 PREPARED：存根压进玻璃板下，result 还是 null——世界尚未改变。

store.prepare 把存根持久化。从这里开始，「我打算做什么」已经是数据库里不可否认的事实。

有历史的三个分支之一：SUCCEEDED 直接返回缓存的结果——同一次调用重复到达也只执行一次，天然幂等。

分支之二：FAILED 直接抛错并带回当时的错误信息——失败的结论同样不许被静默覆盖。

分支之三：停在 PREPARED 的孤儿存根——问 canAutomaticallyReplay 能否自动重放。

答不了绿灯就抛错冻结，把效果分类写在错误信息里供人工审查——绝不猜。

能重放的细节：复用原来的执行记录对象，绝不能再 store.prepare 一次——同一 toolCallId 的唯一约束会让第二次插入当场爆炸。

把顺序铁律压缩成一条流水线：

1

策略守卫

→

→

已成功的调用直接回放结果，不再触碰外部世界。重试语义被数据库吸收，调用方无感。

🔒

PREPARED → 复用原记录

允许重放时沿用旧记录 ID，不能再 prepare——唯一约束（每 toolCallId 一条）既是防重复插入，更是防账本分叉。

崩溃之后：系统如何决定「继续」还是「叫人」

先看成功路径的收尾：结果与检查点同一个事务写入。Checkpoint 不是内存 dump，而是一个稳定引用——runtimeSessionRef 加 lastEventSequence，指向「去哪里、从哪条事件继续」。

CODE · src/tools/tool-gateway.ts（节选） 
        const checkpoint:Checkpoint = {
            id:crypto.randomUUID(),
            runId:input.runId,
            toolExecutionId:preparedExecution.id,
            runtimeSessionRef:input.runtimeSessionRef,
            lastEventSequence:input.lastEventSequence,
            createdAt:finishedAt,
        }
 
        this.store.completeWithCheckpoint(succeededExecution,checkpoint);
 
        return result;
白话

构造检查点：它记录的不是全部状态，而是两个坐标——哪个 Runtime 会话（runtimeSessionRef）、读到第几条事件（lastEventSequence）。

引用而非快照：体积恒定小巧，且天然跟随事件流的版本。

关键方法名说明一切：completeWithCheckpoint——工具结果（SUCCEEDED）与检查点在同一个事务里落库。

于是不会出现「结果记了但恢复点丢了」的裂缝：两者要么同时存在，要么同时不存在，崩溃恢复永远面对一致的世界。

重启后的决策大脑是 decideRecovery：输入有效 checkpoint 与所有孤儿存根，输出一个三选一的计划：

CODE · src/checkpoints/recovery-decision.ts 
export function decideRecovery (
    checkpointId:string|null,
    preparedExecution:readonly ToolExecution[],
):RecoveryDecision{
    if (checkpointId === null){
        const action : RecoveryAction = "MANUAL_REVIEW";
        const recoveryReason : RecoveryReason= "NO_CHECKPOINT";
        const execution : RecoveryDecision = {
            action:action,
            reason:recoveryReason,
            blockingToolExecutionId:null,
        }
        return execution;
    };
    const unsafeExecution = preparedExecution.find(
        (execution) => !canAutomaticallyReplay(
            execution.status,
            execution.effect,
        )
    );
 
    if (unsafeExecution !== undefined){
        return {
            action:"MANUAL_REVIEW",
            reason:"UNSAFE_TOOL_EFFECT",
            blockingToolExecutionId:unsafeExecution.id,
        }
    }
 
    return {
        action:"AUTO_RESUME",
        reason:"SAFE_CHECKPOINT",
        blockingToolExecutionId:null,
    }
}
白话

决策函数签名本身就是文档：给一个 checkpoint 引用加一串孤儿存根，还你一个明确的恢复计划。

情形一：连 checkpoint 都没有——无从知道执行到哪，直接 MANUAL_REVIEW（人工审查），理由 NO_CHECKPOINT 写明。

注意设计取舍：没有恢复点时绝不尝试「从头重跑」——那等于把已发生的副作用再来一遍。

情形二：有 checkpoint，但在孤儿存根里找到任何一个不能自动重放的（回到上一屏的那个函数逐一审问）。

只要有一个可疑分子，整体就冻结：action 仍是 MANUAL_REVIEW，并且精确记录 blockingToolExecutionId——告诉人工「卡在这条记录上」。

一票否决制：AUTO_RESUME 要求所有存根全部干净，而不是大多数干净。

情形三：checkpoint 有效且所有存根都是 READ_ONLY 绿灯——放心 AUTO_RESUME，理由 SAFE_CHECKPOINT。

纯函数、无副作用、可单测：恢复正确性可以被 254 个测试里的用例钉死，而不是靠运维经验。

最后一步为什么 RecoveryService 不直接调 runtime.resume？源码里的一段注释就是标准答案：

CODE · src/checkpoints/recovery-service.ts 
 * 这一层只建立恢复计划，不直接调用 AgentRuntime：
 * - 扫描和状态修正是同步、确定性的数据库工作；
 * - Runtime resume 是可能失败的外部执行，应由下一层逐个消费计划。
白话

分层铁律：计划层（RecoveryService）只负责想清楚「该做什么」，执行层（RecoveryExecutor）才负责「去做」。

扫描修正（陈旧 RUNNING → INTERRUPTED，附 PROCESS_RESTART 事件）是确定性的数据库操作——可以批量、可重入、永不部分失败。

而 resume 是可能失败的外部调用，绝不能混进确定层——否则一次失败污染整个扫描批次。

所以 AUTO_RESUME 的计划由下一层逐个调 coordinator.submitResume 消费——重新入队！恢复也要重新过资源准入与公平调度，不许插队。

隐蔽死角：恢复数据的归属校验

恢复是多租户防串最容易漏的一环。如果拿错恢复数据，就会「用 A 租户的 checkpoint 驱动 B 租户的 Run」——所以在重新入队前再做一次绑定校验：

CODE · src/runs/run-service.ts · queueResume（节选） 
        if (
            input.checkpoint.runId !== input.runId
            || interruptedRun.checkpointId !== input.checkpoint.id
        ) {
            throw new Error(
                `Checkpoint ${input.checkpoint.id} 不属于当前 Run`,
            );
        }
白话

双向绑定校验：checkpoint 必须属于这个 Run，且 Run 当前指向的也必须是这个 checkpoint——两个方向都对得上才放行。

同类绑定还有策略快照 snapshot.runId === input.runId：策略也必须是这个 Run 自己那份，不能借用别家的。

面试加分点：这类「关系完整性」校验不放在 UI 层也不放在 API 层，而是放在业务动作入口——离数据最近的地方最可靠。
