claimNext：选中即占 slot

数据结构三件套：Map<tenantId, QueuedRun[]> 每租户队列 + tenantOrder[] 轮转数组 + activeTenantByRunId slot 表。看 claimNext 怎么在三者之间跳转：

CODE · src/scheduling/tenant-run-scheduler.ts 
claimNext() : QueuedRun | null {
    // 首先检查全局 slot
    if (this.activeTenantByRunId.size >= this.config.maxActiveRuns){
        return null;
    }

    const tenantsToInspect = this.tenantOrder.length;
    for (let inspected = 0; inspected < tenantsToInspect; inspected += 1) {
        // 从轮转队列头部取出本轮tenant
        const tenantId = this.tenantOrder.shift();
        if (tenantId === undefined) { return null; }

        const tenantQueue = this.queuesByTenant.get(tenantId);
        if (tenantQueue === undefined || tenantQueue.length === 0) {
            this.queuesByTenant.delete(tenantId);
            continue;
        }

        const activeTenantByRunCount = this.getActiveTenantRunCount(tenantId);

        // 当前 tenant 已经达到并发上限，它仍有等待任务，所以放回轮转队尾.
        if (activeTenantByRunCount >= this.config.maxActiveRunsPerTenant){
            this.tenantOrder.push(tenantId);
            continue;
        }

        const run = tenantQueue.shift();
        if (run === undefined){ this.queuesByTenant.delete(tenantId); continue; }

        // 如果这个 tenant 还有等待任务，那么将它放在下一轮队尾
        // 如果已经清空，那么就从 queuesByTenant 删除
        if (tenantQueue.length > 0){ this.tenantOrder.push(tenantId); }
        else { this.queuesByTenant.delete(tenantId); }

        this.activeTenantByRunId.set(run.runId, run.tenantId);
        return run;
    }
    return null;
}
白话翻译

先看果篮是否已满：全局活跃数达到上限就直接返回空。

最多检查一圈所有租户——避免死循环。

轮转指针从队头取出本轮该叫的租号。

这个租户没有等待任务了？清理掉，继续下一家。

统计它当前占了多少个 slot。

达到单租户上限？把它放回队尾但跳过——它还有等待任务，只是这一轮不能领。

从它的队列头部取出第一个等待 Run（FIFO）。

如果它还有后续任务，租户放回轮转队尾；否则彻底移出。

关键一行：立刻登记 slot 占用。claim 的语义是"离开队列并占用一个并发名额"，不是"看看有没有人"。

claim 出来之后交给资源准入。注意这个细节——算术自洽的软硬两层：

CODE · src/scheduling/run-queue-coordinator.ts 
// 选出 run 的时候，run 已经离开队列并占用了 slot，所以需要更新资源情况
const capacity = this.scheduler.getCapacity(queuedRun.tenantId);

const admissionRequest = {
    runId : queuedRun.runId,
    tenantId : queuedRun.tenantId,
    activeRunCount : capacity.activeRunCount - 1,
    activeTenantRunCount : capacity.activeTenantRunCount - 1,
}
白话翻译

claim 已经让这个 Run 占了一个 slot，此时读到的容量数字包含它自己。

构造准入请求时把自己刚占的名额减掉——策略层判断的是"除了我之外还有多少人在跑"。这就是槽位双保险：scheduler 是硬上限，策略是减去自身后的软判断，两边算术永远自洽，不会出现"自己把自己挤下去"的悖论。

QUEUE 分支：release 和 re-enqueue 的时序铁律

准入说"还不能跑"时，Run 要回到队列。这里有一行注释值得背下来：

CODE · src/scheduling/run-queue-coordinator.ts 
if (decision.action === "QUEUE") {
    const reasonCode = toQueueReasonCode(decision);

    this.scheduler.release(queuedRun.runId);
    // 顺序一定要是先 release 再 enqueue，否则 enqueue 会认为 run 仍在执行并拒绝入队
    this.scheduler.enqueue({
        runId:queuedRun.runId,
        tenantId:queuedRun.tenantId,
        reasonCode,
        enqueuedAt:queuedRun.enqueuedAt,
    });

    return { kind:"DEFERRED", runId:queuedRun.runId, decision }
}
白话翻译

决策是排队——先把 reasonCode 转换成队列语言。

第一步必须先归还 slot。因为 enqueue 会拒绝"正在执行中"的 Run——而此刻它在 slot 表里还占着名字。

第二步再入队，带上新的排队原因码。

注意 enqueuedAt 原样带回：被 defer 的 Run 不丢自己的排队时间戳。如果重置了这个时间，反复被 defer 的任务会永远排在后面——公平性就被惩罚机制破坏了。

drain：单飞模式（single-flight）

提交任务、释放 slot、定时器到点……很多事件都会喊"推一把队列"。如果每次都真起一个循环，就会并发乱套。解法是 single-flight：

CODE · src/scheduling/run-queue-coordinator.ts 
drain() : Promise<CoordinatorResult[]> {
    // 每次调用都代表系统状态可能发生了变化
    // 因此至少请求进行一轮队列检查
    this.drainRequested = true;

    // 已经有 drain 在执行，重复用同一个 Promise
    if (this.drainPromise !== null){
        return this.drainPromise;
    }

    // 没有 drain 执行，就启动新的推进循环
    this.drainPromise = this.runDrainLoop();
    return this.drainPromise;
}
白话翻译

任何调用者都先把"需要推进"的标志位置真——这是请求的唯一副作用。

已有循环在跑？直接复用同一个 Promise，不另起炉灶。

没有才创建新循环。循环体是 while(drainRequested)：每轮开始清掉标志位、跑一遍 drainOnce；期间又有人调 drain() 标志位重新变真，循环就再来一轮。finally 里清空 drainPromise，允许下次冷启动。

⏱️
RunQueuePump 定时器兜底

setInterval 周期性 tick → drain()；构造后立即 tick 一次不等首个间隔。stop() 只清定时器，不打断进行中的 drain。资源恢复后最多等一个周期，队列自动推进。

⚡
提交即调度

HarnessApplication.submitRun 里 void this.queuePump.tick()——新任务不等下一个轮询周期，立刻触发一轮 drain。

🔄
进程重启后的队列重建

内存队列是易失的。启动时从持久化的 QUEUED 行重建（restoreQueuedRun）；listActiveRuns 把陈旧 RUNNING 转 INTERRUPTED 再走恢复扫描——内存状态永远从数据库事实重建。

已知设计缺口：面试主动讲反而加分

这五个缺口全部记录在项目手册 §14.5——能说清"哪里不完美、为什么可接受、怎么改"，比假装完美更有说服力：

① sessionId 客户端可自报会话固定/抢注 DoS；结论倾向：服务端鉴权后签发 session id
② reasonCode 仅存内存重启后 GET /queue 的排队原因不可复现；应落 policy_decisions 还原
③ 缺 RUN_DEFERRED 事件反复 defer 的过程在 run_events 时间线上是空白
④ TOCTOU 归档窗口claimNext 与 release+re-enqueue 之间崩溃 → run 从内存队列消失但 DB 仍 QUEUED，需等重启 recovery 回队（已知边界，低风险）
⑤ 准入是 point-in-time决策 t0、派发 t1 中间资源可变；定位为"去耦的准入点"而非实时保证
