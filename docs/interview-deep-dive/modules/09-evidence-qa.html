高频追问速答弹药库

每条答案控制在 60 秒内说完，先给结论再给一层细节：

Q1
为什么用 runsc/gVisor 而不自研沙箱？

预算/人力/安全责任都不够自研 runtime。亮点在上层三环：策略边界编译、租户资源管控、可验证证据三元组。没有 KVM 就不声称 strict VM 隔离通过——诚实边界本身就是设计决策。

Q2
资源准入怎么做？背压怎么触发？

vLLM /metrics + nvidia-smi 双源并行 → ResourceSnapshot → 四组阈值分类 NORMAL/BUSY/CRITICAL/UNKNOWN → DeterministicExecutionPolicy 出 START/QUEUE + reasonCode → policy_decisions+resource_snapshots 同事务落库。观测失败=QUEUE(RESOURCE_OBSERVATION_FAILED)，fail-closed。

Q3
任务崩溃了怎么恢复？

ToolEffect 三分类；只有 PREPARED+READ_ONLY 自动重放（IDEMPOTENT_WRITE 也 fail-closed：声明≠证据）。RecoveryService.scanInterruptedRuns 把陈旧 RUNNING 转 INTERRUPTED 并建计划 → decideRecovery 出 AUTO_RESUME/MANUAL_REVIEW → RecoveryExecutor 经 coordinator.submitResume 重新入队——恢复也要重新过资源准入和 slot 占用。

Q4
多租户怎么隔离？

身份层：API Key→摘要比对→Principal{tenantId,scopes}，tenant 不来自请求体；运行层：独立 workspace 目录 + runsc 容器（非 root、只读 rootfs、cap drop ALL、默认无网络）；调度层：Tenant 内 FIFO、租户间 round-robin、双并发上限；数据层：查询按 tenant 收口 + 404 反枚举 + DB 约束兜底。

Q5
为什么 IDEMPOTENT_WRITE 不自动重放？

"写入被声明为幂等"不足以证明外部系统会使用稳定幂等键。在 ToolExecution 持久化并校验真实幂等证据之前保持 fail-closed——声明不等于证据，这是恢复安全性的底线。

Q6
并发更新 Run 会不会互相覆盖？

乐观锁：UPDATE ... WHERE id=$id AND status=$previousStatus，changes!==1 即抛错——过期快照覆盖新状态被挡。事件去重靠 UNIQUE(run_id, dedupe_key) 部分唯一索引；Run 快照与事件同事务写入。

Q7
drain 会不会并发跑多个？

single-flight：drainPromise 复用 + drainRequested 标志位补跑一轮。attemptNext 内部先 claimNext 占 slot；QUEUE 时先 release 再 re-enqueue（顺序反了 enqueue 会拒绝），并保留原 enqueuedAt 防饥饿放大。

Q8
流量翻 100 倍怎么办？

诚实回答"现在不行"+ 给出可信路径：RunStore 换 Postgres、调度器外置或多 Worker 抢 DB 行锁、Sandbox Provider 池化、vLLM 多实例 + 网关路由（RouteDecision 扩展点已预留）。当前单进程是 MVP 有意取舍，控制面语义已被测试锁定，迁移不改行为。

Q9
最大的技术挑战是什么？

推荐答：不是某个算法，而是"让安全成为默认值"——fail-closed 贯穿四条线（观测失败→QUEUE、副作用未知→人工确认、能力缺失→REJECTED、runtime 证据不符→删容器）；以及恢复路径的归属校验（checkpoint.runId/策略快照 runId 双绑定）——多租户防串最容易被漏掉的死角。
