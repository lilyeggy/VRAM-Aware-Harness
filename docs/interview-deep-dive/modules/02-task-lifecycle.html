一次任务的一生

用户点下「提交任务」的那一瞬间，一个 Run 开始了它的一生——从 QUEUED 到 COMPLETED，每一步都被持久化、可回放。

隐喻：医院手术系统

Tenant 是医院，Workspace 是独立病房，Run 是一台手术，Attempt 是一次实际开刀（手术可能因故重开）。Sandbox 是无菌手术室，ToolExecution 是手术记录单——每动一刀都记，病历永远追加、不可涂改。

每个对象都有容易混淆的「近亲」。七张速查卡辨析到位，面试里就不会说错词：

Tenant

身份/数据/策略/资源/审计的一等边界。
辨析：来自认证解出的 Principal，绝非客户端自报。

Workspace

租户下受管工作区，目录由服务端生成。
辨析：客户端不能提交宿主机路径——路径是分配的，不是申报的。

Session

对话关系，Pi AgentSession 的持久句柄。
辨析：Session ≠ Run——一段对话可以承载多次任务。

Run

一次受控任务。
辨析：被状态机管理的一生，本模块的主角。

Attempt

Run 的一次实际执行。
辨析：每次真实执行独立 Attempt——重试不是同一次开刀。

Sandbox

每 Attempt 的隔离环境（runsc 容器）。
辨析：绝不跨 Attempt 复用——无菌室用完就换。

ToolExecution

一次工具调用及副作用记账。
辨析：PREPARED / SUCCEEDED / FAILED 三态，Module 3 深挖。

双轨制：Runtime 是即时的，Run 是持久的

整个可解释性的地基，写在 src/runs/agent-run.ts 开头的一句注释里。设计思想先行，代码只是它的展开：

CODE · src/runs/agent-run.ts 
 * Runtime 和 Run的最大区别就是 Runtime 是即时的，而 Run 是持久的
 * 那么从这个角度看，RuntimeEvent和RunEvent也是同样的区别
 * RuntimeEvent是即时的，而 RunEvent 是harness 长期保存的
白话

Runtime 是「正在发生的执行」：SDK 里的事件转瞬即逝，进程一崩就没了。

所以事件也要分两轨：RuntimeEvent 属于执行的瞬间，RunEvent 属于 Harness 的长期记忆。

面试一句话：底层 SDK 的事实会消失，Harness 把值得保留的部分翻译成自己的业务事实，永久落库。

⚡

RuntimeEvent · 即时轨

存在于 SDK 执行的瞬间：token 流、工具开始/结束。其中 text_delta 这类高频碎片只用于实时展示，不落库。

🗄️

RunEvent · 持久轨

Harness 长期保存的业务事实：RUN_CREATED、TOOL_COMPLETED、策略决策……带 sequence 序号，可完整回放。

💡
这就是「事件溯源」（Event Sourcing）思想

agent_runs 表存「现在是什么状态」，run_events 表存「过去发生过什么」。查询看快照所以快，审计看事件流所以全——两者各司其职，缺一不可。

Run 的六态状态机：合法迁移全在这张表里

状态机是控制面的骨架：src/runs/run-state-machine.ts 用一张字面量表声明所有合法迁移，表里没有的路一概非法。

CODE · src/runs/run-state-machine.ts 
const allowedTransitions : Record<AgentRunStatus,readonly AgentRunStatus[]>={
    QUEUED: ["RUNNING","INTERRUPTED"],
    RUNNING : [
        "WAITING_TOOL",
        "INTERRUPTED",
        "FAILED",
        "COMPLETED",
    ],
    WAITING_TOOL:[
        "RUNNING",
        "INTERRUPTED",
        "FAILED",
    ],
    INTERRUPTED:[
        "QUEUED"
    ],
    COMPLETED:[],
    FAILED:[]
}
 
export function assertValidTransition(
    from : AgentRunStatus,
    to : AgentRunStatus,
): void {
    if (!canTransition(from,to)){
        throw new Error(
            `非法的 AgentRun 状态转换：${from} -> ${to}`
        )
    }
}
白话

一张只读的迁移表：每个状态只能去「名单上」的状态，类型系统保证六个状态一个不少。

QUEUED 只有两个出口：过准入变 RUNNING，或者排队期间被打断。

RUNNING 是枢纽：可以等工具、可以被打断、可以失败、可以完成——四种出口只有一种是好结局。

WAITING_TOOL 不能直接 COMPLETED：工具结果回来必须先回 RUNNING 收尾。

最关键的一条：INTERRUPTED 只能回到 QUEUED——为什么不能直接 RUNNING？下面这张图揭晓。

COMPLETED 和 FAILED 的数组是空的：终态就是死路，没有任何代码能把它们改写。

守卫函数：任何非法转换直接抛错，带着「从哪来 → 到哪去」的完整证据。

错误消息用中文写进代码——这个错误是给人看的，而且大概率是开发者自己的 bug。

Run 的诞生：状态与历史在同一事务里落地

createQueuedRun 是每个 Run 的出生证明开具处。注意最后那行 store.create(run, createdEvent)——Run 快照和第一条事件必须在同一个 SQLite 事务里写入，否则可能出现「状态变了但历史没记」的裂缝。

CODE · src/runs/run-service.ts 
    createQueuedRun(input : StartRunInput) : AgentRun {
        const runId = crypto.randomUUID(); 
        const timestamp = new Date().toISOString();
        const controlBinding = this.controlBindingResolver?.resolve(input);
 
        const run : AgentRun = {
            id:runId,
            tenantId:input.tenantId,
            harnessSessionId:input.harnessSessionId,
            status : "QUEUED",
            userInput:input.userInput,
            workspacePath:input.workspacePath,
            createdAt:timestamp,
            updatedAt:timestamp,
            startedAt:null,
            finishedAt:null,
            checkpointId:null,
            failureReason:null,
            ...(input.runPolicy === undefined
                ? {}
                : { runPolicy: input.runPolicy }),
            ...(controlBinding ?? {}),
        };
 
        const createdEvent : RunEvent = {
            eventId:crypto.randomUUID(),
            runId,
            sequence:1,
            type:"RUN_CREATED",
            timestamp,
            payloadVersion:1,
            payload:{},
        };
 
        this.store.create(run,createdEvent);
 
        return run;
    }
白话

工厂方法入口：调用方只递输入，不许自己拼 Run 对象——构造逻辑集中在一处，谁都造不出畸形 Run。

主键在出生瞬间生成：ID 先于状态存在，之后每一条事件都能引用它。

时间戳取自服务端时钟——客户端时间是不可信输入。

可选链解析控制绑定：把策略上下文附到 Run 上；没配置解析器也不会崩（undefined 安全通过）。

开始构造 Run 快照：前三个字段锁定归属——哪个租户、哪段对话。

起点必须是 QUEUED 而不是 RUNNING：此刻还没过资源准入，谁也无权「出生即执行」。

userInput 与 workspacePath 原样留存：任务当时到底收到了什么，永远可查。

startedAt / finishedAt / checkpointId / failureReason 显式置 null——「未来才填的字段」本身就是 schema 文档。

条件展开：runPolicy 没传就不写这个字段，绝不让 undefined 混进快照污染数据。

同时构造第一条事件 RUN_CREATED——出生证明和本人一起办理。

sequence 从 1 开始：整条事件流的序号原点，回放时靠它校验顺序与完整性。

payloadVersion:1 给事件格式定版本——将来格式演进，老事件依然可以被正确解读。

决定性的一行：Run 与首条事件在同一个 SQLite 事务中写入——要么都存在，要么都不存在，不存在「有状态没历史」的中间世界。

返回内存中的快照给调用方，持久化的真相已经落库。

失败路径的两道保险：finally 兜底与去重键

好结局讲完了，剩下的是工程的大部分：出错时怎么办。第一道保险在 executeQueuedRun 的 finally 块——无论成败，证据必须保留。

白话

启动阶段就炸了？先把 Run 标成 INTERRUPTED（原因 START_FAILED）——绝不让状态停在虚假的 RUNNING 上。

然后原样 rethrow：记录归记录，错误照常向上传播，吞掉异常等于谎报平安。

finally 兜底块：不管上面走的是哪条路，这里的代码都会执行。

第一步先退订事件流——不退订就是监听器泄漏。

注释即设计：中断/失败的执行也会在 workspace 留下用户文件——这些是事实，必须保留证据。

所以失败也要 captureAfter：崩溃前的半成品文件同样是这次 Attempt 的一部分。

但 Artifact 固化更挑剔：只有抵达终态（COMPLETED 或 FAILED）才收集正式交付物。

区分很微妙：证据（evidence）人人有份，交付物（artifact）凭终态领取。

第二道保险在事件桥接层：at-least-once 投递如何变成幂等写入。答案是给「最终结果」一个稳定的去重键。

CODE · src/events/runtime-event-bridge.ts（节选） 
            case "tool_completed":
                return {
                    runId: event.runId,
                    type: event.isError
                        ? "TOOL_FAILED"
                        : "TOOL_COMPLETED",
                    timestamp: event.timestamp,
                    payloadVersion: 1,
 
                    // 一个工具调用只能拥有一个最终结果。
                    // 即使 Runtime 错误地先发成功、后发失败，也使用同一个去重键。
                    dedupeKey: `tool:${event.toolCallId}:finished`,
                    payload: {
                        toolCallId:event.toolCallId,
                        toolName:event.toolName,
                        result: event.result,
                        isError: event.isError,
                    },
                };
白话

这是翻译层：把 SDK 的即时事件（tool_completed）翻译成 Harness 的业务事件（RunEvent）。

成功与失败共用一条「完成」通道，只是 type 不同——工具调用的生命周期终点只有一个语义位置。

去重键的灵魂在模板：tool:{toolCallId}:finished。同一个工具调用，无论 Runtime 发几遍完成事件，键都相同。

数据库层 UNIQUE(run_id, dedupe_key) 部分唯一索引只放行第一条——第二条插入直接被拒。

效果：at-least-once 投递（可能重复送达的消息机制）就此变成幂等写入——重复一万次，结果也只记一次。

连 Runtime 自己犯错（先报成功、后补失败）都被这把锁挡住：第一个到达的事实获胜，且不可覆盖。

对照记忆：text_delta 高频碎片只喂给实时展示、由 outputStore 拼接 finalText，不落库——审计流里只留干净的事实。
