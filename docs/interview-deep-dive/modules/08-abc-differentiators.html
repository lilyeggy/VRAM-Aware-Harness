差异化深化 A / B / C

任务能跑通只是及格线。三个方向分别对应 agent infra 岗位的 eval、observability、inference gateway 关键词。

车队管理三件套

A 是行车记录仪 + 油耗报表（任务跑完了，但跑得好吗？）；B 是车队调度大屏；C 是备用路线导航（主路堵了自动换备路，连续堵路就先不推荐这条路）。三者共享一个设计哲学——零侵入：

📊

A · 执行质量评测（Eval）

只读已有落库数据，零新增采集。行业标配指标 + 控制面护城河指标。输出 scripts/eval-report.ts 文本报表 + GET /eval JSON。

🖥️

B · 观测驾驶舱（Observe）

独立只读页 /observe，与任务操作台解耦。状态环形图、完成度渐变条、租户对比、背压堆叠条、明细表，多租户切换。

🧭

C · LLM 路由网关（Gateway）

OpenAI 兼容代理：主备回退 + 熔断 + RouteDecision 记录。Agent/控制面/沙箱都不变，只改 models.json 的 baseUrl 指向网关。

💡
为什么"零侵入"是优点而不是妥协？

如果评测需要往执行路径里插桩，评测系统本身就成了新的故障点和性能损耗源。A 的全部数据来自控制面本来就为"可解释决策"落库的事实——这恰恰证明前面模块的持久化设计是超前的投资：写数据时没想好怎么用，用的时候发现全都够。

方向 A：从六张表读出三层指标

agent_runs终态/租户/排队耗时(created→started)/执行耗时/checkpoint
run_attempts尝试次数（平均 attempt 数）
tool_executions工具副作用画像 + 被拦危险副作用数
run_events(MODEL_COMPLETED)LLM token/cost 用量（聚合 payload.usage）
run_workspace_diffs / run_artifacts / run_output_chunks完成度：diff 率 / artifact 率 / finalText 率
policy_decisions资源准入评测：背压触发率、观测失败率

两类指标的划分是面试记忆点——行业标配证明你懂常识，护城河指标证明你有独家视角：

📏
行业标配

成功率、平均尝试次数、queueWaitMs/runDurationMs 的 avg+P95、token 总量与成本

🏰
控制面护城河

背压触发率 pressuredRate、无人值守率 unattendedRate、危险拦截率 blockedDangerousToolCount、cache 命中率 cacheRead/(input+cacheRead)

"无人值守率"的定义最能体现控制面语义——它直接复用 Module 3 的 canAutomaticallyReplay：

CODE · src/eval/evaluation-aggregator.ts 
// 无人值守率：没有「被拦下的危险副作用」的任务占比。
unattendedRate: rate(
    runs.filter((r) => r.blockedDangerousToolCount === 0).length,
),

// 单个 Run 内的计数逻辑：
// 仍处于 PREPARED 且不可自动重放 = 被拦下的危险副作用。
if (
    row.status === "PREPARED"
    && !canAutomaticallyReplay(row.status, row.effect)
) {
    blockedDangerousToolCount += 1;
}
白话翻译

一个任务全程没有任何"需要人工确认的危险副作用"，才算真正的无人值守。

判定标准不是新造一套规则，而是调用和控制面完全相同的 canAutomaticallyReplay 函数——安全语义只有一份，评测层和控制面永远不会出现两套标准打架。

这就是"零新增采集"背后的深层一致性：数据模型即安全模型。

方向 C：回退语义与熔断三态

网关的回退规则一句话就能讲清（面试原话）：429 / 5xx / 网络错误 / 超时 → 后端问题，换下一个后端重试；其余 4xx → 请求本身的问题，换了也没用，直接透传。

熔断器是经典三态机——Closed（正常放行）→ Open（连续失败达阈值，冷却期内跳过）→ Half-Open（冷却结束允许一次试探）：

CODE · src/llm-gateway/model-router.ts · candidatesFor 
candidatesFor(logicalModel: string): LlmBackend[] {
    const list = this.backendsByModel.get(logicalModel) ?? [];
    const now = this.now();
    return list.filter((b) => {
        const state = this.states.get(b.id);
        if (!state) return true;
        if (state.circuitOpenUntil === 0) return true;
        if (now >= state.circuitOpenUntil) {
            // 冷却结束：半开，允许一次尝试
            state.circuitOpenUntil = 0;
            return true;
        }
        return false;
    });
}
白话翻译

按配置优先级取出该逻辑模型的后端候选列表。

逐个检查熔断状态。

熔断关闭（circuitOpenUntil 为 0）：正常候选。

冷却期已过：半开——清零并放进候选，给它一次将功赎罪的机会。

还在冷却期：跳过，避免反复打挂掉的后端。

配合 recordFailure：连续失败 ≥3 次打开熔断 30 秒；recordSuccess 清零计数。默认阈值和冷却时间都可注入配置。

回退主循环里每一步都记录 RouteDecision——选谁、试了谁、是否回退、延迟、成败，与 policy_decisions「决策台账」同一思路：

CODE · src/llm-gateway/llm-gateway.ts · handleChatCompletions 节选 
for (const backend of candidates) {
    attempted.push(backend.id);
    const outcome = await this.tryBackend(backend, body);
    if (outcome.kind === "success") {
        this.router.recordSuccess(backend.id);
        this.router.recordDecision({ ...base,
            chosenBackendId: backend.id, status: "SUCCESS",
            httpStatus: outcome.response.status,
            fallback: attempted.length > 1, ... });
        return outcome.response;
    }
    if (outcome.kind === "client-error") {
        // 请求本身问题：不回退，直接透传上游 4xx。
        this.router.recordDecision({ ...base, status: "FAILED", ... });
        return outcome.response;
    }
    // retryable：记录失败并回退下一个后端
    this.router.recordFailure(backend.id);
}
白话翻译

依序尝试每个候选后端，记下试过谁。

成功：清零熔断计数，记录 SUCCESS 决策——fallback 字段如实标注"这是换过一次才成功的"。

4xx 客户端错误：请求本身有问题，回退到别的后端只会重复失败，直接把错误透传给调用方。

可重试失败（429/5xx/网络/超时）：给这个后端记一笔失败，继续试下一个。

循环结束还没成？502 + 全部已试后端列表。stream:true 时响应体是透传的上游 SSE 流；转发时逻辑模型名会被替换为后端真实模型名。
