可信身份与六道防串防线

请求体里写着 tenantId: "tenant-a"——你敢信吗？身份只在认证那一刻产生一次，之后一路固化，永不采信自报。

机场安检的登机牌模型

你出示护照（API Key），安检系统打印登机牌（RequestPrincipal）。之后全程——贵宾室、登机口、机上餐食——只看登机牌。有人捡到别人的票想混进另一家航空公司的贵宾室？每个闸口都核对归属，对不上一律回答"查无此人"（404），而不是"这不是你的"（403 泄露存在性）。

1
HTTP 层验 Key

requirePrincipal(request, scope)：Bearer/x-api-key → 摘要 → ApiCredentialStore.authenticate → 命中 {tenantId, scopes}

2
归属在入口一次定死

submitRun 用 principal.tenantId 写入 agent_runs.tenant_id——从此下游调度/沙箱/策略/查询永远用 run.tenantId，不再"猜归属"

3
产品决定：tenant = 用户

RequestPrincipal 精简为 {tenantId, scopes}；migration v15 删除冗余 subject_id。scopes 是授权维度（tasks:read / tasks:write / models:generate…）

🚨
核心认知：Agent 运行时代码是"敌方"

"Agent Runtime 是被隔离的对象，不是可信基础设施。"所以它对用户权限、文件、网络的访问必须经过外面包着的 ToolGateway + 策略 + 沙箱拦截——不能因为"循环是我写的"就放权。

requirePrincipal：统一强制点

每条受保护路由声明自己的 scope；ALLOW/DENY 全部进审计台账：

CODE · src/http/harness-http-api.ts 
private requirePrincipal(request: Request, scope: string): RequestPrincipal {
    if (this.accessControl === undefined) {
        // Retained only for direct legacy unit tests; composition always injects auth.
        return { tenantId: "legacy", scopes: ["*"] };
    }
    const authorization = request.headers.get("authorization");
    const rawKey = authorization?.startsWith("Bearer ")
        ? authorization.slice("Bearer ".length).trim()
        : request.headers.get("x-api-key")?.trim();
    if (rawKey === undefined || rawKey.length === 0) {
        this.audit("AUTHENTICATE", "DENY", null, "missing_api_key");
        throw new HttpError(401, "缺少 API Key");
    }
    const principal = this.accessControl.authenticate(rawKey);
    if (principal === null) {
        this.audit("AUTHENTICATE", "DENY", null, "invalid_or_revoked_api_key");
        throw new HttpError(401, "API Key 无效或已撤销");
    }
    if (!hasScope(principal, scope)) {
        this.audit(scope, "DENY", principal, "missing_scope");
        throw new HttpError(403, `缺少权限：${scope}`);
    }
    this.audit(scope, "ALLOW", principal, "scope_granted");
    return principal;
}
白话翻译

唯一例外：纯单测/演示无鉴权组件时降级为 legacy 身份——正式组装永远注入真实认证。

从两个常见位置提取原始 Key：Authorization 头优先，x-api-key 兜底。

连 Key 都没带？记一条 DENY 审计再返回 401。

拿原始 Key 去凭证库比对摘要——注意存储的是哈希不是明文。

Key 无效或已撤销？同样先审计后 401。

身份对了还要看权限范围：这把 Key 有没有当前路由要求的 scope？没有就 403。

放行也记 ALLOW 审计——每一次授权决定都有据可查。

返回的 Principal 就是后续所有逻辑唯一信任的身份凭据。

六道防线：逐层设防，不赌任何单点

多租户防串不是靠一处检查，而是六层叠着来——任何一层有疏漏，下一层还兜得住：

🔑

① tenant 只来自身份

submitRun 用 principal.tenantId，请求体里的 tenantId 被直接忽略

🔗

② 归属链一致性校验

ManagedAgentRuntime 四元组校验：instance.tenantId / templateVersionId / session.tenantId / session.instanceId 与 run 全对得上才启动

♻️

③ Session 复用校验

DefaultPiControlPlane.resolve 对已存在 session 检查 tenant/instance 归属，防复用别人的会话

🔎

④ 查询侧按 tenant 收口

listForTenant(tenantId)、getForTenant(id, tenantId) 双参数——服务端从不信任客户端自称归属

🙈

⑤ IDOR 反枚举

跨租户访问统一返回 404，与"不存在"不可区分——堵住资源枚举探测

🏛️

⑥ 数据库约束兜底

外键、UNIQUE、CHECK 在存储层拒绝孤儿与非法状态——应用层漏了还有最后一道闸

两段关键代码：404 反枚举 与 服务端目录生成

CODE · src/http/harness-http-api.ts · getRequiredRun 
if (request !== undefined && this.accessControl !== undefined) {
    const principal = this.requirePrincipal(request, scope);
    if (run.tenantId !== principal.tenantId) {
        throw new HttpError(404, `找不到 AgentRun：${runId}`);
    }
}
白话翻译

拿到合法身份后再核对：这个 Run 的租户和你一致吗？

不一致就返回 404"找不到"。为什么不是 403？因为 403 等于承认"这个 id 存在，只是你看不了"——攻击者可以借此枚举出全库的资源 ID。404 让两种情况完全不可区分。

CODE · src/workspaces/workspace-service.ts · create 
const id = crypto.randomUUID();
const workspace: Workspace = {
    id,
    tenantId,
    name,
    rootPath: resolve(this.root, tenantId, id),
    createdAt: new Date().toISOString(),
};
if (!workspace.rootPath.startsWith(`${this.root}/`)) {
    throw new Error("非法 Workspace 根目录");
}
mkdirSync(workspace.rootPath, { recursive: true, mode: 0o700 });
if (this.executionUid !== undefined) {
    // A non-root container UID must own its single bind-mounted root.
    // Failure is safer than creating a Run that can never access its Workspace.
    if (statSync(workspace.rootPath).uid !== this.executionUid) {
        chownSync(workspace.rootPath, this.executionUid, -1);
    }
} catch (error) {
    rmSync(workspace.rootPath, { recursive: true, force: true });
    throw new Error(`无法将 Workspace 交给容器 UID ${this.executionUid}: ...`);
}
白话翻译

目录由服务端生成：root / tenantId / 随机 UUID 三段拼装——客户端永远只能提交不透明的 workspaceId，不能提交宿主机路径。

前缀校验防止路径穿越逃出根目录。

0o700 权限：只有属主能进。

容器里跑 Agent 用的是非 root UID，目录必须归它所有，否则挂载后写不了文件。

注释原文就是面试答案："chown 失败比创建一个永远无法访问的 Run 更安全"——删掉目录、拒绝创建、把错误抛给上层。

诚实短板（主动讲）

API Key 无 TTL——泄露即长期有效（演进方向：会话登录作为第二认证器接到同一 RequestPrincipal 主干）；网关无 per-tenant 限流配额；development profile 沙箱隔离弱，产品化必须 container/strict。
