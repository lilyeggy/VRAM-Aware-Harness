04

资源准入与背压

120 个并发打进 T4 时，新任务是 START 还是 QUEUE？——先看仪表盘，再下决策，每次决策都落库。

匝道红绿灯：不是不让走，是现在上去谁都快不了

高速主路（GPU + vLLM）已经堵死时，匝道灯变红让新车排队。这不是拒绝服务，而是背压——保护已经在上路的所有车都能到达。

传感器坏了怎么办？这个系统的回答是：灯默认常红（fail-closed），绝不猜"应该没事"。

1

观测 — 双源并行采集 vLLM /metrics 与 nvidia-smi

→
2

分类 — 四组阈值判定 NORMAL / BUSY / CRITICAL / UNKNOWN

→
3

决策 — START 或 QUEUE + reasonCode，同事务落库

💡
为什么是三段式？

观测、分类、决策各自是纯逻辑/可注入依赖的小模块，可以独立单测、独立失败、独立替换。"显存高就排队"人人会做；面试官想听的是每一层的细节和失败路径。

观测层：双源并行，单源失败可降级

VllmResourceObserver 用 Promise.all 同时拉两个数据源——避免最坏情况下串行等待两次 timeout。一个源挂了不整体失败；只有双源全挂才返回 ok:false。快照字段允许 null——只有所有压力信号都不可用才算 UNKNOWN。

📊

vLLM /metrics

running / waiting 请求数、KV cache 使用率、prompt/generation token 累计 Counter

🖥️

nvidia-smi CSV

显存 total/used/free、利用率。多 GPU 显存求和、利用率取最大值

🔍
Prometheus 解析的两个反直觉规则

同一指标可能因 model_name 标签出现多行：请求数和 Token Counter 代表总工作量 → 求和；KV cache 代表压力 → 取最大值，因为平均值会掩盖高压实例。另外 vLLM ≥0.7 把 kv_cache_usage_perc 改名 gpu_cache_usage_perc——解析器两个名字都认。

Token 速率怎么算？Counter 型指标需要两次观测算差值；vLLM 重启后 Counter 归零（current < previous）→ 返回 null，绝不给假速率。

决策矩阵：压力越大，越保守

DeterministicExecutionPolicy 的 decide() 就一张四行决策表——注意 BUSY 分支里那条"每租户最多一个在跑"的规则，它是压力之下公平性的最后防线。

CODE · src/resources/execution-policy.ts 
const pressure = input.classification.pressure;
switch(pressure){
    case "CRITICAL":
        return this.createDecision(input, "QUEUE", "RESOURCE_CRITICAL");
    case "UNKNOWN":
        return this.createDecision(input, "QUEUE", "RESOURCE_UNKNOWN");
    case "BUSY":
        if (input.activeRunCount >= this.config.maxActiveRuns) {
            return this.createDecision(input, "QUEUE", "GLOBAL_CONCURRENCY_LIMIT");
        }
        if (input.activeTenantRunCount > 0) {
            return this.createDecision(input, "QUEUE", "RESOURCE_BUSY_TENANT_LIMIT");
        }
        return this.createDecision(input, "START", "RESOURCE_BUSY_TENANT_AVAILABLE");
    case "NORMAL":
        if (input.activeRunCount >= this.config.maxActiveRuns) {
            return this.createDecision(input, "QUEUE", "GLOBAL_CONCURRENCY_LIMIT");
        }
        return this.createDecision(input, "START", "RESOURCE_NORMAL");
}
白话翻译

取出分类器给出的压力等级。

CRITICAL（临界）：没得商量，排队。

UNKNOWN（看不清）：也排队——看不清就是危险，不是机会。

BUSY（繁忙）：先看全局并发是否已达上限，满了就排。

全局还有空位时再看租户：这个租户已有任务在跑？那也排队——繁忙时段每租户最多占一席，防止一家独占余量。

租户还没有任务在跑才放行 START。

NORMAL（正常）：只受全局并发上限约束，有空位就 START。

每个决策都带 reasonCode——事后能回答"为什么当时没让我跑"。

fail-closed 现场：观测失败 = QUEUE，并且照样落库

这一段是整个模块的灵魂："看不见"本身也是被审计的事实。不伪造快照、不放行、不静默——决策记录里 snapshot 为 null 并写明失败原因，数据库 CHECK 约束（migration v4）双重保证这个语义。

CODE · src/resources/resource-admission-service.ts 
const observation = await this.observer.observe();
// 观测失败的情况下
if (!observation.ok){
    const decision : PolicyDecision = {
        decisionId:crypto.randomUUID(),
        runId:request.runId,
        action:"QUEUE",
        reasonCode:"RESOURCE_OBSERVATION_FAILED",
        resourceSnapshotId:null,
        pressure:"UNKNOWN",
        observationFailureReason:observation.reason,
        decidedAt:new Date().toISOString(),
    };

    this.decisionRecorder.save(decision, null);

    return { observation, classification:null, decision }
}
白话翻译

向观测器要一次真实资源快照。

观测失败了——两个数据源都没给出可信信号。

构造一个决策对象：动作是排队……

原因码明确写着 RESOURCE_OBSERVATION_FAILED，不是模糊的"出错了"。

快照 ID 为 null——我们没有数据，就不假装有数据。

压力记 UNKNOWN，并把具体失败原因（超时？HTTP 错误？格式非法？）原样带上。

关键一步：这次"失败的准入"照样写入决策台账。审计员事后能看到每一次 QUEUE 的理由。

返回给调用方，上层据此释放 slot 并重新入队。

💡
fail-closed vs fail-open

安全系统从"不允许"起步逐条放行，而不是从"全允许"收窄。这条哲学在课程里出现了四次：观测失败→QUEUE、副作用未知→人工确认、能力缺失→REJECTED、runtime 证据不符→删容器。面试时主动把这四条串起来讲，就是"设计一致性"的最佳证明。

加分项：预算装饰器与真机证据

基础策略之上还有一个装饰器 BudgetAwarePolicy：原策略说 START 之后，再查租户账本（ResourceLedger 的 commit/settle 模型）和公平份额 floor(capacity × weight / totalWeight)，超了就降级 QUEUE + TENANT_BUDGET_EXCEEDED。

💰
调度尊重"已消耗量"，不只是"在跑几个"

每个 running attempt 先 commit 占用单位、退出时 settle 结算——账本同时驱动公平份额准入和事后计费审计。

🧪
真机证据：T4 120 并发背压实验

AutoDL Tesla T4 16G + vLLM 0.7.3，120 并发压测 → running=120、kv≈62% → CRITICAL → 新任务 QUEUE 落库（scripts/e2e-gpu-pressure.ts）。

⚠️
诚实边界

准入走 running/kv-cache 压力路径（真实），但块调度与超大并发下的绝对公平份额仍属估算——面试时主动说这句。

场景题：某天 vLLM 进程卡死，/metrics 请求 504 超时；但 nvidia-smi 工作正常。这时提交的新任务会遇到什么？

解析 Prometheus 文本时，为什么 num_requests_running 多行求和，而 kv_cache_usage_perc 却取最大值？

vLLM 重启后第一次计算 token 速率，得到的是 null 而不是一个很小的数。为什么这样设计？
