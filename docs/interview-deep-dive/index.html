一句话定位 · 必须原文背下

VRAM-Aware Agent Harness 是一个支持团队共享本地大模型的多租户 Agent 任务服务。用户在独立 Workspace 中提交任务、观察 Agent 执行并获得最终回答、文件 Diff 和 Artifact；系统负责可信租户身份、隔离运行环境、公平调度共享 GPU、工具权限与副作用治理，以及故障后的安全恢复。

一个隐喻定调：物业公司与房客

Agent（Pi）是房客——会自己做饭、洗澡、接待客人，对应思考、调模型、用工具。Harness 是物业公司——决定谁能进楼、哪间房给谁用、水电超载要限流、出了事故怎么善后。

物业不替房客过日子；但没有物业的楼，是危楼。

🧠

自己决定做什么：推理、选择工具、组织回答。项目复用 Pi SDK，不重新实现「模型—工具循环」——动脑的事归它。

🏢

物业 = Harness（控制平面）

身份、策略、调度、隔离、记账、恢复。它不替模型做任何决策，但在副作用发生前握有最终否决权——安排与安保的事归它。

💡
关键洞察：否决权放在哪里

控制面不替模型做工具选择，但必须在副作用发生之前有最终否决权。事后审查无法撤销一次已经发出去的网络请求或已经删掉的文件——所以检查点必须在行动之前，而不是之后。

白话

Runtime 是「正在发生的执行」：SDK 里的事件转瞬即逝，进程一崩就没了。

所以事件也要分两轨：RuntimeEvent 属于执行的瞬间，RunEvent 属于 Harness 的长期记忆。

面试一句话：底层 SDK 的事实会消失，Harness 把值得保留的部分翻译成自己的业务事实，永久落库。

⚡

RuntimeEvent · 即时轨

存在于 SDK 执行的瞬间：token 流、工具开始/结束。其中 text_delta 这类高频碎片只用于实时展示，不落库。

🗄️

RunEvent · 持久轨

Harness 长期保存的业务事实：RUN_CREATED、TOOL_COMPLETED、策略决策……带 sequence 序号，可完整回放。

💡
这就是「事件溯源」（Event Sourcing）思想

agent_runs 表存「现在是什么状态」，run_events 表存「过去发生过什么」。查询看快照所以快，审计看事件流所以全——两者各司其职，缺一不可。

一张只读的迁移表：每个状态只能去「名单上」的状态，类型系统保证六个状态一个不少。

Run 的诞生：状态与历史在同一事务里落地

createQueuedRun 是每个 Run 的出生证明开具处。注意最后那行 store.create(run, createdEvent)——Run 快照和第一条事件必须在同一个 SQLite 事务里写入，否则可能出现「状态变了但历史没记」的裂缝。

CODE · src/runs/run-service.ts 
    createQueuedRun(input : StartRunInput) : AgentRun {
        const runId = crypto.randomUUID(); 
        const timestamp = new Date().toISOString();
        const controlBinding = this.controlBindingResolver?.resolve(input);
 
        const run : AgentRun = {
            id:runId,
            tenantId:input.tenantId,
            harnessSessionId:input.harnessSessionId,
            status : "QUEUED",
            userInput:input.userInput,
            workspacePath:input.workspacePath,
            createdAt:timestamp,
            updatedAt:timestamp,
            startedAt:null,
            finishedAt:null,
            checkpointId:null,
            failureReason:null,
            ...(input.runPolicy === undefined
                ? {}
                : { runPolicy: input.runPolicy }),
            ...(controlBinding ?? {}),
        };
 
        const createdEvent : RunEvent = {
            eventId:crypto.randomUUID(),
            runId,
            sequence:1,
            type:"RUN_CREATED",
            timestamp,
            payloadVersion:1,
            payload:{},
        };
 
        this.store.create(run,createdEvent);
 
        return run;
    }
白话

工厂方法入口：调用方只递输入，不许自己拼 Run 对象——构造逻辑集中在一处，谁都造不出畸形 Run。

主键在出生瞬间生成：ID 先于状态存在，之后每一条事件都能引用它。

时间戳取自服务端时钟——客户端时间是不可信输入。

可选链解析控制绑定：把策略上下文附到 Run 上；没配置解析器也不会崩（undefined 安全通过）。

开始构造 Run 快照：前三个字段锁定归属——哪个租户、哪段对话。

起点必须是 QUEUED 而不是 RUNNING：此刻还没过资源准入，谁也无权「出生即执行」。

userInput 与 workspacePath 原样留存：任务当时到底收到了什么，永远可查。

startedAt / finishedAt / checkpointId / failureReason 显式置 null——「未来才填的字段」本身就是 schema 文档。

条件展开：runPolicy 没传就不写这个字段，绝不让 undefined 混进快照污染数据。

同时构造第一条事件 RUN_CREATED——出生证明和本人一起办理。

sequence 从 1 开始：整条事件流的序号原点，回放时靠它校验顺序与完整性。

payloadVersion:1 给事件格式定版本——将来格式演进，老事件依然可以被正确解读。

决定性的一行：Run 与首条事件在同一个 SQLite 事务中写入——要么都存在，要么都不存在，不存在「有状态没历史」的中间世界。

返回内存中的快照给调用方，持久化的真相已经落库。

启动阶段就炸了？先把 Run 标成 INTERRUPTED（原因 START_FAILED）——绝不让状态停在虚假的 RUNNING 上。

然后原样 rethrow：记录归记录，错误照常向上传播，吞掉异常等于谎报平安。

finally 兜底块：不管上面走的是哪条路，这里的代码都会执行。

第一步先退订事件流——不退订就是监听器泄漏。

注释即设计：中断/失败的执行也会在 workspace 留下用户文件——这些是事实，必须保留证据。

所以失败也要 captureAfter：崩溃前的半成品文件同样是这次 Attempt 的一部分。

但 Artifact 固化更挑剔：只有抵达终态（COMPLETED 或 FAILED）才收集正式交付物。

区分很微妙：证据（evidence）人人有份，交付物（artifact）凭终态领取。

这是翻译层：把 SDK 的即时事件（tool_completed）翻译成 Harness 的业务事件（RunEvent）。

去重键的灵魂在模板：tool:{toolCallId}:finished。同一个工具调用，无论 Runtime 发几遍完成事件，键都相同。

数据库层 UNIQUE(run_id, dedupe_key) 部分唯一索引只放行第一条——第二条插入直接被拒。

效果：at-least-once 投递（可能重复送达的消息机制）就此变成幂等写入——重复一万次，结果也只记一次。

连 Runtime 自己犯错（先报成功、后补失败）都被这把锁挡住：第一个到达的事实获胜，且不可覆盖。

对照记忆：text_delta 高频碎片只喂给实时展示、由 outputStore 拼接 finalText，不落库——审计流里只留干净的事实。

03

副作用记账与崩溃恢复

Agent 不是聊天机器人——它的 bash 会真删文件。进程在工具执行到一半时崩溃，重启后这个工具该重放吗？

隐喻：支票双联存根

出纳每动一笔钱都要留底：先把「我准备转 500 元」的存根压在玻璃板下，转账成功后再盖「已完成」章。银行倒闭重启后，看到只有存根没有章的交易怎么办？答案藏在四步流程里：

1
写存根：PREPARED

动手前先把意图持久化——「我准备执行这个工具」。此刻什么都没改变，但账上已经有了这一笔。

2
盖章：SUCCEEDED

真实执行完成后，结果与检查点在同一个事务里落库。从此这笔调用有了不可抵赖的最终结论。

3
重启盘点：发现无章存根

银行（进程）倒闭重启后，扫描账本：那些只有 PREPARED 没有 SUCCEEDED 的「孤儿存根」就是全部疑点。

4
分类处置：绝不盲目重转

纯查询（READ_ONLY）就安全重做；说不清影响的（UNKNOWN）就冻结等人工。宁可慢，不可错。

🏛️
这不是新发明：双复写（Write-Ahead Intent）

「先持久化意图，再执行，最后确认」正是数据库 WAL（预写日志）与分布式事务 2PC（两阶段提交）的共同思想。你的 Agent Harness 和 PostgreSQL 用的是同一个直觉。

两个三元组：整个机制的数据模型

ToolEffect · READ_ONLY只读不改世界——重放一万次也无害
ToolEffect · IDEMPOTENT_WRITE声称幂等的写——注意是「声称」，后面有它的大戏
ToolEffect · UNKNOWN_EFFECT说不清影响——bash 脚本、发邮件都在这里，默认嫌疑犯
Status · PREPARED存根已写，动作未发——崩溃恢复最关心的状态
Status · SUCCEEDED / FAILED已有终局结论的调用，重启后无需任何处置

核心决策函数：谁能自动重放？

恢复安全性的核心不是 Checkpoint 本身，而是副作用分类。整个系统的安全边界浓缩在下面这一个函数里——注意 IDEMPOTENT_WRITE 的下场：

CODE · src/tools/tool-execution.ts 
export type ToolEffect = 
    | "READ_ONLY"
    | "IDEMPOTENT_WRITE"
    | "UNKNOWN_EFFECT";
 
export type ToolExecutionStatus = 
    | "PREPARED"
    | "SUCCEEDED"
    | "FAILED";
 
export function canAutomaticallyReplay(
    status:ToolExecutionStatus,
    effect:ToolEffect,
):boolean{
    if (status !== "PREPARED"){
        return false;
    }
 
    switch(effect){
        case "READ_ONLY":
            return true;
        case "IDEMPOTENT_WRITE":
            // “写入被声明为幂等”本身不足以证明外部系统会使用稳定幂等键。
            // 在 ToolExecution 持久化并校验真实幂等证据前保持 fail closed。
            return false;
        case "UNKNOWN_EFFECT":
            return false;
    }
}
白话

先定义效果三分法：只读、声称幂等的写、说不清的写。类型即文档——三种可能穷尽，没有第四种。

执行状态也是三态：存根（PREPARED）、成功、失败。两个三元组组合出全部审计场景。

决策函数登场：输入「停在哪个状态 + 属于哪类效果」，输出一个布尔值——能不能不经人批准直接重放。

第一道闸：只有 PREPARED 才考虑重放。SUCCEEDED 有结果缓存可直接返回，FAILED 有错误结论——都不是「待处理」。

READ_ONLY 是唯一绿灯：读操作不改变世界，重放天然无害。

全场最精彩的一行：IDEMPOTENT_WRITE 也是红灯！注释给出了理由——「写入被声明为幂等」只是工具作者的口头声明，不是证据。

外部系统是否真的用稳定幂等键去重，控制面无法验证；在拿到持久化的真实幂等证据之前，保持 fail closed——不确定就拒绝。

UNKNOWN 更不用说：连影响都描述不清的操作，绝不允许机器擅自重来。

💡
面试金句：声明 ≠ 证据

「写入被声明为幂等」本身不足以证明外部系统会使用稳定幂等键。恢复安全性靠的不是乐观假设，而是把不确定当成危险——这就是 fail-closed 与 fail-open 的分野。

ToolGateway.execute：顺序就是安全

所有工具调用的必经之路。盯住顺序：策略检查 → 查历史 → PREPARED 落库 → 最后才 invokeTool。每换一次顺序，都会打开一种新的漏洞。

CODE · src/tools/tool-gateway.ts（节选） 
    async execute(
        input:ExecuteToolInput,
        invokeTool:() => Promise<unknown>,
    ) : Promise<unknown>{
        // 策略检查必须发生在 PREPARED 写入和真实副作用之前。
        this.policyGuard?.assertAllowed(input);
 
        const history = this.store.getByToolCall(runId,toolCallId);
        let preparedExecution : ToolExecution;
 
        if (history === null){
            preparedExecution = {
                id : crypto.randomUUID(),
                runId,
                toolCallId,
                toolName:input.toolName,
                arguments:input.arguments,
                effect:input.effect,
                status:"PREPARED",
                result:null,
                errorMessage:null,
                createdAt:new Date().toISOString(),
                finishedAt:null,
            }
            this.store.prepare(preparedExecution);
        } else {
            switch(history.status){
                case "SUCCEEDED":
                    return history.result;
                case "FAILED":
                    throw new Error(`工具执行失败:${history.errorMessage}`);
                case "PREPARED":
                    if (
                        !canAutomaticallyReplay(
                            history.status,
                            history.effect,
                        ))
                        {
                            throw new Error(
                                `不允许自动重放：${history.effect}`,
                            );
                        }
                    // 允许重放时复用原来的执行记录，
                    // 不能再次调用 store.prepare()，否则会违反唯一约束。
                    preparedExecution = history;
                    break;                    
            }
        }
白话

execute 接收两样东西：要执行什么（input），以及怎么真正执行（invokeTool 回调）——网关掌握流程，Runtime 提供动作。

第一行就是铁律：策略守卫 assertAllowed 必须跑在最前面——在任何记账、更在任何副作用之前。没授权的事，连存根都不配写。

第二步查历史：这个 toolCallId 是否已经有记录了？正常执行这里是空，崩溃恢复时这里就有故事。

无历史 = 全新调用：开始构造完整的执行记录——谁发起的（runId）、调用的是什么（toolName）、参数原样封存。

effect 与 status 一并落库：效果分类是调用方申报、策略审批过的，此刻固化成账面事实。

status 定格为 PREPARED：存根压进玻璃板下，result 还是 null——世界尚未改变。

store.prepare 把存根持久化。从这里开始，「我打算做什么」已经是数据库里不可否认的事实。

有历史的三个分支之一：SUCCEEDED 直接返回缓存的结果——同一次调用重复到达也只执行一次，天然幂等。

分支之二：FAILED 直接抛错并带回当时的错误信息——失败的结论同样不许被静默覆盖。

分支之三：停在 PREPARED 的孤儿存根——问 canAutomaticallyReplay 能否自动重放。

答不了绿灯就抛错冻结，把效果分类写在错误信息里供人工审查——绝不猜。

能重放的细节：复用原来的执行记录对象，绝不能再 store.prepare 一次——同一 toolCallId 的唯一约束会让第二次插入当场爆炸。

重启后的决策大脑是 decideRecovery：输入有效 checkpoint 与所有孤儿存根，输出一个三选一的计划：

export function decideRecovery (
    checkpointId:string|null,
    preparedExecution:readonly ToolExecution[],
):RecoveryDecision{
    if (checkpointId === null){
        const action : RecoveryAction = "MANUAL_REVIEW";
        const recoveryReason : RecoveryReason= "NO_CHECKPOINT";
        const execution : RecoveryDecision = {
            action:action,
            reason:recoveryReason,
            blockingToolExecutionId:null,
        }
        return execution;
    };
    const unsafeExecution = preparedExecution.find(
        (execution) => !canAutomaticallyReplay(
            execution.status,
            execution.effect,
        )
    );
 
    if (unsafeExecution !== undefined){
        return {
            action:"MANUAL_REVIEW",
            reason:"UNSAFE_TOOL_EFFECT",
            blockingToolExecutionId:unsafeExecution.id,
        }
    }
 
    return {
        action:"AUTO_RESUME",
        reason:"SAFE_CHECKPOINT",
        blockingToolExecutionId:null,
    }
}
白话

决策函数签名本身就是文档：给一个 checkpoint 引用加一串孤儿存根，还你一个明确的恢复计划。

情形一：连 checkpoint 都没有——无从知道执行到哪，直接 MANUAL_REVIEW（人工审查），理由 NO_CHECKPOINT 写明。

注意设计取舍：没有恢复点时绝不尝试「从头重跑」——那等于把已发生的副作用再来一遍。

情形二：有 checkpoint，但在孤儿存根里找到任何一个不能自动重放的（回到上一屏的那个函数逐一审问）。

只要有一个可疑分子，整体就冻结：action 仍是 MANUAL_REVIEW，并且精确记录 blockingToolExecutionId——告诉人工「卡在这条记录上」。

一票否决制：AUTO_RESUME 要求所有存根全部干净，而不是大多数干净。

情形三：checkpoint 有效且所有存根都是 READ_ONLY 绿灯——放心 AUTO_RESUME，理由 SAFE_CHECKPOINT。

纯函数、无副作用、可单测：恢复正确性可以被 254 个测试里的用例钉死，而不是靠运维经验。

最后一步为什么 RecoveryService 不直接调 runtime.resume？源码里的一段注释就是标准答案：

CODE · src/checkpoints/recovery-service.ts 
 * 这一层只建立恢复计划，不直接调用 AgentRuntime：
 * - 扫描和状态修正是同步、确定性的数据库工作；
 * - Runtime resume 是可能失败的外部执行，应由下一层逐个消费计划。
白话

分层铁律：计划层（RecoveryService）只负责想清楚「该做什么」，执行层（RecoveryExecutor）才负责「去做」。

扫描修正（陈旧 RUNNING → INTERRUPTED，附 PROCESS_RESTART 事件）是确定性的数据库操作——可以批量、可重入、永不部分失败。

而 resume 是可能失败的外部调用，绝不能混进确定层——否则一次失败污染整个扫描批次。

所以 AUTO_RESUME 的计划由下一层逐个调 coordinator.submitResume 消费——重新入队！恢复也要重新过资源准入与公平调度，不许插队。

UNKNOWN（看不清）：也排队——看不清就是危险，不是机会。

BUSY（繁忙）：先看全局并发是否已达上限，满了就排。

全局还有空位时再看租户：这个租户已有任务在跑？那也排队——繁忙时段每租户最多占一席，防止一家独占余量。

租户还没有任务在跑才放行 START。

NORMAL（正常）：只受全局并发上限约束，有空位就 START。

每个决策都带 reasonCode——事后能回答"为什么当时没让我跑"。

数据结构三件套：Map<tenantId, QueuedRun[]> 每租户队列 + tenantOrder[] 轮转数组 + activeTenantByRunId slot 表。看 claimNext 怎么在三者之间跳转：

CODE · src/scheduling/tenant-run-scheduler.ts 
claimNext() : QueuedRun | null {
    // 首先检查全局 slot
    if (this.activeTenantByRunId.size >= this.config.maxActiveRuns){
        return null;
    }

    const tenantsToInspect = this.tenantOrder.length;
    for (let inspected = 0; inspected < tenantsToInspect; inspected += 1) {
        // 从轮转队列头部取出本轮tenant
        const tenantId = this.tenantOrder.shift();
        if (tenantId === undefined) { return null; }

        const tenantQueue = this.queuesByTenant.get(tenantId);
        if (tenantQueue === undefined || tenantQueue.length === 0) {
            this.queuesByTenant.delete(tenantId);
            continue;
        }

        const activeTenantByRunCount = this.getActiveTenantRunCount(tenantId);

        // 当前 tenant 已经达到并发上限，它仍有等待任务，所以放回轮转队尾.
        if (activeTenantByRunCount >= this.config.maxActiveRunsPerTenant){
            this.tenantOrder.push(tenantId);
            continue;
        }

        const run = tenantQueue.shift();
        if (run === undefined){ this.queuesByTenant.delete(tenantId); continue; }

        // 如果这个 tenant 还有等待任务，那么将它放在下一轮队尾
        // 如果已经清空，那么就从 queuesByTenant 删除
        if (tenantQueue.length > 0){ this.tenantOrder.push(tenantId); }
        else { this.queuesByTenant.delete(tenantId); }

        this.activeTenantByRunId.set(run.runId, run.tenantId);
        return run;
    }
    return null;
}

先看果篮是否已满：全局活跃数达到上限就直接返回空。

最多检查一圈所有租户——避免死循环。

轮转指针从队头取出本轮该叫的租号。

这个租户没有等待任务了？清理掉，继续下一家。

统计它当前占了多少个 slot。

达到单租户上限？把它放回队尾但跳过——它还有等待任务，只是这一轮不能领。

从它的队列头部取出第一个等待 Run（FIFO）。

drain：单飞模式（single-flight）

提交任务、释放 slot、定时器到点……很多事件都会喊"推一把队列"。如果每次都真起一个循环，就会并发乱套。解法是 single-flight：

CODE · src/scheduling/run-queue-coordinator.ts 
drain() : Promise<CoordinatorResult[]> {
    // 每次调用都代表系统状态可能发生了变化
    // 因此至少请求进行一轮队列检查
    this.drainRequested = true;

    // 已经有 drain 在执行，重复用同一个 Promise
    if (this.drainPromise !== null){
        return this.drainPromise;
    }

    // 没有 drain 执行，就启动新的推进循环
    this.drainPromise = this.runDrainLoop();
    return this.drainPromise;
}
白话翻译

任何调用者都先把"需要推进"的标志位置真——这是请求的唯一副作用。

已有循环在跑？直接复用同一个 Promise，不另起炉灶。

没有才创建新循环。循环体是 while(drainRequested)：每轮开始清掉标志位、跑一遍 drainOnce；期间又有人调 drain() 标志位重新变真，循环就再来一轮。finally 里清空 drainPromise，允许下次冷启动。

CODE · src/http/harness-http-api.ts 
private requirePrincipal(request: Request, scope: string): RequestPrincipal {
    if (this.accessControl === undefined) {
        // Retained only for direct legacy unit tests; composition always injects auth.
        return { tenantId: "legacy", scopes: ["*"] };
    }
    const authorization = request.headers.get("authorization");
    const rawKey = authorization?.startsWith("Bearer ")
        ? authorization.slice("Bearer ".length).trim()
        : request.headers.get("x-api-key")?.trim();
    if (rawKey === undefined || rawKey.length === 0) {
        this.audit("AUTHENTICATE", "DENY", null, "missing_api_key");
        throw new HttpError(401, "缺少 API Key");
    }
    const principal = this.accessControl.authenticate(rawKey);
    if (principal === null) {
        this.audit("AUTHENTICATE", "DENY", null, "invalid_or_revoked_api_key");
        throw new HttpError(401, "API Key 无效或已撤销");
    }
    if (!hasScope(principal, scope)) {
        this.audit(scope, "DENY", principal, "missing_scope");
        throw new HttpError(403, `缺少权限：${scope}`);
    }
    this.audit(scope, "ALLOW", principal, "scope_granted");
    return principal;
}

function intersectConstraints(
    left: PolicyConstraints,
    right: PolicyConstraints,
): PolicyConstraints {
    return {
        sandboxProfile: intersectSandboxProfiles(
            left.sandboxProfile ?? null,
            right.sandboxProfile ?? null,
        ),
        allowedTools: intersectValues(left.allowedTools, right.allowedTools),
        allowedSkills: intersectValues(left.allowedSkills, right.allowedSkills),
        allowedModels: intersectValues(left.allowedModels, right.allowedModels),
        workspaceRoots: intersectRoots(left.workspaceRoots, right.workspaceRoots),
        allowNetwork: left.allowNetwork && right.allowNetwork,
        allowProcess: left.allowProcess && right.allowProcess,
        allowedSecrets: intersectValues(left.allowedSecrets, right.allowedSecrets),
        resourceLimits: {
            cpuCores: minimum(left.resourceLimits.cpuCores, right.resourceLimits.cpuCores),
            memoryMiB: minimum(left.resourceLimits.memoryMiB, right.resourceLimits.memoryMiB),
            diskMiB: minimum(left.resourceLimits.diskMiB, right.resourceLimits.diskMiB),
        },
    };
}

方向 C：回退语义与熔断三态

网关的回退规则一句话就能讲清（面试原话）：429 / 5xx / 网络错误 / 超时 → 后端问题，换下一个后端重试；其余 4xx → 请求本身的问题，换了也没用，直接透传。

熔断器是经典三态机——Closed（正常放行）→ Open（连续失败达阈值，冷却期内跳过）→ Half-Open（冷却结束允许一次试探）：

        const state = this.states.get(b.id);
        if (!state) return true;

高频追问速答弹药库

每条答案控制在 60 秒内说完，先给结论再给一层细节：

Q1
为什么用 runsc/gVisor 而不自研沙箱？

预算/人力/安全责任都不够自研 runtime。亮点在上层三环：策略边界编译、租户资源管控、可验证证据三元组。没有 KVM 就不声称 strict VM 隔离通过——诚实边界本身就是设计决策。

Q2
资源准入怎么做？背压怎么触发？

vLLM /metrics + nvidia-smi 双源并行 → ResourceSnapshot → 四组阈值分类 NORMAL/BUSY/CRITICAL/UNKNOWN → DeterministicExecutionPolicy 出 START/QUEUE + reasonCode → policy_decisions+resource_snapshots 同事务落库。观测失败=QUEUE(RESOURCE_OBSERVATION_FAILED)，fail-closed。

Q3
任务崩溃了怎么恢复？

ToolEffect 三分类；只有 PREPARED+READ_ONLY 自动重放（IDEMPOTENT_WRITE 也 fail-closed：声明≠证据）。RecoveryService.scanInterruptedRuns 把陈旧 RUNNING 转 INTERRUPTED 并建计划 → decideRecovery 出 AUTO_RESUME/MANUAL_REVIEW → RecoveryExecutor 经 coordinator.submitResume 重新入队——恢复也要重新过资源准入和 slot 占用。

Q4
多租户怎么隔离？

身份层：API Key→摘要比对→Principal{tenantId,scopes}，tenant 不来自请求体；运行层：独立 workspace 目录 + runsc 容器（非 root、只读 rootfs、cap drop ALL、默认无网络）；调度层：Tenant 内 FIFO、租户间 round-robin、双并发上限；数据层：查询按 tenant 收口 + 404 反枚举 + DB 约束兜底。

Q5
为什么 IDEMPOTENT_WRITE 不自动重放？

"写入被声明为幂等"不足以证明外部系统会使用稳定幂等键。在 ToolExecution 持久化并校验真实幂等证据之前保持 fail-closed——声明不等于证据，这是恢复安全性的底线。

Q6
并发更新 Run 会不会互相覆盖？

乐观锁：UPDATE ... WHERE id=$id AND status=$previousStatus，changes!==1 即抛错——过期快照覆盖新状态被挡。事件去重靠 UNIQUE(run_id, dedupe_key) 部分唯一索引；Run 快照与事件同事务写入。

Q7
drain 会不会并发跑多个？

single-flight：drainPromise 复用 + drainRequested 标志位补跑一轮。attemptNext 内部先 claimNext 占 slot；QUEUE 时先 release 再 re-enqueue（顺序反了 enqueue 会拒绝），并保留原 enqueuedAt 防饥饿放大。

Q8
流量翻 100 倍怎么办？

诚实回答"现在不行"+ 给出可信路径：RunStore 换 Postgres、调度器外置或多 Worker 抢 DB 行锁、Sandbox Provider 池化、vLLM 多实例 + 网关路由（RouteDecision 扩展点已预留）。当前单进程是 MVP 有意取舍，控制面语义已被测试锁定，迁移不改行为。

Q9
最大的技术挑战是什么？

推荐答：不是某个算法，而是"让安全成为默认值"——fail-closed 贯穿四条线（观测失败→QUEUE、副作用未知→人工确认、能力缺失→REJECTED、runtime 证据不符→删容器）；以及恢复路径的归属校验（checkpoint.runId/策略快照 runId 双绑定）——多租户防串最容易被漏掉的死角。

Prefill 是计算密集型（整段并行算，GPU 算力打满）；Decode 是显存带宽密集型（每步只算 1 个 token 却要读全部 KV Cache，算力闲着等数据）。PD 分离、Chunked Prefill、量化……全是在处理这对矛盾。

PagedAttention：给 KV Cache 装上"虚拟内存"

传统做法按序列最大长度预分配连续显存——内部碎片高达 60-80%。vLLM 的答案是借鉴操作系统分页：

🧩

逻辑块 + 物理块 + 块表

每个序列的逻辑 KV 分成固定大小块（如 16 token/块），按需映射到物理块——类比虚拟内存页表

📉

碎片几乎归零

内部碎片 < 一个块；没有外部碎片——省下的显存换成更大 batch，吞吐提升数倍

🔗

前缀共享 / 写时复制

相同前缀（system prompt）的序列共享物理块；需要分叉时才复制——Prefix Caching 的底层基础

🧷
面试金句

"PagedAttention 解决的是 KV Cache 显存的内外部碎片问题：外部碎片来自连续分配找不到大块空地，内部碎片来自按 max_len 预留却只用了一半。分页之后显存利用率从 ~40% 提到接近满载。"

Continuous Batching 与 Scheduler 抢占（同花顺真题）

Static batching 要等一整批里最长的序列跑完才能换下一批——GPU 大量空转。Continuous Batching 把调度粒度从"批"降到"迭代"。

而显存被挤爆时就要抢占。vLLM 0.7.x（本项目真机实测版本）中，调度器位于 vllm/core/scheduler/scheduler.py，两种抢占模式：

♻️
_preempt_by_recompute（重算式）

直接丢弃该请求的全部 KV Cache，释放显存；请求回到等待队首，之后重新 Prefill。代价是重复计算，但实现简单、不占额外内存。

💾
_preempt_by_swapped（换出式）

KV Cache 块搬到 CPU 内存，恢复时再搬回来。省重算但 PCIe 来回搬运慢，且 CPU 侧要有 swap 空间。

⚖️
抢谁？默认抢最新的

vLLM 默认抢占最近到达的请求（它重算成本最低）。这就是同花顺二面"抢占策略代码在哪"的标准答案骨架——答出文件路径 + 两个函数名 + 抢谁的原则。

🛡️
Harness 视角的边界（必背口径）

"我们能够修改自己的 vLLM fork，但源码权限不等于立即重写 Scheduler。第一阶段优先使用标准 API、usage 和 Metrics……只有基线数据证明存在收益时才进入 priority、KV Events、offload 或 Agent-aware scheduling。"——这是 ADR 0005 的原文口径，既证明你懂内部，又证明你有克制。

PD 分离与量化（百度 / 阿里真题）

PD 分离（Prefill-Decode Disaggregation）：把 Prefill 和 Decode 放到不同的 GPU 实例池，中间只传 KV Cache。为什么必须分？混布时 Prefill 的长计算会阻塞正在 Decode 的请求——首 token 延迟（TTFT）和后续 token 间隔（ITL）互相拖累。记法：XpYd（如 4p8d = 4 卡做 Prefill、8 卡做 Decode）。业界参照：Mooncake（Kimi 的 KVCache 中心化分离架构）、DistServe、Splitwise。

八股速答：每题 60 秒版 + 项目桥接

1️⃣
Function Calling vs RAG，什么时候用哪个？

实时数据/执行动作 → FC；私有知识/离线文档 → RAG；实际系统常组合。桥接："我的项目是 FC 的安全壳——工具调用全部过策略守卫、副作用分类和沙箱命令边界，这是生产级 FC 和 demo 级 FC 的差别。"

2️⃣
幻觉怎么产生？怎么减轻？

模型在预测下一个 token 不是检索事实，天然会编。五板斧：RAG 供事实 / FC 查真实数据 / Structured Output 收窄格式 / Prompt 明示"不知道就说" / 多轮自检或交叉验证。桥接："工程侧我再加两板斧：副作用 fail-closed（不确定就不动手）+ 全量审计可回放——幻觉最多导致答错，不会导致做错。"

3️⃣
Structured Output 怎么保证稳定？

Prompt 规定格式不稳定；JSON Schema 约束（主流 API 支持）把字段名、类型、必填卡死。桥接："下游要自动化解析所以格式即契约——我的 RunEvent payload 带 payloadVersion 字段，就是给事件 schema 的演进留的版本位。"

4️⃣
上下文腐化 / Lost in the Middle 是什么？

窗口塞满后早期内容被稀释、注意力大幅下降；中间位置的信息最容易被忽略。桥接："所以工程上不是拼命塞满窗口而是精准控制放什么——我的方案是把记忆压缩整个交给 Pi 会话层（appendCompaction 写进会话文件持久化），Harness 只管选会话和复用句柄。"

5️⃣
RAG 检索策略怎么设计？

混合检索（向量抓语义 + 关键词抓精确）用 RRF 融合；Chunk 512-1024 token 带 50-100 重叠；HyDE 先生成假设文档再检索；重排序提升精度。桥接："我的项目没做 RAG——诚实承认，但我知道难点三座山：文档预处理质量、召回质量、生成忠实度。"

6️⃣
SFT vs RLHF？微调 vs RAG？

改行为风格用 SFT 快速迭代；对齐偏好用 RLHF/DPO；知识频繁更新用 RAG（改库不改模）；能力本质缺失才微调。桥接："我把模型当可替换工作负载（ADR 0005），这些是模型侧手段——我的立身之本是控制面语义不随模型升级漂移。"

7️⃣
多 Agent 主子通信链路怎么设计？异常怎么处理？

主 Agent 拆解任务 → 子 Agent 独立上下文执行 → 结构化结果回传；异常要有超时/重试/降级和部分结果回收。桥接："我的项目单 Runtime 但机制同构：Attempt 隔离每次执行、Sandbox LOST 事件 → Attempt INTERRUPTED → agent_interrupted 事件 → 调度层重新排队，这就是'子任务失败的标准化收敛路径'。"

8️⃣
Agent 成本失控监控什么指标？

token 总量与增速、单任务成本分布、cache 命中率、工具调用的间接成本（失败重试放大器）、预算告警。桥接："我的 Eval 层直接产出这些：totalTokens/costTotal/cacheHitRate 从 MODEL_COMPLETED usage 聚合，零新增采集。"
