虚拟机是怎么被"造"出来的

这一页假设你没有任何操作系统和硬件基础。我们从"一台电脑是什么"讲起，然后一步一步看： 本项目在收到"请给我一台虚拟机"的请求后，具体做了哪些事情，每一步对应哪段代码。

一、先搞清楚：一台电脑到底由什么组成？

虚拟机的本质，是用软件伪造出一台电脑。要伪造，先得知道一台真电脑由哪些东西组成：

CPU（处理器）真正执行指令的芯片。它只会一件事：按顺序读指令、算数、读写内存。
内存（RAM）CPU 的"工作台"。程序和数据要先放到内存里，CPU 才能处理。断电即失。
硬盘（磁盘）长期保存文件的地方。里面存着操作系统、程序、你的文件。断电不丢。
其他设备网卡、键盘、屏幕、串口等，负责和外界交换信息。

任何一台电脑开机时，做的都是同一件事：CPU 从某个固定位置取第一条指令开始执行。这个位置通常放着"引导程序"，它把操作系统内核从硬盘读进内存，然后把控制权交给内核。

什么是"操作系统"和"内核"？

内核（kernel）：操作系统的心脏。它是一个大程序，负责管理 CPU（让多个程序轮流用）、内存（给每个程序分地盘）、硬盘和设备（替程序读写）。

init（1 号进程）：内核启动后第一个启动的用户程序，它是所有其他程序的"祖先"，负责按配置启动服务。

根文件系统（rootfs）：一个装着 /bin、/etc、/usr 等目录的磁盘镜像，就是操作系统"本体"的全部文件。

所以一台能用的系统 = 内核（会启动） + rootfs（有文件可用） + init 配置（知道要启动什么）。本项目 guest 镜像里这三样都准备好了。

什么是"虚拟机"？

真电脑
真实的 CPU、内存、硬盘，直接连着
=
虚拟机
一个进程假装拥有 CPU、内存、硬盘，
里面运行的系统以为自己是真的

关键问题是：这个"假装"怎么做到的？ 答案分三层：

① 硬件辅助（KVM）：现代 CPU 自带"虚拟化模式"。Linux 内核的 KVM 模块让宿主机上的一个进程进入这个模式，CPU 大部分指令直接在硬件上跑，效率接近真机。遇到"碰到真实硬件"的操作，CPU 会自动"停下来"，交给宿主机处理。
② 虚拟机监视器（VMM，本项目用 Firecracker）：一个普通的宿主进程，负责"伪造硬件"。它告诉 KVM："给我一块 256MB 的内存、2 个 CPU、一个串口、两块硬盘"，然后把客户机要碰的设备操作转译成宿主机上的文件读写。
③ 客户机（guest）：运行在里面的操作系统，它完全不知道自己是虚拟的，按照正常流程开机。
一句话：KVM 负责让 CPU 能"隔出一个假电脑"；Firecracker 负责"往这台假电脑上装假硬件"；guest 里的内核和系统像真电脑一样启动。

二、创建虚拟机 = 三件事

不论细节如何，造一台虚拟机都可以拆成三件事：

  1. 准备材料：内核文件、系统盘、工作区盘、一块私有的文件夹。
  2. 启动"管家进程"：把 Firecracker 跑起来，它此时还是个"空壳"，没有任何硬件。
  3. 通过配置，把假硬件插上去，然后按"开机"：用 HTTP 请求告诉 Firecracker "给我装什么"，最后发一个"开机"指令。

这里有个容易混淆的地方：Firecracker 不是虚拟机本身，它是"管家"。虚拟机是 Firecracker 通过 KVM 造出来的那台假电脑。管家进程死了，虚拟机也会跟着消失。

三、本项目的完整创建过程（逐步）

下面按真实执行顺序讲。每一步标注了谁在做： 宿主机代码 宿主机上的 TypeScript 程序； Firecracker/KVM 管家进程与硬件虚拟化； 虚拟机内部 guest 里的系统。

1

检查环境能不能造虚拟机 宿主机代码

第一件事是确认"造得出来"：

  • /dev/kvm 能不能读写。它是 KVM 的入口，没有它就没有硬件虚拟化，只能拒绝创建。
  • 内核文件和系统盘文件是否存在。缺一个就报错，不会造一台没有操作系统的"空机器"。
  • 如果开启了 jailer（见下文第 5 步），检查 jailer 和 firecracker 两个程序都在。

对应代码：firecracker-sandbox-driver.ts 的 create() 开头部分。

2

分配"身份证件"与私有文件夹 宿主机代码

每台虚拟机需要三样东西，都是宿主机上的程序分配的：

东西作用例子
私有文件夹放这台虚拟机的所有文件，权限设成只有自己能进<runtimeRoot>/<id>/，权限 0700
UID / GID（用户编号）让这台虚拟机的管家进程用一个专属、低权限的用户身份运行20000～29999 之间取一个没用过的
CID（通信地址）之后宿主机和虚拟机通过 vsock 对话，需要一个唯一的"房间号"从 3 开始递增，0～2 系统保留

对应代码：vm-run-directory.ts、vm-uid-allocator.ts、vm-cid-allocator.ts。

3

把材料放进私有目录 宿主机代码

把三样材料复制到这台虚拟机自己的目录里：

  • 内核文件（kernel.bin）：告诉 CPU 第一步该执行什么的操作系统核心。
  • 系统盘（rootfs.ext4）：Alpine Linux 的全部文件。
  • 工作区盘（workspace.ext4）：一块空白磁盘，Agent 的代码和产物都放在这里。

复制有两种方式，由配置决定：

  • 硬链接（内核文件默认如此）：只是给同一份文件多起一个名字，不真的复制内容，几乎零成本。前提是文件只读，所以它们被设成 0444。
  • 整份复制（系统盘默认如此）：每台虚拟机各复制一份，各自可写。系统盘也可以通过环境变量改成只读共享，但那样 guest 里除工作区外都是只读的，pip install 之类写临时文件的操作会失败，所以默认关闭。

工作区盘永远是每台虚拟机独占的，因为它要被写入。对应代码：copyFileReflink、shareBaseFile。

4

把文件的所有权交给这台虚拟机的专属用户 宿主机代码

执行 chown -R uid:gid。原因是：第 5 步启动的管家进程会以那个低权限用户身份运行，如果文件属于 root，它就读不到。

5

启动管家进程 Firecracker（经由 jailer 上锁） 宿主机代码 Firecracker

宿主机用 spawn 启动 jailer，jailer 再启动 Firecracker。jailer 做的事情：

  • 切换到第 4 步分配的低权限用户；
  • 把 Firecracker 关进一个只包含上面材料的文件夹（chroot），它看不到宿主机的其他文件；
  • 用 cgroup 限制它能用的 CPU 和内存。

Firecracker 启动后什么硬件都没有，它只打开一个 API 接口（一个本地 socket 文件 firecracker.socket），等待宿主机发配置。

宿主机同时把这个管家进程的进程号写进一个小文件（vm.pid），这是以后找回它的唯一凭证。

对应代码：firecracker-sandbox-driver.ts 的 jailer 分支，buildJailerCgroupArgs。

6

等管家进程就绪 宿主机代码

宿主机轮询 firecracker.socket，直到它出现，说明 Firecracker 已经在听了。这一步在真机上通常只要几十毫秒。

7

用 HTTP 请求"插上"假硬件 宿主机代码 Firecracker

宿主机通过上一步的 socket，像调用网页接口一样给 Firecracker 发配置。下面是本项目冷启动时的真实顺序：

顺序接口含义（用人话说）
1PUT /boot-source"开机时，内核文件用这个，启动参数是这些。"启动参数里写着 init=/sbin/init，告诉内核第一个程序是谁。
2PUT /drives/rootfs"插上第一块盘，它是系统盘（根设备）。"
3PUT /drives/workspace"再插上第二块盘，它是工作区，可读写。"在虚拟机里它会显示为 /dev/vdb。
4PUT /vsock"开一条和宿主机的专用通信线路，地址是第 2 步的 CID，socket 文件是 vsock.sock。"
5PUT /machine-config"给你 2 个 CPU、256/512MB 内存。"这些数值由策略决定。
6PUT /actions {InstanceStart}"开机！"
注意：没有网卡。这是产品边界，代码里根本不会插入网络设备。虚拟机只能通过 vsock 与宿主机说话。

对应代码：firecracker-sandbox-driver.ts 中 putSocket(...) 的调用序列。

8

虚拟机内部开机 虚拟机内部 KVM

KVM 让 CPU 进入虚拟化模式，从内核文件的入口开始执行。接下来发生的是任何一台 Linux 开机都会经历的流程：

  1. 内核初始化：识别 CPU、内存，找到两块盘（/dev/vda 系统盘、/dev/vdb 工作区盘）。
  2. 启动 init（1 号进程）：内核把控制权交给 /sbin/init。本项目用的是 Alpine 的 init，它读取 /etc/inittab。
    注：启动参数里没有 root=，源码中也没有说明内核如何选定根设备。这一点我没有验证，以真机能启动为准。
  3. 执行 inittab 里的命令（这是本项目专门写进去的，见下一步说明）。

内核启动日志默认是静默的（quiet loglevel=3），因为宿主机不消费它，打印出来只会浪费时间。

9

inittab 把工作区挂到 /workspace，并启动"接线员"和"执行员" 虚拟机内部

本项目的 /etc/inittab 大致是这样（由 scripts/microvm/build-guest-rootfs.sh 写入）：

::sysinit:/bin/mount -t proc proc /proc      # 挂上进程信息目录
::sysinit:/bin/mount -t sysfs sysfs /sys     # 挂上设备信息目录
::sysinit:/bin/mount -t ext4 -o noatime /dev/vdb /workspace   # 把工作区盘挂成 /workspace
::respawn:/agent/main                        # 静态 C agent 自己监听 vsock 5000，每连接 fork
  • 挂载：磁盘本身只是一堆字节，要"挂载"到一个目录，程序才能用路径访问它。挂到 /workspace 之后，Agent 的命令就能在那里读写文件。
  • agent 自己监听：guest/agent/agent.c 编译成静态 ELF（974,536 字节）后直接 respawn，它自己 socket(AF_VSOCK) + listen(5000)，每来一个连接 fork 一个子进程——不需要 socat，也不需要 96MB 的 Bun 运行时。
  • 为什么换掉 socat + Bun：真机 A/B（台账 O9/O10）——早期 socat VSOCK-LISTEN:5000,fork EXEC:/agent/main（Bun 编译产物 96MB）时 guest 用户态就绪约 1281ms，换成静态 C agent 后约 130ms；socat 自己从 execve 到 listen 只要 5.3ms，慢的是 96MB 二进制的加载与重定位。旧路径仍可用 HARNESS_GUEST_AGENT_IMPL=bun 构建。
  • respawn：如果 agent 退出了，init 会自动把它重新拉起来。
10

宿主机与虚拟机"握手"，通道正式打通 宿主机代码 虚拟机内部

宿主机此时才真正"确认虚拟机活着"：

  1. 连接 vsock.sock（这是 Firecracker 为 vsock 开的宿主侧入口）。
  2. 发送一行文本 CONNECT 5000，意思是"我要连 guest 的 5000 端口"。
  3. 收到 OK 5000：这一行由 Firecracker 的 vsock 设备（VMM）回，表示"通道已建立"，不是 guest 里的程序回的。
  4. 发一个 ping 帧，收到 pong，才证明 guest 里的 agent 正常回话。

冷启动时虚拟机要从内核一路起到底，所以宿主机会反复尝试：每 50ms 重试一次、单次握手 300ms 超时、总窗口 20 秒（O10 之后对端提前关闭会被立即当成失败；修之前要白等满 300ms + 100ms 间隔，把实际 ~70ms 就绪的 guest 量化成 ~400ms，这也是"冷启动 539ms"里最长的一段假延迟）。

快照热恢复时 guest 已经就绪，这段握手实测只要 ~5.5ms；恢复后执行一条 uname -r 的 median 是 11.6ms。

对应代码：firecracker-vsock-bridge.ts 的 connectWithRetry（默认 20000/150/1000，驱动冷启动路径用 20000/50/300）。

11

可选：给这台虚拟机"拍快照"，供以后快速复用 宿主机代码 Firecracker

冷启动一台虚拟机要 1.5 秒左右。如果每次都这么慢，体验会很差，所以项目做了"快照"：

  • 快照是什么：把一台已经开机、agent 已就绪的虚拟机，连同它的内存状态保存成两个文件（vm.snap 是设备状态，mem.snap 是整块内存）。像游戏存档：存档时的画面、进度原样保留。
  • 怎么拍：先 PATCH /vm {"state":"Paused"} 暂停虚拟机，再 PUT /snapshot/create 写文件，最后 Resumed 继续运行。
  • 怎么用：之后同一模板的虚拟机不再开机，而是 PUT /snapshot/load 直接把存档读回内存，然后继续运行。真机实测这一步只要 6～7 毫秒。
  • 代价：拍快照时虚拟机会被冻结，宿主机和它的 vsock 连接会断，需要重连。
  • 模板指纹：存档只对"同样的内核 + 同样的系统盘 + 同样版本的 agent"有效。任何一个变了，指纹就变，旧存档自动不用。

对应代码：vm-snapshot-manager.ts（指纹与存档路径）、firecracker-sandbox-driver.ts 的快照分支。

12

create 返回，虚拟机交付给上层 宿主机代码

到这里，create 才算完成。上层拿到的是一个"沙箱句柄"（sandbox handle），里面有 id、工作区路径、隔离声明等信息。之后 Agent 的每一次工具调用，都是拿这个句柄去执行命令。

四、创建完成后的状态：一张图看懂

宿主机（Linux）
│
├─ 运行目录 <runtimeRoot>/<id>/（权限 0700）
│     ├─ vm.pid            ← 管家进程的号码（以后找它用）
│     ├─ kernel.bin        ← 内核（只读）
│     ├─ rootfs.ext4       ← 系统盘（只读共享或独立副本）
│     ├─ workspace.ext4    ← 工作区盘（这台虚拟机独占，可写）
│     └─ vsock.sock        ← 与虚拟机通话的门
│
├─ 管家进程 jailer → firecracker  （低权限用户 uid=2xxxx，被关在 chroot 里，受 cgroup 限额）
│        │
│        │  KVM（CPU 的虚拟化模式）
│        ▼
└─ ┌──────────── 虚拟机（guest） ────────────┐
   │ 内核 → init → inittab                    │
   │   系统盘作为根文件系统（见下方说明）        │
   │   /dev/vdb 挂为 /workspace                │
   │   /agent/main 自监听 vsock 5000（静态 C）  │
   └──────────────────────────────────────────┘
到这一步，虚拟机"活着"，并且宿主机和它之间的通道已经打通。之后要执行命令，就是通过这条通道发消息、收结果，本文不再展开（见总览页的第 3 节）。

五、销毁时发生什么（简要）

虚拟机用完之后，顺序是固定的，而且是"先停、后拷、再删"：

  1. 停机：用 vm.pid 找到管家进程，发 SIGKILL 强制结束，并等它真正退出。这样虚拟机里不会再有人写盘。
  2. 导出：把工作区盘里的文件拷回宿主机的工作区目录。
  3. 删除：释放 UID、CID，删除 chroot 和私有目录。删除必须放在停机之后，否则管家进程就找不到了，会变成"吃内存的孤儿"。

六、常见疑问

Q：虚拟机里的 root 用户能不能逃出去？
A：虚拟机里的 root 只能控制它自己的内核和文件。跨出去需要攻破 CPU 的硬件隔离，这远比攻破普通进程难。即使这样，管家进程还有 jailer 再一层限制。

Q：为什么不直接用 Docker？
A：Docker 容器和宿主机共用一个内核，内核漏洞会波及所有容器。虚拟机有自己的内核，隔离更强。代价是启动更慢、更占资源，所以我们用快照来弥补。

Q：宿主机重启了，虚拟机会怎样？
A：管家进程会随宿主机进程一起消失，虚拟机也就没了。下次启动时，平台会根据运行目录里的 vm.pid 找到遗留的管家进程并清理掉。

Q：虚拟机里能上网吗？
A：不能。它没有网卡，这是设计决定。需要宿主能力时，只能走 vsock 通道。

Q：一台虚拟机能跑多个命令吗？
A：可以。开机和握手只做一次，之后每条命令都通过同一条通道发过去，互不共享环境变量，各自有独立的退出码。
