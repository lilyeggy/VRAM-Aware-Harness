二 · 一条 Run 的隔离之旅

租户 A 提交一个带 bash 工具的任务。从 HTTP 请求进来到容器被回收，它会穿过这 10 道闸门——每道闸门标注了它能拦下什么：

→01
认证
Bearer/x-api-key 缺失 → 401；scope 不足 → 403。失败鉴权记密钥摘要进审计。
→02
归属判定
tenantId = principal.tenantId（凭证派生）。客户端传什么都不算。
→03
会话/工作区校验
sessionId 被其他租户占用 → 409；工作区不属于本租户 → 与「不存在」不可区分的 404。
→04
资源准入
vLLM 观测 → 压力分级 → 全局/租户并发闸 → 预算闸。任何一闸不过 → QUEUE。
→05
排队调度
进本租户 FIFO 队列；轮转 claim + 老化插队；等待超 TTL → 有界失败，不死等。
→06
容器创建
runsc 容器 + OCI 硬限制；非 root；Secret 不进 argv/Env；创建后 inspect 验证 runtime 证据。
→07
工具裁决
每次工具调用过策略守卫（白名单/路径围栏/网络）；副作用前先落 PREPARED。
→08
模型调用
分权凭证走网关（仅 models:generate）；上下文预算裁剪；多后端路由 + 熔断。
→09
落库与产物
事件/结果带 tenant_id 入库；产物写入租户工作区目录；输出经 redact 再落库。
10
回收与审计
容器销毁（崩溃也有孤儿清理）；预算 settle；全程 ALLOW/DENY 留痕。
下面六节把这 10 步背后的六层机制逐个拆开。每节的固定结构：机制（怎么强制）→ 为什么这么设计（深色卡）→ 场景实证（绿边卡）。

三 · 新时代 AI OS：与操作系统、数据库对照

把六层机制放远一点看，这台东西的形状就是一台跑在单卡上的操作系统：OS 管理 CPU 给进程用，这里管理 GPU 给 agent 用。Karpathy 的 LLM OS 类比（LLM = CPU、context window = RAM、工具 = 外设）只画到了「硬件层」；缺的那一半——谁能用这个 CPU、能用多久、在隔离里怎么跑、坏了谁负责——正是内核职能，也正是本项目的全部内容。所以「AI OS」不是修辞：§4–§9 每层都配了核心代码与 OS/数据库对照，读完你应该能在两个知识体系之间自由翻译。

类比的边界：三个「不像 OS」的地方（面试里比相似点更加分）

1
GPU 是非抢占的——没有时间片
CPU 时间片毫秒级可抢占，OS 才能做时间片轮转；一个 run 占住推理槽就要跑到完成，调度粒度是「任务」不是「时间片」。所以只能排队 + 公平轮转，尾延迟结构性高于 OS——Q12 过载 p95 97s 的根源在这里，不是 bug。
2
显存没有「虚拟内存」
OS 用虚拟内存给每个进程「独占全部内存」的幻觉；显存给不了每个租户这个幻觉（A6000 连 MIG 都不支持）。隔离只能时间复用、不能空间分区——L1 整层重心全在排队/公平/准入上的原因。
3
价值排序与通用 OS 相反：fail-closed 优先
通用 OS 可用性优先；这里观测不到就全量排队、runtime 证据不符就销毁容器、无法证明隔离就禁 bash。因为 OS 调度错了顶多慢，agent 平台调度错了会把崩溃的副作用重放（R05 防的正是这个）——为一个实验室平台选「宁可不可用」，要能说出代价。
面试用法：先讲映射建立框架（30 秒），被追问时再讲失效点展示深度——顺序别反。只讲相似点会被当成背概念；先讲失效点又没有框架承接。

四 · L0 身份与租户归属

机制：租户身份是凭证的属性，不是请求的参数

整层建立在一个不可变对象上：RequestPrincipal{tenantId, scopes}（src/auth/request-principal.ts）。它只能由服务端在认证时构造——HTTP 层处理任何请求之前，先经过 requirePrincipal()（src/http/harness-http-api.ts:944）：

认证链
请求头 Bearer / x-api-key
→ API 凭证库按 SHA-256 摘要索引查找（库中从不存明文，api-credential-store.ts:57–64）
→ timingSafeEqual 恒时比较（68–88），防时序侧信道
→ 命中 → 构造 RequestPrincipal{tenantId, scopes}（tenantId 来自凭证记录，非请求体）
→ hasScope 校验；缺失 → 403；未认证 → 401 + 审计记录被试密钥摘要（绝不记明文）

四类凭证、四种生命周期：

凭证机制隔离意义
API key存摘要 + 绑定 tenant_id 与 scopes泄漏时可单独撤销，不伤其他租户
会话 token邮箱/密码登录签发 7 天 token，同样只存摘要；未知邮箱做 dummy scrypt 对齐时序，防用户枚举（106–111）登录并发 1/10/50 实测（G08）
Worker 分权 keyPi/Worker 调模型用独立 key，仅 models:generate scope（create-harness-application.ts:219–233）agent 能花的钱 ≠ 人工能动的权限；可独立撤销
bootstrap key人工管理通道，["*"] 全 scope与 agent 凭证物理分离

两个容易忽略的入口攻防

会话抢注（session squatting）：客户端可以自选 sessionId，如果归属判定在提交之后才做，B 租户就能抢注 A 的会话 ID。实现是提交时先查 resolveSessionOwner（按会话最早一条 Run 的租户判定归属，src/runs/runstore.ts:225），非归属租户直接 409「已被其他租户占用」；首次使用即认领。

资源枚举：访问不属于自己的 workspace，返回的 404 与「资源真的不存在」不可区分（src/http/harness-http-api.ts:555）——不给攻击者「这个 ID 存在但我没权限」的确认信号。跨租户 interrupt/resume 一律 DENY + 审计（519、684）。

OS / 数据库对照 · L0
机制操作系统里像什么数据库里像什么

为什么这么设计 · L0

为什么：多租户系统里最致命的漏洞是把「客户端声明的身份」当真。把 tenantId 做成凭证的派生属性，意味着不存在一个可以伪造的字段——攻击面从「所有输入」收窄到「凭证本身」。

如果反过来：让请求体带 tenantId（很多教程架构这么写），那么每一层都要重复校验「这个 tenantId 是不是你的」，漏一层就是横向越权；而且审计里再也分不清「谁声称的」和「谁证明的」。

代价：所有数据访问层 API 签名都多一个 principal 参数，内部工具调用不能图省事直接传 ID——测试里大量「跨租户 404/409」断言就是在守这个纪律。

五 · L1 调度、准入与配额

机制一：GPU 压力分级准入（观测 → 分类 → 判决 → 记账）

这是「资源隔离」的第一道闸。观测器解析 vLLM 的 Prometheus /metrics（src/resources/vllm-resource-observer.ts），分类器拿三个信号判级（src/resources/resource-classifier.ts:120）：显存增量比例、KV cache 占用、running/waiting 请求数。判决由准入服务落库（src/resources/resource-admission-service.ts:45），策略是确定性的（src/resources/execution-policy.ts:60）：

↓ 分类
NORMAL 空闲
→ 全局闸 maxActiveRuns
BUSY 有压力
→ 全局闸 + 每租户仅 1 个在跑（102–108）
CRITICAL / UNKNOWN 危急/观测失败
→ QUEUE（fail-closed）
↓ 还要过
预算闸（BudgetAware） ceiling − activeTenantRunCount ≥ 1 ?
不过 → QUEUE(TENANT_BUDGET_EXCEEDED)　budget-aware-policy.ts:111–151
↓
START　QUEUE（等待超 TTL → 有界失败 QUEUE_TIMEOUT，run-queue-coordinator.ts:128）
为什么准入只看「基线之上的增量」：vLLM 启动就预占约 90% 显存（gpuMemoryBaselinePercent，默认 90）。如果直接拿显存占用率判压，平台会被自己的推理服务永久判 CRITICAL、什么都进不去。所以分类器以 90% 为基线，只看基线之上的增量压力（resource-classifier.ts:60, 99–117）——这是真机上踩出来的参数，不是教科书参数。

机制二：每租户 FIFO + 轮转 + 老化插队（公平性核心）

调度器（src/scheduling/tenant-run-scheduler.ts）为每个租户维护独立 FIFO 队列，全局 claimNext() 在队列间轮转领取：全局并发硬闸 → 每租户并发闸 → 同一会话强制串行 → 租户预算闸。N10 修复引入老化插队：等待越久的租户在轮转中权重越高，给被洪泛租户挡住的租户一个确定的等待上界，而不是「理论上轮得到」。

机制三：预算账本（commit / settle 记账模型）

为什么这么设计 · L1

为什么排队而不是拒绝：单卡上 vLLM 无法硬分区（A6000 不支持 MIG），租户间的「隔离」只能建立在时间维度——排队本身就是隔离策略：它把「谁在什么时候独占推理」变成调度器的确定性决定，而不是先到先得的混战。

如果反过来：不做每租户队列，一个租户的洪泛请求会占满全局并发槽，其他租户 starvation（Q05 实测过：洪泛下 B 租户尾延迟最高 215s——这正是 N10 加老化插队的动机）；不做 TTL，调度器会被死等拖垮。

代价：① 隔离是「软」的——排队能保证公平与上界，不能保证时延；② 观测器挂了就全量 QUEUE（fail-closed 拿可用性换正确性）；③ 预算账本是内存实现，重启即清零（单机定位下的取舍）。

为什么 prepare/complete 拆两阶段：工具副作用（写文件、调外部 API）一旦发生就不可收回。「先落 PREPARED 再执行」让系统在崩溃恢复时永远能回答「副作用到底发没发生」——答不出来就拒绝自动重放。不安全重放比不重放危险得多：重复转账、重复删除。

十二 · 诚实边界（面试官会戳的）

下面每一条都建议主动讲——能说出边界和代价的隔离方案才可信。每条附了应对话术。

1
GPU 完全共享，隔离是软的
所有租户共享同一 vLLM 实例/同一张卡。租户隔离 = 并发 slot + 预算 + 轮转排队；显存不做任何分区（A6000 不支持 MIG）。noisy neighbor 不能被「挡住」只能被「排队」。
话术：「单卡无 MIG 是硬件约束；我用准入+排队把公平性做成确定性的——老化插队给出确定等待上界，Q12 实测了过载拐点。要硬分区得换 A100/H100 走 MIG 或上多实例，那是明确不做的大纲外。」
2
LLM 网关没有每租户限流 / token 配额
上下文预算全局一份；网关内无每租户 token 计量；租户间模型算力公平只靠 L1 并发排队间接实现。
话术：「已知最大缺口。修法是现成的——把 L1 的账本模型扩展出 token 粒度（账本接口本来就预留了 settledTotalUnits 做计费），在网关层加每租户令牌桶。没做是因为先让并发/预算排队顶住，网关限流排第二优先级。」
3
prefix cache 有意跨租户共享
前缀指纹与 vLLM APC 都不掺租户盐。安全性依赖「逐字节相同前缀才复用」的性质。
话术：「这是利用率取舍不是疏漏：相同前缀即相同内容，无泄漏面；分桶会同时伤命中率和全局吞吐。若要更保守，可以在指纹里掺租户盐，一行改动，代价是命中率。」
4
单机单进程单点
调度器、预算账本（内存实现）、网关路由状态全在进程内存；单 SQLite 文件；无 HA/多机——项目定位明确不做。
话术：「实验室单机平台的定位。状态机设计上所有关键状态先落 SQLite，所以进程重启可恢复（D1 场景验证过恢复链路）；但账本/路由是内存态，重启即重建。上多机要先把账本换成共享存储——知道怎么走，没走。」
5
网络隔离是全有/全无
容器 --network none 或 bridge，没有受控 egress proxy、没有域名级出口治理；restricted-egress 遇 allowNetwork 直接拒绝（fail-closed）。
话术：「方向正确但粒度粗。受控 egress 需要一个 per-run 的代理层（域名白名单 + 审计），是明确登记在边界外的下一块拼图。」
6
Secret 防护有残留面 + 两处残留卫生项
① 同机同用户可读 docker CLI 子进程 /proc/<pid>/environ（N13 修复后登记）；② Worker 容器绑定靠 agent-harness-${sandboxId} 命名约定（known-issues B9 仍标 OPEN）；③ deploy 示例沙箱还是 development+runc 档（C4 OPEN）。
话术：「残留面①在单用户实验机上威胁模型内可接受，上多用户宿主要换成 socket 注入。②③是登记在案的卫生项——我更愿意让台账里有两条 OPEN，而不是假装全绿。」
7
身份模型薄：tenant == user
注册即建租户，无组织/团队/RBAC 分层，scope 粒度粗（只有 * 与 models:generate 等），会话 token 7 天不轮换。
话术：「对『个人开发者跑 agent』的目标场景够用；组织化多级租户是纯 CRUD+鉴权工程，没有技术风险，所以排最后。」
8
fail-closed 以可用性换正确性
GPU 观测失败 → 全量 QUEUE；runtime 证据不符 → 容器销毁；沙箱无法证明隔离 → bash 全禁；策略相交导致「临时放权」繁琐。
话术：「这是贯穿全系统的价值排序：宁可不可用，不可静默降级隔离。代价是可用性依赖观测器健康——我把『观测失败』也算成一种资源状态，而不是异常吞掉。」

十三 · 面试问答速查

Q1 · 你的 GPU 隔离是硬的还是软的？

软的，而且是三层叠加的软隔离。

A6000 不支持 MIG，所有租户共享同一 vLLM 实例——显存层面没有分区。隔离建立在：① 容器 cgroup 的 CPU/内存/PID 硬限制（这是唯一的硬限制，但限的是容器不是 GPU）；② 每租户并发 slot + 预算上界（min(fairShare, maxUnits)，账本 commit/settle）；③ 租户间轮转 + 老化插队 + GPU 压力分级准入。真机验证：Q12 测出过载拐点在 1.2×–2.0×λ*，2.0× 时队列 48、p95 97.4s 但行为有界；8h 长稳 3505 次沙箱零残留。要硬分区需要 A100/H100 的 MIG，超出单机项目定位。

Q2 · 两个租户提交同一个 sessionId 会怎样？

409，先到先得，归属永续。

提交时先查 resolveSessionOwner——按该会话最早一条 Run 的租户判定归属；非归属租户提交同一 id 直接 409「已被其他租户占用」，首次使用即认领。这个防护（B6）是被 S01–S04 场景组钉住的 15 项跨租户断言之一。配套地，访问不属于自己的 workspace 返回与「不存在」不可区分的 404，防资源枚举。

Q3 · agent 在容器里能拿到别的租户或宿主的密钥吗？

三层防线 + 一个如实交代的残留面。

① 创建防线：容器创建时不携带任何 Secret——明文不进 docker run 的 argv、不写进 Config.Env，docker inspect 读不出任何东西；② 注入防线：Secret 只在工具执行期经 docker exec 的子进程环境注入（只传名字），输出落库前再过 redact；③ 沙箱防线：runsc + cap-drop ALL + 非 root + workspace 单目录 bind mount，S05 用跨租户/宿主哨兵文件实测读取全部被阻断。残留面：同机同用户能读 docker CLI 子进程的 /proc/environ——单用户实验机的威胁模型内可接受，如实登记。

Q4 · 容器逃逸怎么办？

纵深让「单点逃逸」不等于「全线失守」。

第一道：runsc 用户态内核——系统调用不进宿主内核，挡掉一大类 runc 逃逸；配置上还有 cap-drop ALL、no-new-privileges、read-only rootfs、非 root uid 65532。第二道：运行时证据验证——创建后 docker inspect 核对实际 Runtime，不符即销毁 fail-closed，防「配置说 runsc 实际跑 runc」的静默降级。第三道：就算容器被完全攻破，网络是 none、文件系统只读、数据在 SQLite 里且访问走凭证派生的 principal——拿不到下一层的钥匙。真机教训是 N12：runsc 对 --pids-limit 的支持是实测出来的（不加限制实测 900 个子进程，加 128 后约 40 处拦停），不能信文档。

Q5 · 一个租户疯狂提交，把别的租户饿死了怎么办？

这正是 Q05 场景 + N10 修复的故事，值得完整讲。

结构上：每租户独立 FIFO 队列，调度器轮转领取，全局与每租户各有并发硬闸。但实测发现光有轮转不够——洪泛租户把轮转机会全吃掉时，B 租户尾延迟最高到过 215s。N10 修复加了老化插队：等待越久的租户权重越高，给被挡租户一个确定的等待上界。另外队列等待超 TTL 会变成有界失败（QUEUE_TIMEOUT），孤儿 QUEUED Run 重启后重入队——调度器不会被死等拖垮。公平性代码也会写错：Q08 抓到预算层双计导致 ceiling=1 的租户永远起不来（N23），已修——所以这条链路有专门的状态机测试压着。

Q6 · prefix cache 跨租户共享，不怕串台？

不怕，因为 APC 的复用条件是「逐字节相同」。

vLLM Automatic Prefix Caching 只复用逐字节相同前缀的 KV block——两个租户前缀相同意味着内容本来就相同，不存在信息泄漏面。网关侧的 prefix 规范化（system 提前、tools 按名排序、键序稳定化）是为了提高命中率，指纹不掺租户盐是有意共享：单机上 KV cache 是最稀缺资源，省显存就是省并发容量。想更保守可以掺盐，一行改动，代价是命中率。

Q7 · 调度器挂了会怎样？隔离状态会乱吗？

进程级单点，但状态先落库，重启可恢复；隔离不变量靠 schema 和 fail-closed 兜底。

关键状态（Run/事件/准入判决/策略快照）先写 SQLite 再行动；重启后孤儿 QUEUED Run 重入队、PREPARED+UNKNOWN_EFFECT 的工具恢复时禁自动重放、迟到事件不覆盖终态（R12）。跨租户隔离在恢复路径上同样成立——「恢复」不是特权通道，恢复动作也走 principal。调度器/账本/路由的内存态会重建，这是单机定位的明确取舍。

Q8 · 凭证泄漏了怎么办？

四类凭证独立生命周期，可单独撤销。

API key、人工会话 token、Worker 分权 key（仅 models:generate）、bootstrap key 相互独立；支持单会话与全会话撤销（X12 验证：登录风暴后撤销，被撤 token 立即失效）。库中只存 SHA-256 摘要 + timingSafeEqual 恒时比较；鉴权失败审计记摘要不记明文。Worker key 泄漏的爆炸半径被 scope 压到「只能调模型」——动不了数据、动不了策略、动不了其他租户。
