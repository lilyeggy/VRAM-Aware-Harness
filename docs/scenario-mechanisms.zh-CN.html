场景 0 · 启动顺序不变量

测的不是"服务能起来"，而是一条不变量：在恢复扫描与队列 Pump 就绪之前，监听端口绝不能存在。它看着像基础设施，实际上决定了后面所有场景的可解释性——如果端口早开，任何在此窗口内到达的请求都会走进一个必然报错的分支，而这种错误看起来像是"鉴权失败"或"参数错误"，会污染场景 1 的归位结论。

可观测的证据：GET /health → 200 {"ok":true,"started":true}。这里的 started 字段就是 application.isStarted() 的直读（harness-http-api.ts:225）——它能返回 200，本身就说明第 3、4 步已经完成。反过来说，只要这个端口有响应，这条不变量就已经被满足。
为什么 start() 与 stop() 都要 single-flight。startPromise 与 stopPromise 两个字段让重复调用返回同一个 Promise（harness-application.ts:86-126）。更关键的是 stop() 开头会 await this.startPromise：如果启动途中被要求停止，它会等启动跑完再关闭，而不是留下一个 started=true 的孤儿应用。若没有这一句，"启动到一半 + 收到 SIGTERM" 就会产生一个既没恢复完、又认为自己活着、且已经开放端口的进程。
关闭失败不静默。stop() 用 Promise.allSettled 中断 listActiveRuns() 的全部活跃 Run，只要有任何一个 rejected 就抛 安全关闭时有 N 个 Run 无法中断。此时 create-harness-application.close() 的后续步骤（healthMonitor / metrics / sandboxProvider / database）都不会被执行，closed 保持 false —— 宁可留着资源并报错，也不假装关干净了。

recover() 内部：唯一会"杀东西"的一步

三步的顺序是设计，不是巧合。RecoveryStartupCoordinator.recover() 注释写明：必须先停止旧进程可能遗留的执行环境，再允许恢复任务重新入队；先恢复旧的 QUEUED Run，随后扫描产生的新任务由 RecoveryExecutor 直接加入同一个 Scheduler，不会重复恢复。
"不 drain" 是恢复不享有特权的实现方式。类注释：这里不直接 drain，HarnessApplication 会在 recover 完成后启动 QueuePump，由 Pump 使用与普通提交相同的资源准入和调度路径推进恢复任务。所以场景 D1 看到的是 RUN_INTERRUPTED → RUN_QUEUED → QUEUE_BLOCKED ×2 → RUN_RESUMED，而不是直接 RUN_STARTED。恢复任务也要重新过准入、也要排队。
这条 fail-closed 取舍值得单独记住。只要有一个遗留沙箱清理不掉，整个进程就拒绝启动。代价是"一次清理故障 = 服务不可用"，收益是"绝不会出现两个执行环境写同一份 workspace"。在一个把"沙箱隔离"当作核心卖点的系统里，这个方向的取舍是对的——但它意味着 cleanupStale() 的健壮性直接决定了可用性。

场景 1 · 失败归位与租户隔离

测的不是"能不能拒绝非法请求"，而是每一次拒绝是否由正确的那一层做出、返回正确的状态码、并留下可归因的审计。这个区别很重要：如果 401 是被路由层顺手拦下的，那么"鉴权正常"这句话就永远无法被证伪。七个用例全部命中，且没有一个是"别的层顺手拦下的"。

两处顺序事实（这才是"归位"的实质）
① 400 在 401 之前：JSON 解析先于凭证校验。反过来的话，未认证调用者永远拿不到 400，客户端无法区分"请求体写坏了"和"密钥不对"。
② 413 在 workspace 解析之后：脚本里有一条自注释——"输入上界在 workspace 解析之后检查，所以这里必须带一个真实存在的 workspaceId 才能命中 413"。副作用是：一个 413 必然意味着调用者已通过鉴权、且在自己租户内指向了一个真实 workspace，所以 413 不能被用来探测别的租户。
两个 404 是两个不同的层。找不到 HTTP 路由 由路由表抛出，找不到 AgentRun 由资源层抛出。同一个状态码、不同来源——这正是"失败归位"要证明的东西。而两处资源级 404 都是刻意的防枚举：workspace 跨租户与"根本不存在"返回完全相同的响应；Run 跨租户同理，区别只在 interrupt 路径会额外落一条 run_not_owned 的 DENY 审计。响应上不可区分，追溯上留痕。

场景 2 + 3 · 共用的资源准入决策树

场景 2 和场景 3 跑的是同一段代码，只是输入不同。这个场景对存在的意义就是把这一点钉死：场景 2 证明「资源空闲时提交即可跑」，场景 3 证明「资源紧张时同一个提交会被挡下并给出可查的原因」。两者共享两段门：

四路信号是「或」关系，不是加权。任一 _CRITICAL 直接判 CRITICAL —— 所以 runningRequests ≥ 8 单独一项就能把判决拉到 CRITICAL，哪怕 GPU 显存还很空。这是保守取向：任一维度饱和即视为整体饱和。反过来，只要还能拿到一路有效信号，就不会退化成 UNKNOWN。
UNKNOWN 有两条来源，而且可区分。分类器四路全空 → RESOURCE_UNKNOWN + INSUFFICIENT_DATA；观测本身失败 → RESOURCE_OBSERVATION_FAILED，且 resourceSnapshotId = null。两条都判 QUEUE，但原因码与证据完全不同。后者是全系统唯一允许 snapshotId 为 null 的决策，PolicyDecisionStore.assertEvidenceMatchesDecision() 会在运行时拦住任何「观测失败却带快照」或「观测成功却没有快照」的组合，数据库层还有一条等价的 CHECK 约束做第二道防线。

两次决策都留在库里，而且各自引用不同的快照。GET /runs/:id/decisions 返回的是两条记录而不是最后一条覆盖——它们回答的是两个不同的问题：「当时为什么不让它跑」和「后来为什么让它跑了」。如果只有最终状态，这个 Run 的排队原因就永远无法被独立复核。
关于「自动续跑」的精度，我要更正自己上次的说法。上次我说「观测器切回 20% 后 550ms 内自动 START」，这句话给了错误的印象，好像系统在响应资源变化。实际不是：RunQueuePump.start() 只做两件事——立刻 tick 一次，然后每 intervalMs 设一个定时器；它不订阅任何资源事件。观测器被切换后，系统是在下一个固定周期才发现资源已经回落。所以正确的表述是：无需任何人工干预，然后延迟上界 = 1 个 pump 周期（1000ms），本次实测落在 555ms。这是一个轮询系统，不是事件驱动系统——把它说成"响应式"是拔高了。
enqueuedAt 的保留是防饥饿的关键，不是细节。被拒后重新入队时写的是 enqueuedAt: queuedRun.enqueuedAt（run-queue-coordinator.ts:361），而不是当前时间。如果每次准入重排都刷新这个时间戳，那么一个反复被排队、反复被拒的 Run 的等待时长会被无限重置，enforceQueueTtl() 永远等不到它超过 queueTtlMs（默认 300000ms），它就永久饥饿。重启恢复路径同理：restoreQueuedRun() 取的是 DB 的 run.updatedAt，注释写明「排队时间取 DB updatedAt，重启不重置 TTL 时钟，等待时间跨重启累计」。
release 与 enqueue 的顺序是被代码强制约束的。attemptNext() 里注释原文：「顺序一定要是先release再 run，否则enqueue会认为 run 仍在执行并拒绝入队」。原因是 TenantRunScheduler.enqueue() 第一件事就是检查 this.activeTenantByRunId.has(input.runId)，命中即抛「Run 正在执行中」。这是把「不变量」写成运行时会抛错的断言，而不是靠调用方自觉。

QUEUE_BLOCKED 的两条折叠规则（synchronizeQueueBlockers()）：
① 跳过 AWAITING_SCHEDULING —— 「在队列里」这个事实已经由 RUN_CREATED/RUN_QUEUED 表达，只有具体阻断原因才值得单独成事件；
② 相同连续原因折叠 —— pump 会反复 drain，如果每次都写，「原因没变」也会产生海量重复事件；但原因一旦变化就写新事件，因为那是新的因果事实（这正是场景 3 与 D1 里能看到原因演变的原因）。
另外 listQueueBlockers() 会让调度器容量原因覆盖已存的资源原因：GLOBAL_CONCURRENCY_LIMIT > TENANT_CONCURRENCY_LIMIT > SESSION_SERIALIZATION 优先，代码注释的理由是「容量才是此刻不能领取该 Run 的直接原因」。

① 本机没有真实 GPU。这两次决策里的观测源是注入的假观测器（snap-normal-1 / snap-critical-1 / snap-normal-2 都由它产生），唯一的真实替换点就是「GPU 多忙」这一个数字。所以这两个场景证明的是决策链在给定观测下的正确性，不是 classifyResource 面对真实 vLLM /metrics 的准确性。要覆盖后者只能跑 e2e-gpu-pressure（需真实 vLLM）。
② 轮询而非事件驱动，延迟上界是一个 pump 周期。资源回落与续跑之间必然存在 0–1000ms 的空窗，这段时间 GPU 是空闲的。
③ CRITICAL 是硬拦：GPU ≥ 90% 时连一个 Run 都不放行，没有「降级小任务」这类中间档。这是明确的保守选择，代价是利用率，收益是避免把已经打满的卡再压上去。

场景 5 · 双租户公平轮转

场景 3 证明了「排队」，场景 5 证明「排队时不会有人被饿死」。两者用的是同一个调度器，但关注点完全不同：场景 3 看的是一个 Run 的命运，场景 5 看的是多个 Run 之间的相对顺序。

公平性不是靠限流，是靠一个轮转指针。claimNext() 里没有任何按租户加权的公平调度——它只有一句：取走一个 Run 之后，如果该租户队列还非空，就把这个租户 push 回 tenantOrder 队尾；空了就从 queuesByTenant 与 tenantOrder 中删除。所以一个租户即使排 100 个任务，每轮也只能拿到一个名额。
position 是投影，不是权威顺序。position / tenantPosition 由 listQueue() 在队列副本上跑另一遍同样的轮转规则算出；claimNext() 则在真实结构上跑，并且额外应用单租户上限与会话串行。两者可以分歧——被租户上限挡下的 Run 仍留在队列里占着 position，而 claimNext() 会跳到下一个租户。所以 QueueBlocker 的注释说它是 "diagnostic evidence, not a new scheduler decision"。

恢复决策：fail closed 的两道把关

「计划说自己能自动恢复」不算数。RecoveryExecutor.execute() 在真正推进之前，会按当前的 preparedExecutions 重算一次 decideRecovery()。如果重算结果是 MANUAL_REVIEW，即便 plan.decision 声称 AUTO_RESUME 也坚决拒绝。代码注释给了理由：计划可能来自旧的扫描快照，或被上层改写。这是把「信任边界」放在了执行点上而不是计划生成点上。
为什么 IDEMPOTENT_WRITE 也被拒绝。tool-execution.ts:47-50 注释原文：「写入被声明为幂等」本身不足以证明外部系统会使用稳定幂等键。在 ToolExecution 持久化并校验真实幂等证据前保持 fail closed。 也就是说，「工具自己说自己幂等」不被采信——需要外部系统侧的真实幂等证据。这是一个刻意偏保守、且把缺口写进注释而不是藏起来的决定。

本轮新发现 · QUEUE_BLOCKED 折叠规则在并发领取下失效

这个发现来自对 D1 事件线的一个疑问：为什么 tenant A 有两条完全相同的 QUEUE_BLOCKED，而 tenant B 只有一条？我把 D1 的种子与两阶段启动复现出来并打了插桩（tmp/day7-inspect.ts），拿到完整 payload。

=== CRITICAL 下连续 5 次 tick，观察 QUEUE_BLOCKED 计数 ===
  起点：A=2 B=1
  tick #1：A=3 B=1
  tick #2：A=4 B=1
  tick #3：A=5 B=1
  tick #4：A=6 B=1
  tick #5：A=7 B=1
结论：这不是竞态，是确定性行为 —— A 每 tick 稳定 +1，B 恒为 1。两次独立运行结果完全一致。

两条事件的内容

0005 QUEUE_BLOCKED {"reasonCode":"RESOURCE_CRITICAL","position":2,"tenantPosition":1,
                    "activeRunCount":0,"activeTenantRunCount":0}
0006 QUEUE_BLOCKED {"reasonCode":"RESOURCE_CRITICAL","position":2,"tenantPosition":1,
                    "activeRunCount":0,"activeTenantRunCount":0}    ← 与上一条逐字节相同

payload 完全相同：没有新的原因码、没有变化的计数、没有新信息。所以它不是「一条新的因果事实」，而是同一句话重复写。

机制

synchronizeQueueBlockers() 用一张内存表 lastQueueBlockerByRunId 做折叠，规则是「与上次相同的原因码就跳过」。但它还有一段删除逻辑：

for (const runId of this.lastQueueBlockerByRunId.keys()) {
    if (!queuedRunIds.has(runId)) {
        this.lastQueueBlockerByRunId.delete(runId);   // 「不在当前队列里」= 「不再排队」
    }
}

问题在于：claimNext() 会把 Run 从队列里摘走，直到 release() + enqueue() 才放回去。在这段窗口里，该 Run 的「不在队列里」并不代表它不再排队——它只是正在被评估。drainOnce() 又会用 Promise.allSettled 并发发起 N 个 attemptNext()，所以 A 的 synchronize 调用完全可能落在 B 被摘走的窗口里，反之亦然。被误删的一方，下一轮就会把同一条原因重新写一遍。

本次实测里受害的是 A，因为 A 在队列中是 position 2，被 claimNext() 取得更晚、admission.evaluate() 也返回更晚，于是它的表项总是先被 B 的那次 synchronize 删掉。这解释了为什么它是确定性的。

为什么现有测试没拦住

测试它覆盖了什么 / 漏了什么
tests/scheduling/run-queue-coordinator.test.ts:1421-1426明确断言折叠：「A subsequent Pump tick sees the same blocker but must not flood the immutable event log with an identical explanation.」 但它调用的是串行 attemptNext()，且前一步已返回 EMPTY —— 被阻断的 Run 从未被 claimNext() 摘走，表项因而从未被误删。这条路径恰好绕过了缺陷。

影响面，按实测数据推算。生产默认 pumpIntervalMs = 1000，所以每个「被反复拒绝且需要重新入队」的 Run 会以 1 条/秒的速率写 QUEUE_BLOCKED。缓解因素是 queueTtlMs 默认 300000ms：Run 最多在队列里待 5 分钟就被 FAILED(QUEUE_TIMEOUT) 熔断，所以单个 Run 的上界约 300 条。但如果把 queueTtlMs 调大、或设为 undefined 关闭 TTL（enforceQueueTtl() 会直接 return），而队列因资源长期 CRITICAL 而无法推进，事件写入就是无界的。run_events 是不可变事件日志，只会增长。
建议的修法（我没有改代码，先报给你判断）。把「不在队列里」与「已不再排队」区分开：删除判据不应只看当前队列快照，而应显式检查调度器是否仍持有该 Run——例如提供 isTracked(runId)（队列中 或 已领取活跃），仅当它既不在队列也不是活跃时才删除表项。或者更简单：把折叠从「比较上一次原因」改成「比较上一次写入到事件日志的原因」，并让删除逻辑只在 Run 真正进入终态或离开调度器时才触发。

9 这个数字是算出来的，不是看到的。queuePump.drain() 在飞行中会把同一个 drainPromise 返回给每个调用者（drainRequested = true 但不新建循环）。当它最终 reject，每个等待者的 tick() 都会在 catch 里调一次 onError。本次窗口里正好有 9 个等待者：4011 ÷ 500 ≈ 8 个周期 tick，加上 submitRun() 末尾那次主动 tick。所以「9 次」是可复算的，而非随机值——这也解释了为什么 F1/F2 只有 1 次：它们的失败几乎是瞬时的，只有一个 tick 在等。

// src/runtime/supervised-agent-runtime.ts:102-105
private async interruptWithinGrace(runId: string): Promise<void> {
    const interrupt = this.inner.interrupt(runId);
    if (!(await settlesWithin(interrupt, this.config.interruptGraceMs)))
        void interrupt.catch(() => undefined);
}

// src/runtime/supervised-agent-runtime.ts:129-137
async function settlesWithin(promise: Promise<unknown>, ms: number): Promise<boolean> {
    const timeout = deferredTimeout(ms);
    try {
        return await Promise.race([
            promise.then(() => true, () => true),   // ← 成功与失败都返回 true
            timeout.promise.then(() => false),
        ]);
    } finally { timeout.cancel(); }
}

settlesWithin 回答的是「有没有结束」，而不是「有没有成功」——两个 handler 都返回 true。调用方却把它当成了后者：注释的意图应是「若宽限内没结束，至少挂一个 catch 避免 unhandled rejection」，但因为 rejection 也算 settled，!(true) 为假，那条 catch 永远不会被执行。

建议的修法（我没改代码）。让 settlesWithin 区分 fulfilled 与 rejected——例如返回 "fulfilled" | "rejected" | "timeout" 三态，或者新增一个 interruptAndReport(runId): Promise<unknown> 把结果交回调用方。最小改动是让 interruptWithinGrace 无条件挂 catch 并把失败记入一个可被 stop() 读取的失败集合，否则 stop() 里那条 安全关闭时有 N 个 Run 无法中断 的检查就永远等不到它要等的东西。
F-5 的说明与边界。上面那个 Cannot use a closed database 出现在我的探针里（因为我注入了数据库句柄、由我自己在最后关闭它）。但它在生产形态下同样成立：ownsDatabase=true 时 close() 会关掉 SQLite，而 stop() 并不等待 in-flight 的 attemptNext() 结束（RunQueuePump.stop() 的注释明确写着「不会强制中断当前已经开始的 drain」）。所以只要有一个 attempt 在 close() 之后才走到写库那一步，它就会撞上关闭的数据库。它至少不是静默的——这条错误会被 pump 的 onError 报出来（实测输出里就有 RunQueuePump 推进失败 这一行）。
一条贯穿性的观察。把这一轮的发现和前面的放在一起看，会发现一个共同的形状：系统里存在若干「名字听起来在防守、但在它所指的那种情况下恰好失效」的代码——settlesWithin（把失败当成功）、synchronizeQueueBlockers 的删除判据（把"被摘走"当"不再排队"）、RUN_FAILED 分支（把"已收尾"当"已发终态"）。三者都是同一类问题：用一个更弱的条件近似了一个更强的条件，而近似恰好在关键路径上不成立。这类问题不会让测试变红，因为测试覆盖的是近似成立的那条路径。
