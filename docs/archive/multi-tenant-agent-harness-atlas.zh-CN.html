01 · four independent axes

“很多用户”不是一个技术结论

多用户、多租户、多任务和多 Agent 是四个正交维度。面试中先拆开它们，后续架构讨论才不会混乱。

Account dimension

多用户

产品有多个账号。只说明登录规模，不自动说明数据隔离、资源公平或任务并发。

userCount > 1
Isolation dimension

多租户

用户或组织拥有独立的数据、权限、配额、Secret、策略与审计边界。

tenantId → policy / quota / data
Concurrency dimension

多任务

一个或多个用户可以同时提交很多 Run；平台必须排队、限流、放置和取消。

many AgentRun instances
Orchestration dimension

多 Agent

单个任务内部存在 Lead、Subagent 或专家团队；它解决分工，不等于多租户。

one run → N agent workers

06 · our learning blueprint

映射到我们的 Harness：每层该学谁

这是实现顺序的架构地图，不替代一周 MVP 手册。绿色是已有基础，黄色是当前纵向切片接下来要补的责任。

foundation ready

Runtime Adapter

借鉴 AgentCore 的“宿主不绑定 Agent 框架”边界：AgentRuntime 接口隔离 Pi，Fake Runtime 证明合同。

foundation ready

Pi AgentSession

单次 Agent 的 loop、上下文和工具协议由 Pi 管理；Harness 不重新实现模型—工具循环。

build next

AgentRun State Machine

借鉴云端平台的 Run / Session 分离：Run 是业务生命周期，Pi Session 是 Runtime 内部上下文。

build next

Durable Event Store

借鉴 OpenHands 的事件流与 Codex 的可验证过程：事实先落盘，再由状态机投影当前状态。

build next

Checkpoint + Recovery

借鉴 AgentCore 的“计算可销毁、状态另持久化”：不能把 worker 内存误当作恢复能力。

later slice

Tenant Context

Tenant → User → Run → RuntimeSession 显式映射；策略、Secret、配额和数据查询全部带 tenantId。

later slice

Fair Queue + Lease

借鉴托管平台的并发边界：per-tenant 限额、全局并发、租约和幂等消费必须分开建模。

later slice

Resource Observer

读取 GPU 使用率、显存、队列与趋势，为 Admission 提供事实；不直接修改 vLLM 的 KV 管理。

later slice

Tool Isolation + Audit

借鉴 Codex、Copilot 和 microVM 平台：工具权限、执行隔离、审计事件是三种不同责任。

08 · interview checklist

设计多租户 Harness 时，必须回答的八个问题

如果这些问题答不清楚，系统往往只是“能跑多个 Agent”，还不能称为可靠的多租户执行平台。

身份怎样传递？tenantId、userId、runId、runtimeSessionId 谁生成、谁校验，能否跨租户伪造？
配额在哪一层执行？并发 Run、排队数、Token、GPU 时间、工具调用分别由谁限流？
隔离边界是什么？只做数据库逻辑隔离，还是进程、容器、microVM、网络和 Secret 也隔离？
Worker 消失后还剩什么？哪些状态在内存，哪些事件已落盘，恢复会不会重复执行有副作用的工具？
如何防止重复执行？Task 幂等键、Run lease、工具幂等键和事件唯一约束是否分别存在？
公平性怎样证明？大 Tenant 是否会饿死小 Tenant？优先级是否能绕过全局硬约束？
审计记录到什么粒度？命令、模型请求、工具参数、审批人、策略版本和资源快照能否串成时间线？
Agent 和模型资源谁负责？Harness 决定何时提交；推理服务决定 token、batch、KV 和 GPU 物理分配。
