From systems thinking to code primitives

先理解系统，再理解 Agent Harness

Agent Harness 不是某个固定类、SDK 或目录结构。它是一组工程能力的组合：把一个开放式、概率性的 Agent 能力，变成能被产品长期使用、被团队维护、被组织治理的系统。

本页的出发点 先抛开任何具体项目与具体框架，从“软件系统为什么需要边界、状态、控制和反馈”开始，再逐层缩放到底层代码机制。
不绑定框架 不假设唯一架构 宏观 → 中观 → 微观 问题 → 保证 → 机制
① 产品与组织 最外层先问：谁在使用？业务承诺是什么？错误会伤害谁？成本由谁承担？

01 / ENGINEERING BEFORE HARNESS

软件工程的本质：把能力变成可依赖的承诺

“模型能完成任务”只证明了能力存在；“系统能在真实用户、并发、失败和副作用下持续完成任务”才是工程。

◇
能力 Capability 它在理想条件下能做什么？例如理解意图、规划步骤、选择工具、生成代码。这通常是 Demo 最先证明的东西。
⬡
约束 Constraints 它绝不能做什么？谁可以做？一次能花多少钱？工具是否需要批准？约束定义了安全边界。
↻
保证 Guarantees 失败后是否能重试？请求是否会重复扣款？任务是否最终结束？保证是系统对外做出的可检验承诺。
◎
反馈 Feedback 我们如何知道系统正在变好还是变坏？日志、指标、轨迹、评估、告警让系统行为重新进入决策。
概率性的智能核心 输出不是传统函数那样完全确定；同一输入可能产生不同计划、不同工具选择和不同成本。
＋
真实世界的不可靠性 网络会超时，进程会崩溃，工具有副作用，用户会并发，外部数据会变化。
→
需要一层可控的工程外壳 给智能核心建立身份、生命周期、边界、持久状态、资源控制、故障处理和反馈闭环。这组能力常被称为 Harness。

PLANE 01

产品与领域平面

这里定义“为什么做”和“什么算成功”。工程设计必须从业务承诺倒推，而不是从某个类名正推。

它拥有任务语义、用户交互、审批体验、领域规则、成功标准。
它向下提出的契约任务必须可追踪；高风险动作必须等待人类；结果需要在某个 SLO 内返回。
缺失时的症状技术组件很多，但没人能说清系统究竟保证什么、错误由谁承担。
设计时要问用户提交的是一次聊天、一个长期任务，还是一项带副作用的业务流程？
关键认知：有人把 Runtime 也叫 Harness，有人只把控制与持久化层叫 Harness，还有人把整个平台都叫 Agent Harness。面试时先说明你采用的边界，再讨论组件。

INTERACTION LIFECYCLE

Session 不是一次执行

Session 表达一段持续关系或上下文边界。它可能包含多个任务、多次 Run，甚至跨越多个进程。

它回答“这些交互是否属于同一段关系，需要共享哪些历史？”
它不回答某一次工作现在是否运行、失败或排队。
典型包含关系一个 Session → 多个 Run；一个 Run → 多个 Turn；一个 Turn → 零或多个 Tool Call。
Session 可以活几小时，Worker 可能只活几分钟。可靠系统不能把业务生命周期绑死在进程生命周期上。

05 / RELIABILITY MECHANISMS

可靠 Harness 的核心不是组件数量，而是系统保证

每个机制都应该从一个故障问题倒推：可能坏在哪里？必须保持什么不变量？靠什么机制守住？

FOUNDATION 01

身份与工作单元

系统首先要能回答：“这是谁的哪一项工作？这次尝试和上次尝试是否相同？”没有稳定身份，后续的状态、重试、审计都无从挂载。

故障模型请求重发、客户端断线、Worker 重启后，系统无法判断看到的是新任务还是旧任务。
常见机制Tenant ID、Session ID、Task ID、Run ID、Attempt ID、Tool Call ID、Correlation ID。
重要取舍业务任务与执行尝试要不要分开？如果 Run 重试，是同一个 Run 还是新的 Attempt？
验证方式让请求断线重发，再检查是否能准确关联到原任务且不会重复创建。
它要守住的保证每个重要事实都有稳定归属，跨进程仍可关联。

07 / END-TO-END JOURNEY

一项真实工作如何穿过整个 Agent 系统

例子不依赖任何框架：用户要求“检查订单并退款”。点击 1–9，观察控制流、事实记录和副作用边界如何协作。

1. 接收意图用户、API、定时器或其他 Agent 发起
2. Admission身份、权限、配额、风险检查

4. 排队与分配选择何时、在哪里执行
5. Agent 推理读取上下文、规划、选择工具

7. 执行副作用调用订单与支付系统

08 / ARCHITECTURAL SHAPES

Agent Harness 领域没有唯一架构，只有不同规模下的形态

选择架构不是“越分布式越高级”，而是根据任务时长、故障成本、并发规模、副作用风险和团队能力做权衡。

SHAPE 01

嵌入式 Harness Library

Harness 作为应用中的库，直接调用模型和工具。部署简单，边界也最少，适合先验证真实需求。

事实来源通常是应用数据库与进程内状态。
故障边界应用崩溃会同时终止 Agent 执行；长任务恢复能力有限。
演进信号任务越来越长、多个应用要共享、失败需要恢复时，考虑拆成服务或工作流。
低运维复杂度
低持久执行能力
小典型组织规模

LOOP-FIRST / EMBEDDED

OpenAI Agents SDK

以少量原语组织 Agent、工具、guardrail、handoff 和 Runner。它刻意让普通语言代码继续拥有编排控制，而不是要求先把一切声明成图。

控制流拥有者Runner 管理单次 Agent loop；跨 Run、分支和更高层流程主要由应用代码组织。
状态真相来源Session 保存跨 Run 的对话历史；Trace 保存运行观测。二者不是同一类状态。
恢复与持久性SDK 提供多种 Session 后端；跨进程的长时持久执行由 Temporal、Dapr、Restate 等集成补足。
最值得借鉴保持核心抽象少；把“manager 调 specialist”和“handoff 后 specialist 接管”明确区分。
工程解读（不是官方原话）适合把 Agent 当作应用内能力；如果任务必须跨进程、跨小时可靠恢复，不应误把会话记忆当成持久工作流。

10 / HOW ENGINEERS THINK

搭系统时，不从类名开始；从承诺和故障开始

这是一套可迁移到任何 Harness 项目的工程推理顺序。每一步都有明确产物，能防止“先写了一堆类，却不知道为什么存在”。

01 定义业务承诺 谁发起什么工作？成功是什么？最长等多久？哪些错误可接受？哪些动作必须人工确认？ 产物：Use cases + SLO + 风险边界
02 定义工作单元与身份 区分 Tenant、Session、Task、Run、Attempt、Turn、Tool Call。明确它们的归属和生命周期。 产物：领域模型 + ID 关系图
03 列出故障模型与不变量 进程崩溃、网络超时、重复消息、越权、工具部分成功时，哪些事实必须仍然成立？ 产物：Failure matrix + Invariants
04 选择最小机制 状态机、幂等键、队列、事件日志、Checkpoint、租约、审批、沙箱分别对应哪个故障？ 产物：组件边界 + 契约 + ADR
05 用故障验证保证 杀 Worker、重复投递、制造超时、压满队列、伪造租户身份，验证系统是否仍守住承诺。 产物：测试、指标、演练与改进闭环
11 / CONCEPTUAL GLOSSARY

用“职责”理解术语，不用框架里的类名理解术语

下面是领域级含义。具体 SDK 可能使用不同名字，甚至把多个概念合并成一个对象。

Agent利用模型、上下文和工具进行选择与行动的智能行为体。重点：它负责“决定做什么”。
Runtime让 Agent 真正跑起来的执行环境与循环。重点：它负责“怎样跑”。
Harness围绕 Agent 的控制、状态、治理、恢复与观测能力集合。重点：它负责“怎样可靠地被系统使用”。
Orchestrator协调多个步骤、Worker、Agent 或服务之间的顺序与依赖。它可能是 Harness 的一部分。
Workflow工作步骤、等待点、分支和补偿的显式流程模型。它比开放式 Agent 规划更结构化。
Session一段持续交互或上下文共享边界。不等同于一次执行。
Task用户或业务希望系统完成的工作目标。它是业务语义。
Run / Attempt完成任务的一次执行实例或一次尝试。它有明确开始、状态和结束。
Turn / StepAgent 在一次运行中推进的一小步。可能包含一次模型调用或工具决策。
Command希望系统做某事的意图。“请开始”不代表“已经开始”。
Event系统中已经发生且不可改写的事实。可以被订阅、存储和重放。
State截至目前事实折叠出的当前视图。便于快速回答“现在怎样”。
Checkpoint可供恢复的已确认执行位置和必要数据。不是简单保存一段聊天文本。
ToolAgent 读取或改变外部世界的受控接口。副作用、权限和幂等最关键。
Memory跨步骤或跨会话保留、检索的经验与事实。它不天然等于数据库全部状态。
Policy根据身份、风险、资源和上下文决定允许、拒绝或等待的规则。可确定，也可包含受约束的智能判断。
The durable mental model

Harness 是不确定智能与可靠软件之间的“工程翻译层”

Agent 提供开放式能力；Harness 把能力约束在可识别的工作单元中，用状态记住现在，用事件保留过去，用策略限制下一步，用反馈判断系统是否值得信任。
  • 看到一个新组件时，先问它在防哪一种故障，而不是先背 API。
  • 看到一个术语时，先问它属于哪只生命周期时钟。
  • 讨论 Harness 边界时，先声明语境；不要假设所有框架定义一致。
  • 设计系统时，先写业务承诺、故障模型和不变量，再决定类、表和事件。
  • 评价架构时，不看组件多不多，而看它是否以可承受的复杂度守住了需要的保证。
