场景 8安全关闭：顺序与启动严格相反PASS
关闭时先停止接收新请求，再停 Pump，最后关 SQLite，避免半途写入。
server.stop(true)→ 队列 Pump 停止→ SQLite 关闭
close() 完成：HTTP 停止 → 队列 Pump 停止 → SQLite 关闭 RESULT: PASS
close() 幂等：重复调用复用同一个 promise；同时摘掉 SIGINT/SIGTERM 处理器。
场景 F1Worker 崩溃（SIGKILL 自身）PASS → FAILED
子进程被强杀时，Run 必须收敛到终态，且孤儿沙箱不能泄漏。
RUN_STARTED→ CONTROL_PREPARED→ SANDBOX_ACQUIRED→ Worker exit 137→ RUN_FAILED→ sandbox TERMINATED
终态 status = FAILED failureReason = "WORKER_CRASHED: exitCode=137, signal=SIGKILL Stderr: [Worker PID 26981] Simulating SIGKILL" attempt#1 status=FAILED reason=WORKER_CRASHED: exitCode=137, signal=SIGKILL sandbox status=TERMINATED failureReason=none ← 异常路径也没留下未回收环境
exitCode 137 = 128 + 9；Master 的 child.exited 看门狗把它翻译成 agent_failed → RUN_FAILED。
场景 F2Worker 主动回报失败PASS 但暴露不一致
Worker 经 IPC 发 RUN_FAILED 时，Run 的落点应当与崩溃分支一致。
RUN_STARTED→ Worker 发 RUN_FAILED→ Master 只 reject(start)→ RUN_INTERRUPTED→ failureReason = null
终态 status = INTERRUPTED failureReason = null attempt#1 status=FAILED reason=Simulated worker execution failure [WARN] 行为不一致：RUN_FAILED 分支只 rejectPromise，不发 agent_failed 事件， 于是走 markRuntimeInvocationFailureInterrupted → Run 变成 INTERRUPTED 且 failureReason=null，而不是像崩溃分支那样 FAILED。失败原因只留在 RUN_INTERRUPTED 事件的 payload.message 与 attempt.failureReason 里， Run 级 API 看不到。此差异无测试覆盖。
这段 [WARN] 是脚本自己打印的，不是我的推断。项目把缺陷以告警形式随证据输出。

Escalating to SIGTERM. 终态 status = INTERRUPTED attempt#1 status=FAILED reason=Agent Runtime 执行超时：5c7d69e2-... 二、需要外部环境、本次未执行的验收入口

scripts/ 下共 21 个可执行入口，本次只跑了 e2e-walkthrough.ts（含 failure 模式）， 其余 20 个未在本机执行。本机没有 GPU / Docker daemon / runsc， 我不为它们的结果背书。列出它们是为了让「测过什么」和「还没测什么」一样清楚。 （下列 12 张卡片覆盖这 20 个入口，部分卡片含 2–3 个脚本。）
E1e2e-gpu-pressure.ts需真实 vLLM /metrics

与已跑场景 3 的区别：观测源从 Fake 换成真实 /metrics，这正是它没被替代的原因。
E2e2-gateway-fault-matrix.ts · G04 网关错误分类全矩阵仅需本地 HTTP 夹具
401/400 不回退原样透传；429/5xx 可回退且有界；坏 JSON / 坏 SSE 不崩；usage 缺失不计数、重复不累加。
本地故障夹具→LlmGateway + ModelRouter→路由台账 / 缓存台账
判定依据是 HTTP 语义 + 台账 + 重试是否有界，不是「请求成功与否」。
E3container-sandbox-smoke.ts / :attacks需 Docker + runsc
前者验证非 root UID、只读 RootFS、仅挂载 Workspace、默认无网络；后者额外覆盖两租户 Workspace/Secret/路径越权、PID/tmpfs 上限、意外 kill → LOST。
docker run --runtime=runsc→docker inspect 取证→攻击用例
源码注释明确：fake Docker runtime 无法证明这些边界，所以本机没有 daemon 时这些命令应当失败，而不是把 fake 单测当证据。
E4e2-sandbox-limits.ts · S06/S08/X10需 Docker + runsc
CPU / 内存 / PID / tmpfs 四类限额必须「由运行环境实际执行」；并检查 Secret 是否经宿主可读路径（docker argv / inspect）泄漏。
破坏性压力（内存超额 / PID 风暴）会终结被压沙箱本身，所以每种压力用独立沙箱，避免污染对照。
E5e2-container-failure.ts · G09 Provider 边界需 Docker
镜像缺失 / 创建失败 → create 必须抛错且收敛为 FAILED、不留残留；运行中容器消失 → 识别为 LOST 而非普通工具失败；失败后同一 Provider 仍能创建新沙箱。
E6e2-warm-pool.ts · G10 容器热池需 Docker
冷/热启动耗时对比（热启动必须显著更快且 warmHit=true）；另一租户不能租到别人的热容器；热容器里看不到上次残留的文件/环境变量/Secret；结束后不遗留 agent-harness-warm-*。
E7sandbox-runtime-benchmark.ts需 Docker + runsc
在同一台机器、同一镜像上比较 runc 与 runsc 的冷启动 / 命令执行 / IO / 清理耗时，为 Kata、Firecracker Provider 预留同一套实验方法。
