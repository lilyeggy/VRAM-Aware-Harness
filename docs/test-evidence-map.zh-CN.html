§3 覆盖缺口（诚实清单）

缺口 1：F2 的语义不一致没有任何测试断言。 两个分支各自都有测试——Worker 主动报失败见 tests/runtime/worker-process-runtime.test.ts:137，但它只断言 caughtError?.message 含 "Simulated worker execution failure"（即错误确实透传到 Runtime 层）； 崩溃分支见同文件 :158。 没有任何测试断言"这两个分支在 Run 级终态语义上应当一致"，所以 RUN_FAILED → INTERRUPTED + failureReason=null 这个差异可以长期存在而不报警。
缺口 2：single-flight onError 重复计数没有断言。 tests/scheduling/run-queue-pump.test.ts:118 使用了 onError 探针，但断言的是 "报错后仍能继续下一次推进"，不是调用次数； run-queue-coordinator.test.ts 覆盖了 single-flight 的复用与清理， 但没有测试在"并发 tick + 一次失败"的组合下数 onError 被调了几次。 实测该值为 9（去重后 1）。
缺口 3：真机验收未执行。以下内容不是"没写测试"，而是"没在具备条件的环境跑过"： smoke:container / smoke:container:attacks / e2-sandbox-limits / e2-warm-pool / e2-container-failure / sandbox-runtime-benchmark / e2-gateway-fault-matrix / e2e-gpu-pressure。本机无 Docker daemon、无 runsc、无 vLLM。 与之相对，"有测试"的部分并不因此打折：§1 里 H 组（隔离证据方向）的 fail-closed 逻辑 是纯逻辑可测的，已全部有断言。
缺口 4：MANUAL_REVIEW 之后的人工确认闭环缺端到端。 已有：拦截为 MANUAL_REVIEW（recovery-hardening.test.ts:115）、 审计写入事件时间线（:248）。 尚无：一个"人工确认 → 继续推进 → 终态"的端到端用例。
