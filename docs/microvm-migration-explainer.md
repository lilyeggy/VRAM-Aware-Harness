# 从 Docker 切换到 microVM：问题详解与解决方案（不含代码修改）

> 面向不具备操作系统背景的读者。目标：理解每个问题的"为什么"，以及对应方案解决的是什么。
> 前提回顾：上一轮已完成 Phase 0——封死了 E2B 假执行、Firecracker 缺配置时的静默降级、伪造的隔离证据（fail-closed）。本文讲的是"真正切过去"还差什么。

---

## 0. 一个总的认知框架

把隔离强度想象成"墙的材质"：

| 方案 | 墙是什么 | 墙塌了的条件 |
|---|---|---|
| runc 容器 | 宿主内核自己划的线（namespaces/seccomp） | 宿主内核漏洞 → 全体租户沦陷 |
| gVisor runsc（现状） | 用户态翻译层（Sentinel），拦截翻译所有系统调用 | gVisor 自身实现缺陷或被绕过 |
| Firecracker microVM（目标） | CPU 硬件虚拟化边界（VT-x/AMD-V，即 /dev/kvm） | 需要 CPU 漏洞级别的攻击（极罕见且有硬件补丁） |

结论：**方向是对的**。microVM 给每租户一个独立内核，"每用户一台云电脑"在安全语义上成立。但独立内核也意味着：**所有原来"宿主内核免费帮你做的事"（文件共享、进程创建、资源限额、网络），现在都隔着一条硬件边界，必须显式地重新设计**。下面六个问题全部源于此。

---

## 1. 命令通道：串口是"隔门喊话"，vsock 才是"对讲机"

### 现状（问题所在）
当前 Firecracker 驱动通过**串口**（ttyS0）向 guest 发命令：把命令文本直接写进虚拟机的"终端输入"，然后在输出里找一个哨兵字符串（`__HARNESS_DONE_xxx__: 退出码`）判断命令结束。

### 为什么这是问题（原理）
串口的本质是"往一台机器的键盘上打字、看它的屏幕输出"。这意味着：

1. **命令被 shell 二次解释（注入）**：命令是按空格拼起来的文本，含引号、`$`、`;` 等字符时会被 guest 里的 shell 重新解释，语义和你以为的不一样。
2. **哨兵可被伪造**：哨兵是一个普通字符串，guest 里的**任何**进程（包括正在跑的恶意代码）都可以打印 `哨兵:0`——于是宿主以为"命令成功结束、退出码 0"，而恶意代码继续在后台跑。超时熔断也被架空。
3. **stdout/stderr 不分离**：guest 里所有输出混在一条流里，上层无法区分正常输出与错误信息。
4. **共享 root 会话**：所有命令在同一个登录为 root 的持久 shell 里执行，环境变量、工作目录互相污染——A 工具设置的变量会被 B 工具看到。

### 解决方案：virtio-vsock + guest agent
Firecracker 提供的标准 host↔guest 通信设备叫 **vsock**——可以理解为宿主和虚拟机之间的一根"专用对讲机线路"：

- guest 里跑一个小型守护进程（agent，开机自启）；
- 宿主通过 vsock 发**结构化请求**（例如 JSON：`{command: [...], workdir: "...", env: {...}}`，命令数组做 base64 编码，彻底避免注入）；
- agent 收到后 **fork 一个专用子进程**执行（每次命令独立环境、独立退出码），把 stdout/stderr/exitCode 以结构化响应回传；
- 请求带随机 nonce，响应必须携带同值——杜绝伪造。

**为什么这样安全**：通道里传的是数据而不是"待解释的指令"；执行环境每次隔离；身份靠 nonce 而不是靠"猜字符串"。

## 2. jailer：给"虚拟机管理程序"本身上锁

### 现状（问题所在）
当前直接以 Harness 进程的身份 spawn Firecracker：管理 socket 放 `/tmp/fc-<id>.socket`（路径可预测、目录共享），rootfs 副本也放 `/tmp`。

### 为什么这是问题（原理）
要分清两个东西：

- **guest 里的 root**：被 KVM 硬件边界关着，无害——这正是我们买 microVM 的原因；
- **Firecracker 进程本身**：它是宿主上的普通进程，以启动它的用户的全部权限运行。它读写磁盘文件、占用内存、监听 socket。

如果 Firecracker 进程本身被攻破（或被滥用），攻击者拿到的不是"一台虚拟机"，而是**宿主上的一个进程**。更具体的两条现实路径：

1. Firecracker 的管理 socket **没有任何鉴权**，且放在人人可写的共享 `/tmp` 里：同机的其他本地用户可以抢先创建同名 socket、或直接连上它，下发自己的 boot 配置（比如把磁盘指向宿主上的任意文件）。
2. rootfs 副本（上一个 run 的完整磁盘内容）在删除前躺在 `/tmp`，同机用户可以直接读取——**跨租户数据泄漏**。

### 解决方案：官方 jailer
Firecracker 官方随包提供一个 `jailer` 工具，它做四件事（这就是 AWS Lambda 的生产部署姿势）：

1. **降权**：Firecracker 不再用你的用户身份跑，而是每台 VM 一个专用低权限 UID/GID——即使逃逸，能碰的东西也极少；
2. **chroot**：把 Firecracker 关进一个只含必要文件的目录，它"看不见"宿主的其他文件系统；
3. **独立网络命名空间（netns）**：它没有任何网络；
4. **cgroup 限额 + seccomp**：限制它的 CPU/内存，并禁止它调用用不到的系统调用。

同时把所有 socket、磁盘副本放进 **0700 权限的私有目录**（路径随机），/tmp 问题随之消失。

## 3. 工作区数据流：VM 天生"看不见"宿主目录

### 现状（问题所在）
上一轮改成了"每 Run 复制一份 ext4 工作区盘挂进 VM"——隔离对了，但 **VM 里写的数据不会自动回到宿主的工作区目录**。run 结束后，快照/artifact 系统看到的是空目录。

### 为什么这是问题（原理）
容器可以 bind mount（把宿主目录"映射"进容器），因为它们**共享同一个内核**——同一个文件系统缓存、同一个 inode 空间。虚拟机有独立内核，它的世界里只有"挂给它的虚拟磁盘"，宿主目录在它的物理宇宙中不存在。这不是 bug，是虚拟机的定义。

### 解决方案（三选一，建议先 B）
- **A. virtio-fs / 9p 共享文件系统**：实时双向共享。代价：性能损耗显著，而且等于重新打开一条"guest 直接触达宿主文件系统实现代码"的通道——我们在花力气缩小攻击面，不要随手又开一个。
- **B. 终止时导出（建议）**：run 结束时，guest 内 `sync` 落盘，宿主把 ext4 副本挂到私有目录（loop mount）或用 `debugfs` 直接抽取文件，写回用户工作区，然后销毁磁盘副本。简单、隔离最干净，且和你们现有的"run 级 BEFORE/AFTER 快照"语义天然一致——本来快照就是 run 结束时拍的。
- **C. 定期导出**：长任务场景下周期性做 B，减少崩溃时的丢失窗口。

## 4. 启动性能：冷启动与 snapshot restore

### 现状（问题所在）
每个 run 都要走"整盘复制 rootfs（同步阻塞）→ 开机 → 等串口就绪"，秒级延迟；且没有预热池。

### 为什么这是问题（原理）
- 容器启动 = 创建一个进程，毫秒级；
- VM 启动 = 一台电脑完整开机：内核解压、驱动探测、init……Firecracker 裸启动本身只要 ~125ms（它就是为此优化的），但你们现在叠了两个放大器：
  1. `copyFileSync` **同步整盘复制**——几百 MB 的镜像会让整个 Node 事件循环卡住，**所有**并发用户的请求一起卡；
  2. 没有"已开机 VM"的存货。

### 解决方案：两个成熟技术
1. **Firecracker snapshot/restore**：把一台已经开机到"就绪状态"的 VM 的**完整内存 + 设备状态**拍照存成文件；下次创建 VM 不再开机，而是把照片直接加载进内存接着跑——~10ms 级。这正是 AWS Lambda 冷启动优化的核心机制。可以理解为"把开好机的电脑连同内存一起冷冻，用时解冻"。
2. **CoW 磁盘副本**：用文件系统的写时复制（reflink / overlay）代替整盘复制——多台 VM "共享"同一份只读模板，各写各的增量，复制成本从 O(镜像大小) 降到 O(1)。
3. **microVM 预热池**：你们容器链路已经有 `ContainerWarmPool`（预热 + 命中即补货），microVM 需要等价物——预热的是"restore 好的 VM + CoW 盘"，语义几乎可以照搬。

另外：所有文件复制必须异步化（worker 线程或异步 IO），不能阻塞事件循环。

## 5. 受控出口网络（controlled-egress 的真实实现）

### 现状（问题所在）
VM 没有网卡，`allowNetwork=true` 的策略已被 fail-closed 拒绝。功能上是缺的。

### 为什么不能"直接给网卡"
给每台 VM 一张直通网卡 = 它可以访问任何地方：内网元数据服务、其他租户、数据库。多租户场景下**必须**经过一个强制检查点。

### 解决方案：每 VM 独立 netns + 出口网关
1. jailer 已给 Firecracker 进程独立 netns；
2. 在其中创建 tap/veth 设备，VM 的虚拟网卡接到这个 netns；
3. netns 的默认路由指向一个**出口代理**（网关进程）：只有白名单里的目标（例如 `api.openai.com`）放行，其余拒绝，并记录审计事件。

这样"controlled-egress"从名字变成事实。gVisor 容器链路未来也走同一个网关，两边策略语义一致。

## 6. 资源限额与数据残留

### 限额：VM 外面的 cgroup 比 VM 里面更硬
- **CPU/内存**：直接对 Firecracker 进程（jailer 已放入 cgroup）设限——这是宿主侧强制的，guest 里的 root **改不了**（对比：容器里 root 理论上能感知/干扰自己 cgroup 的一些行为）。这反而比容器更干净。
- **磁盘**：给工作区盘设"稀疏文件 + 上限大小"，超限即拒绝写入。
- **PID/进程数**：guest 内 cgroup 由 agent 配置，或内核启动参数 `nr_cpus`/`init_on_alloc` 等收紧。

### 数据残留：用"加密临时盘"一次性解决
现状：磁盘副本 `unlink` 后数据还在磁盘块上，直到被复用；SIGKILL 停 VM 时 ext4 日志未刷，可能残留半新半旧的数据。

方案：每个 run 的工作区盘用**一次性随机密钥加密**（loop 设备 + dm-crypt，或 LUKS），密钥只存在 Harness 内存里，run 结束即丢弃密钥——磁盘块本身不用擦，**没有密钥就是一堆乱码**。这比 shred 快得多，也彻底。

## 7. 切换路线图与"要不要全切"

### 建议的分阶段路径

| 阶段 | 内容 | 达成 |
|---|---|---|
| Phase 0（已完成） | 封死假执行/假证据，fail-closed | 不再撒谎 |
| Phase 1 | vsock agent + jailer | 安全边界成型（P1 #5、#6） |
| Phase 2 | 工作区导出 + 资源/磁盘限额 + 加密临时盘 | 功能与生命周期完整（P1/P2 #3、#9） |
| Phase 3 | snapshot restore + CoW + microVM 预热池 + 异步复制 | 性能达标（P1 #7） |
| Phase 4 | 出口网关 + controlled-egress | 能力对齐 gVisor |

### 迁移方式：不要一刀切
`SandboxProviderRouter` 天然支持按 profile 路由：**strict（microVM）与 default（runsc）双轨并行**，按租户灰度切流。每一步都有对照组，出问题可秒级回退到 gVisor。

### 一个诚实的提醒
gVisor 已经是强隔离（Google Cloud Run 生产同款）。切 microVM 的**必要性**来自：合规/客户要求"每用户一台独立机器"、或需要比"翻译层正确性"更强的硬件边界保证。如果动机是"更安全"，收益是真实但边际的；如果动机是产品语义（云电脑），那 microVM 是唯一选择——而上述六块硬骨头就是要付的完整代价。

## 附：术语速查

| 术语 | 白话解释 |
|---|---|
| KVM / /dev/kvm | Linux 内核提供的硬件虚拟化接口，让 CPU 用 VT-x 指令隔出"假电脑" |
| VMM / Firecracker | 管理虚拟机的那个宿主进程；Firecracker 是极简实现 |
| Guest / 宿主 | 虚拟机里面的系统 / 跑虚拟机的真实机器 |
| 串口 (ttyS0) | 虚拟机的"键盘+屏幕"文本通道 |
| vsock | 宿主与虚拟机之间的专用 socket 通信通道 |
| jailer | 官方工具：给 Firecracker 进程降权、隔离文件系统与网络 |
| snapshot/restore | 把开机状态的 VM 连内存一起存档/秒级恢复 |
| netns | 网络命名空间：一套独立的网卡/路由表，互相看不见 |
| cgroup | 内核的"资源配额表"：限 CPU、内存、进程数 |
| CoW (reflink) | 写时复制：多台 VM 共享只读模板，只保存各自改动 |
| ext4 | Linux 常用的磁盘文件系统格式 |
