## 0. 一句话总结

**86 个场景里约 76 个通过、5 个 FAIL（全部有证据且已定位根因）、3 个未跑、2 个只跑了部分；Q12 与 8h 长稳均已收口。**
系统侧（状态机 / 调度 / 隔离 / 恢复 / 网关）非常稳，**0 跨租户泄露、0 不安全重放、终态未被迟到事件覆盖**；缺陷集中在**恢复语义、UI 渲染与离线可观测、预算公平**三处。
**最大的短板不是系统，是模型能力**——但**这条结论只对 T7 成立**。跑道 A 报出的 T2/T3/T6/T7 "全数 0 通过" 已逐案复核：T2 的 10 例答案全对（0% 是验收器字符串比较缺陷 + 驱动复用会话）、T3 的 12 例被验收器缺陷（`added` 判据不取 `.path`）与工作区复用叠加压成 0（外层还有落盘问题）、T6 是任务做对但落盘 JSON 少了右花括号（上游 **N27**）、**只有 T7 是真实的能力/步数上限失败**（详见 known-issues §20）。
**真正的上游短板是 N27**：vLLM 流式工具调用参数偶发丢末字符（实测 26%，批次间 5%–58%），直接决定"结构化产物"能不能落盘。

**三个必须随数字一起说明的点：**

1. **λ\* 低估了容量。** λ\* 由闭环 C=4 定义，而 A4 的开环 2.29×（2.291 任务/s 到达）实际达成 **1.887 任务/s**，比 λ\* 高约 65%。指南正好警告过这一点——闭环会在系统变慢时自动减少提交，**掩盖过载**。所以 λ\* 是保守下界，不是容量上限；真正的可持续区间由 A4 的稳态档给出。
2. **A1 的 t4/t6/t7/t8 与另一路发压器并发跑过**（子智能体④的 `campaign-driverdev`），这几档的数字可能被并发负载污染，摘要里已自行标注。
3. **上进并发档位是环境阻塞而非系统拐点**：C=8/16/32 未跑是因为宿主 GPU 余量 <1G（共享机、vLLM 预占 44G），不是因为系统在 C=8 就撑不住。

**另注**：A3 的 66 个失败（3.2%）是模型在批处理下把 `17×23` 答成 `3` 而非 `391`——与之前发现的"改措辞答 491"同源，**属模型不确定性，不是系统失败**。

## 4. 整体评估（诚实版）

**稳的部分（可以拿出去讲）**
- 硬性安全不变量经住了：跨租户读/写/凭证 15/15 拒绝、**不安全副作用重放 0 次**（R05/X05 都是真实写盘 + 真 `kill -9` 验的）、终态未被迟到/重复事件覆盖（R12）。
- 隔离是真的：runsc 下 `uname` 报 `4.19.0-gvisor`，Secret 不再进 argv 与容器 `Config.Env`，PID/内存/tmpfs 限额真实生效。
- 恢复与故障传播大体正确：Checkpoint 恢复同 runId 推进且不新建 Run、Worker `kill -9` 只影响该 Run、网关断流会熔断并切换（修 N17 后）、SQLite 忙/只读都 fail-closed 不伪造成功。
- 容量上有实测曲线：**λ\* ≈ 1.15 任务/s**、E2E p50 3.4s / p95 5.0s、TTFT p50 1.4s。

**不稳的部分**
- **恢复语义**是当前最薄弱一环：N18（静默降级）、N19（槽位活锁 + 沙箱泄漏）两个高危都在这条路径上，而恢复恰恰是"用户已经踩过一次坑"之后最需要可靠的地方。
- **UI 可观测性**：N25（离线无提示）+ N22（跨对话串扰）+ N24（路径不可读）三条叠加，意味着"界面看起来没问题"这件事本身不可信。
- **预算公平**：N23 会让开了预算的集群谁也跑不动，属功能性断流。

**必须随报告披露的口径问题（否则数字会被误用）**
1. **λ\* 是 T1 单族测出来的**，不是混合负载容量。任务族的正确率另有归因问题：**只有 T7 的 0%（10/10 未完成）是真实能力上限**；T2/T3/T6 的 0% 分别由验收器缺陷、驱动会话/工作区复用、以及上游 N27 造成，**不能当能力数据用**（known-issues §20）。真按 §9.2 的 25/30/20/15/10 混合打，有效吞吐仍会低于 λ\*，但降幅待重跑测定。2. **T4/T7/T10 的 diff 判据是空判（T1 缺陷）**，这些族的通过数不可信，必须修复后重跑或对已存 diff 离线复算。
3. 所有吞吐/延迟都是**共享主机、含邻居负载**（load≈31、22 个 polar 评测容器、vLLM 预留 44G）条件下的数值，不能当独占容量承诺。
4. 长稳跑了 **8 小时档**：RSS 四时段均值 237/231/233/234 MB、FD 早期升到 ~30 后持平、线程 22–25、沙箱容器收工归零，**可以说"8 小时内无内存/FD/容器泄漏"**；但 **24h 档仍未跑**，不能外推到一天以上。
5. 环境档要标准：**bash 只能用 container，而 container+runsc 就是 E2**——不存在"E1 且能用 bash"，所以 T4/T7/T8/T10、R01/R04/R07 实际都是 E2。

**真正卡住"结果正确"的有两层，别混为一谈。** 一层是**上游 N27**（流式工具参数丢末字符，26%），它让"把结构化内容写进文件"这件事在落盘那一步就碎了——T3/T6 的 0% 是它造成的，与模型无关。另一层才是**模型能力**：T7 只读 10/20 个模块、只修 5 个缺陷中的 1 个，是实打实的步数/纪律上限。把这两层分开之后，本项目的定性应当改成：**平台把状态机、隔离与恢复做扎实了；"结果正确"的上限一层卡在推理框架的流式工具协议上，一层卡在 7B 模型的工具纪律上**——这个区分比笼统说"短板是模型"更有价值，也更经得起追问。
