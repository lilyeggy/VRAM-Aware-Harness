这是一个支持团队共享本地模型的多租户 Agent 任务服务。用户在独立 Workspace 中提交任务、查看过程并取得回答、文件 Diff 和 Artifact；现有 可靠执行内核负责 Run、副作用、资源准入与恢复，下一步重点补齐可信身份、 真实 Sandbox 和用户端到端任务体验。

系统承诺： Tenant 之间不能互读代码与 Secret；资源不足时不盲目启动；进程失败后 不盲目重做；用户最终获得可使用的修改结果，而不只是内部终态。

01 / responsibility boundary

先把责任边界钉死，系统才不会越做越散

Pi 决定 Agent 如何工作，vLLM 决定推理如何执行；Harness 管理跨 Run 的可靠性、资源准入与审计。这个边界是当前设计最正确的部分之一。

Behavior plane

Pi Agent Runtime

拥有模型—工具循环、Pi Session、上下文压缩与内置工具协议。

  • 接收 start / resume / interrupt
  • 产生即时 RuntimeEvent
  • 维护 Agent 如何完成任务
Control plane

VRAM-Aware Harness

拥有持久 Run、恢复安全边界、资源策略、逻辑并发 slot 与追加式审计事实。

  • 决定任务何时可以启动
  • 决定失败后能否自动恢复
  • 解释为什么启动或排队
Inference plane

vLLM + NVIDIA GPU

拥有 batching、Prefill/Decode、KV Cache、显存分配与真实推理执行。

  • 暴露 Metrics 与设备状态
  • 执行模型请求
  • 不理解 Run 和工具副作用
当前资源感知发生在 Run 准入层：它控制一个新 Run 或恢复 Run 是否提交给 Runtime；它不接管 vLLM 的 token scheduler，也不物理管理 KV block。

05 / core mechanics

四个机制，构成当前 Harness 的真正内核

状态机约束合法生命周期；恢复门判断能不能自动继续；资源策略决定现在能不能开始； Scheduler 保证选中与占 slot 是一个动作。

run state machine

Run 是持久任务，不等于一次模型调用

一个 Run 可以经历多个模型调用与工具阶段。终态不可逆，恢复只能从 INTERRUPTED 重新进入 QUEUED。

QUEUED→ RUNNING↔ WAITING_TOOL→ COMPLETED
RUNNING→ INTERRUPTED→ QUEUED→ RUNNING
recovery safety gate

恢复判断的是“能否继续”，不是“重试几次”

Checkpoint 提供恢复位置；PREPARED 工具提供崩溃窗口内的副作用事实。二者共同决定自动恢复边界。

checkpoint?不存在可靠恢复位置MANUAL
READ_ONLY未完成调用可以安全重放AUTO
IDEMPOTENT明确具备幂等语义才可重放AUTO
UNKNOWN可能已经产生外部副作用MANUAL

07 / principal engineer review

从技术大牛视角看：主干是对的，下一步要从“语义闭环”走向“系统承诺”

当前设计最有价值的不是模块数量，而是已经形成可靠执行内核。 但它仍是单进程 MVP：生产化的难点会集中在 lease、隔离、幂等边界和真实资源数据。

overall verdict

这是一个可信的 Harness MVP，不是生产级云平台

架构方向正确：Runtime 可替换、事实优先、恢复保守、资源决策可解释。 真正的下一关不是再加几个 CRUD，而是让这些承诺在并发进程、网络重试、 Workspace 隔离和真实 A6000 压力下仍然成立。

边界清晰

没有重写 Pi Agent Loop，也没有假装控制 vLLM token scheduler。

证据驱动

Run、事件、工具、Checkpoint、资源和决策均有持久事实。

恢复保守

不确定副作用进入人工处理，避免“自动恢复”变成重复破坏。

确定性基线

153 项测试让策略和故障分支先可证明，再谈智能调度。

风险

两个 Harness 实例共享 SQLite 时，可能同时认为同一个 Run 可执行；进程失联也没有可过期的执行所有权。

深挖

引入 RunAttempt、owner_id、lease_expires_at、fencing_token，并让 claim 成为数据库条件更新。

证明

双进程竞争、旧 worker 迟到写入、lease 过期接管与重复完成事件的故障注入。

风险

客户端超时重试可能创建两个 Run；Runtime 恢复后若 toolCallId 变化，历史成功结果无法自动命中。

深挖

增加 tenant-scoped idempotency key、RunAttempt 和业务幂等键；明确每类工具的 dedupe contract。

证明

网络响应丢失、相同提交重复十次、恢复后 toolCallId 改变、外部 API 超时但实际成功。

风险

云端部署后，逻辑 Tenant 字段不能阻止路径越界、进程逃逸或访问其他租户文件。

深挖

Workspace sandbox、路径根校验、Tenant Capability Policy、Tool/Skill allowlist、密钥作用域和网络 egress policy。

证明

符号链接穿越、绝对路径、bash fork bomb、跨 Tenant 文件读取和未经授权工具调用测试。

风险

临界阈值附近会反复 START/QUEUE；Decision 没有完整保存 policy version 和阈值配置哈希。

深挖

观测 TTL、EWMA、hysteresis、采样批次复用、Run/Request 归因、policy_version 与 config_hash。

证明

压力锯齿、Metrics 延迟、nvidia-smi 超时、同一 Snapshot 批量准入与历史决策重放。

风险

长时间 bash、测试或外部 API 等待会占据 Run slot，导致 GPU 空闲而队列不推进。

深挖

先测量 MODEL / TOOL / IDLE 阶段，再考虑 Run lease 与 inference permit 分离、阶段感知容量。

证明

工具等待占比、GPU idle 时间、切换 permit 前后吞吐、公平性与恢复复杂度对照。

风险

一个 drain pass 中多个 attemptNext 各自 observe，既增加开销，也可能基于不一致快照作出并发决策。

深挖

单轮共享 Snapshot、Admission batch、有限并发观测、快照有效期和一次决策分配多个 permit。

证明

100 个等待 Run 下的 nvidia-smi 调用次数、drain 延迟、决策一致性和故障隔离。

风险

一个超长 Run 与一个短交互 Run 消耗同一个 slot；VIP、deadline、token plan 都无法表达。

深挖

Weighted DRR、cost estimate、deadline/SLO class、最大输出 token budget 与 aging。

证明

长短任务混合、Tenant 权重、尾延迟、有效吞吐与估算误差校准。

风险

真实 Pi/vLLM 故障时，RunEvent 只能解释领域事实，无法快速关联网络、模型请求和 GPU 指标。

深挖

OpenTelemetry trace_id/span_id、结构化日志、RED/USE 指标、事件归档和防篡改哈希链。

证明

从 HTTP submit 一键定位到 Pi 模型请求、工具执行、vLLM 指标与最终 RunEvent。

08 / depth roadmap

后续主线由 ADR 0009 固定：不再扩张异构 Runtime 和大型控制面，围绕 用户任务闭环建设可信身份、Tenant Workspace、真实 Sandbox、编排恢复 和结果交付。第③④层是内部技术重点，不是产品名称。
