想象你走进一家代办事委托中介：你把任务交给柜台，它替你把一切都安排妥当。

一个系统，三层分工

控制面（Control）管「谁能跑、在哪跑、何时跑、失败了怎么办」；行为（Behavior）由模型负责——它动脑；基础设施（Infrastructure）提供隔离工作间与算力。三层各司其职，互不越界。

安检口：身份与隔离墙

想进贵宾室，先过安检。系统的 身份 是从密钥派生出来的——请求体里自称的租户，一个字都不信。

🏢

一个客户/团队一个独立空间。所有数据按它 隔离，别的租户看不见。

📁

密钥 · 安检凭证

密钥不直接存数据库，只存哈希。查得到才算数，查不到就拒绝。

真实代码 

    authenticate(rawKey: string): RequestPrincipal | null {
        const row = this.db.query<CredentialRow, { keyDigest: string }>(`
            SELECT id, key_digest AS keyDigest, subject_id AS subjectId,
                tenant_id AS tenantId, scopes_json AS scopesJson,
                created_at AS createdAt, revoked_at AS revokedAt
            FROM api_credentials
            WHERE key_digest = $keyDigest AND revoked_at IS NULL;
        `).get({ keyDigest: digest(rawKey) });
        if (row === null) return null;
大白话

「验证」：拿客户端递过来的密钥，查出它的身份。名字就叫 authenticate（认证）。

先把密钥做一次哈希处理，然后去数据库里找匹配的记录。

找到就把它的身份信息取出来：属于谁、属于哪个租户、带哪些权限。

查询锁定在两件事上：只按密钥指纹找，而且只找没被吊销的。

执行查询，把「密钥指纹」作为查找条件传进去。

一条都没查到（密钥错了或已吊销）就返回「没有这个人」，直接拒绝。

注意：身份全部来自查表结果，而不是 请求体里客户自己报的。

验证通过后，「登机牌」长这样：你是谁、属于哪个租户、能做什么（ 权限范围）。

塔台：Run 与 Attempt

Run 是「一次用户任务」，Attempt 是「那一次实际执行」。任务先进入 队列排队，轮到才执行；失败 重试 = 新的 Attempt，绝不覆盖原任务。

✈️

Run · 一次任务

乘客的行程单：用户想要什么、属于哪个会话、当前什么状态。任务可以对应很多次执行。

🛫

航班的一次具体起飞：尝试编号、用了哪个沙箱、什么状态、失败原因。重试 = 新 Attempt。

机库：飞行记录仪与记账本

每一次执行、每一步动作，都作为事件写进 SQLite，长期 持久化保存。

0001 RUN_CREATED 任务建档
0002 RUN_QUEUED 进跑道排队

0004 TOOL_COMPLETED 工具完成，结果入账

每条事件都带着递增的 序号，只 追加、不可 篡改。改动任何一步，后面的时间线就对不上了；网络抖动导致重复上报时，系统靠稳定编号 去重，只记一次。

03

数据如何流动

Command、Event、State 三种信息，怎样落进 SQLite，又怎样回放——跟着一封信走完整个系统。

三种信息：想干嘛、发生了什么、现在是什么

系统里跑一次任务，会产生三种信息——就像寄一封信：快递单上的指令、每一站盖下的邮戳、信件此刻所在的站点。

把它们记成三个词：Command、Event、State。

✉️

Command · 想让它干嘛

快递单上的指令。用户说「帮我把这个任务跑通」，指令带着目标进入系统。

📮

Event · 刚刚发生了什么

每一站盖下的邮戳：「已排队」「工具已调用」……只追加，不改写。

📍

State · 现在是什么

信件此刻在哪一站。最新状态一查就知，但它只反映「现在」。

快照 vs 历史：一张状态牌 + 一本邮戳册

系统同时维护两张表：快照表 agent_runs 是「当前状态牌」，追加式表 run_events 是「邮戳合订本」。

为什么不能只留一本？因为「现在」会被不断覆盖，而「过去」必须完整保留——排障、回放、审计都靠它。

🪧

agent_runs · 当前状态牌

每封信只占一行，永远是最新状态。像快递页顶部的最新动态，一查就知。

📔

run_events · 邮戳合订本

每一站一条记录，按 sequence 编号，只增不改。像钉在册子里的邮戳，一张张往下加。

PLAIN ENGLISH

状态跳转不是随意的，得遵守规则表——这就是「状态机」。

定义一个「盖章检查员」：想从 A 状态跳到 B 状态时，先叫他来验票。

检查员读规则表，看看这个跳法在不在许可名单里。

不在？直接抛错：报出「从哪跳到哪不合法」——邮戳不能乱盖。

合法才放行，状态才能往前走。

QUEUED → RUNNING 排队中 → 资源到位，开始跑（也可能被打断）
RUNNING → WAITING_TOOL 运行中 → 停下来等工具结果
WAITING_TOOL → RUNNING 工具结果回来了 → 继续跑
RUNNING → COMPLETED / FAILED 正常完成，或失败
INTERRUPTED → QUEUED 被打断 → 重新排队
COMPLETED / FAILED → 终点 到终点后不再跳转

决策也要留证据

任务能不能开始，由策略决定：放行（START）还是排队（QUEUE）。

沙箱：真的隔离，不是假装

沙箱不是纸面承诺——它真的是一台 容器 。每个任务都会被请进一间「一次性隔离工作间」：只挂进它自己那份材料（workspace），墙是只读的，没有网线，没有管理员钥匙。

盒子的模板叫 镜像 ，创建、查看盒子靠 Docker ；而真正让盒子跑起来的引擎叫 runtime 。

development 本地调试专用：不做隔离，可联网。它从不是多租户生产档。
default 默认生产档： runsc （ gVisor ），只读 + 断网。
restricted-egress 受控出口档：预留，尚未接入代理，当前拒绝直连公网。
strict 最严档：预留，必须路由到独立 microVM Provider。

这些档位叫 profile 。下面这份施工图纸，把工作间的每项硬性要求编译成 Docker 能听懂的参数——这是真实代码里的原样片段：

CODE

开始建工作间：后台运行、任务结束时自动整个拆除、名字用这次任务的。

用普通用户身份进去——不是管理员，没有钥匙。

墙是 只读 的；把 特权清单 直接撕光（cap-drop ALL）。

禁止再申请任何新特权；最多同时跑 128 个 进程 （pids-limit 128）。

工作目录固定为 /workspace——也就是挂进来的材料箱。

把宿主电脑上的工作区文件夹「插」进来当 U 盘（ bind mount ），只有这一份。

临时目录放内存盘（ tmpfs ）：能写，但禁止执行、禁止挂载，限 64MB。

每一条参数都在回答同一个问题：如果攻击者使坏，他能碰到的东西有多小？答案被压到只剩「他自己那份材料」。

配置 ≠ 事实：先验货，再开工

施工图纸说「用防弹玻璃」。但你不亲手摸一摸，怎么知道装上去的不是普通玻璃？

所以每次沙箱启动后，系统会用 inspect 去「验货」：读真实容器上实际生效的 runtime。这一步的意义是——配置只是 证据 要验证的「意图」，而不是事实本身。

🛡️
防御不静默降级（fail closed）

配置写 runsc，就绝不允许 runc 悄悄顶上。 静默降级 是敌人；隔离是承诺，承诺必须被检查——inspect 对不上就 fail closed 。宁可任务不跑，也不假装安全。

这段真实代码就是「验货」本身——DockerRunscRuntimeAdapter 每次启动后都这么做：

CODE 

        const result = await commands.run([
            docker, "inspect", "--format", "{{.HostConfig.Runtime}}", containerName,
        ]);
        const observedRuntime = result.stdout.trim() || null;
        const verified = result.exitCode === 0 && observedRuntime === this.runtime;
大白话

向 Docker 发一个验货请求：读取这个真实容器的 HostConfig.Runtime 字段——它记录「实际用的是哪个 runtime」。

把读到的值前后空白清干净，这就是「事实」里的 runtime 名字。

只有当命令成功返回、且事实确实等于我们要求的 runsc，才盖上「已验证」的章。

事实与意图一致，任务才准开工；不一致，直接 fail closed。这套代码同时在沙箱一侧的 OciSandboxSpecCompiler 里再拦一道：profile 必须配 runsc，否则抛错拒绝执行。

聪明的机制

为什么 AI 不能"说做就做、崩了就重跑"——记账、副作用分类、Checkpoint，以及拿不准就拒绝。

为什么执行前要"记账"？

AI 说"帮我干活"的时候，它面对的不是沙盘，而是真实的外部世界：文件真的会被改、请求真的会发出去、钱真的会动。所以系统有一条铁律——副作用发生之前，先记账。

这本账叫双复写记账本：动手前先写下"我准备做X"（工具的复写联），做完了再盖一枚"已完成"章。外部世界一旦被改动，就没有撤回键。

三种墨水：副作用的分类

每支工具进场前都要声明自己是哪一类副作用。账本上有三种墨水颜色，决定它享受什么待遇——能不能自动重试，还是永远要人拍板。

📖

READ_ONLY · 蓝笔

只看不改：读文件、查配置、问状态。重复执行一百次也不会改变任何东西——像翻书翻到同一页。

🔄

幂等IDEMPOTENT_WRITE · 绿笔

重复执行结果和第一次完全相同：盖两次章，还是同一个章。所以系统允许安全重试。

🔥

UNKNOWN_EFFECT · 红笔

可能改外部系统、可能花钱、可能发消息——谁也没法保证重复执行无害。这是热炉子：不确定，就绝不自动重试。

分类决定待遇：蓝笔绿笔可以自动重放，红笔永远要人拍板。真实代码里，这三种墨水就是一组简单的定义：

真实代码

Checkpoint：账本上的装订线

光有账本还不够——每次崩溃都从第一页开始恢复太慢了。所以每隔一段，系统会在账本上画一条装订线，这就是 Checkpoint：到这里为止，一切都确认过。

恢复时从最近的装订线接着走：已经盖过"已完成"章的记录直接复用结果，绝不重做。系统还把"成功结果"和"装订线"两笔写入放进同一个事务里——绝不会出现"账本说成功、却没有装订线"的中间状态。

热炉子警告

想象厨房里一锅"可能已经在烧的红烧肉"：账本上写着"准备开火"，但没有"已完成"章。肉可能在锅里炖着，也可能还没下锅——这时盲目再开一次火，就是重复扣款、重复发钱。正确做法：让人来看一眼。

Fail-closed：拿不准就拒绝

热炉子哲学：不确定炉子烧没烧，就绝不碰开关。系统的默认答案是拒绝，而不是"先试试看"。这份谨慎体现在每一道关口：

🧩
策略与 profile 冲突

Provider 配置与策略要求的 profile 不一致 → 直接抛错，不硬着头皮建沙箱。

💾
磁盘配额无法落实

bind mount 技术上无法强制磁盘配额 → 干脆拒绝执行，而不是假装限了。

🔍
Runtime 证据不符

Docker inspect 发现实际 runtime 和声明不一致 → 标记 FAILED，先销毁容器再报错。

第三个例子最有代表性——"证据"和声明不符，就按失败处理，绝不睁一只眼闭一只眼。看真实代码里第一个例子怎么拒绝：

真实代码

        }
大白话

如果策略要求了磁盘配额……

而这套实现根本没法强制配额——那就直接抛错：拒绝执行。

💡
这是整个系统最重要的工程品格

fail-closed（拿不准就关门），而不是 fail-open（拿不准就放行）。对 AI 干活来说，放行一次可能真金白银地烧掉钱；拒绝一次，最多浪费一次重试。

事件证据链：崩溃后还能回放

除了账本，系统还留了三样东西，组成一条完整的证据链：RunEvent（流水账）、Checkpoint（装订线）、Diff（改过页面的复印件）。重启之后，任务可以像看监控回放一样，把出事前的事重新走一遍。

但回放不等于放行：恢复的任务必须重新过一遍身份、策略、沙箱、资源准入。

06

当它出故障时

安全收敛与诚实边界——系统如何优雅地"坏掉"，以及哪些话绝不能说。

飞机不会硬着头皮继续飞

发动机失联时，机长不会赌一把继续飞，而是立刻按预案备降、腾空跑道、复盘。这套系统也一样：每一环都可能出故障，而它的设计目标是安全收敛——不硬扛、不泄漏、不重复。

🔇

沙箱失联（LOST）

容器被外部杀死或整个消失，怎么喊都没有回应。

💥

进程崩溃（FAILED）

任务里的 Agent 进程自己挂了，执行当场中断。

🔪

被外部 kill

这不是代码的 bug，是外力把容器强制终止了——系统必须能识别出这种"非我之过"。

🔁

重试策略

网络抖动这类小故障，按策略重试而不是放弃；但致命故障绝不盲目重试。

下面就是管家按响报警器的真实代码——它把事情做得干净利落。

CODE 

    private markLost(sandboxId: string, reason: string): void {
        const current = this.store.get(sandboxId);
        if (current === null || current.status !== "ACTIVE") return;
        this.containerBySandboxId.delete(sandboxId);
        this.secretValues.delete(sandboxId);
        const lost: SandboxRecord = {
            ...current,
            status: "LOST",
            updatedAt: new Date().toISOString(),
            failureReason: reason || "docker exec reported missing container",
        };
        this.store.update(lost, "ACTIVE");
        this.emit(lost, "LOST", lost.failureReason!);
    }
PLAIN ENGLISH

管家的"标记失联"函数：告诉它哪个沙箱丢了、为什么丢的。

先翻账本找到这个沙箱；如果它根本不在账上，或已经不是"活跃"状态，就立刻收手——绝不重复报警。

从名册上划掉"容器 ↔ 沙箱"的对应关系，清掉这个沙箱的密钥。

基于原记录造一份"失联版"：盖上 LOST 的章，记下报警时间。

写下失联原因；如果没有原因，就记录"docker exec 报告容器不存在"。

把这份失联记录写回账本（要求之前必须是活跃状态，防止写脏数据）。

最后 广播 LOST 事件——火灾报警正式响起，整栋楼都听得到。

槽位不泄漏，重启不慌

飞机备降后，跑道槽位必须还给塔台，下一班才能用。系统同理：沙箱终止时，容器、密钥、槽位一样都不能泄漏。

1
取出记录

从账本里找到这个沙箱和它对应的容器——先定位，再动手。

2
划掉映射、清掉密钥

容器映射和密钥先从内存里删除——从这一刻起，它不再是"活跃"的。

3
强制删容器

docker rm --force 把容器尸体也清掉，磁盘不留渣。

4
标记 TERMINATED

状态落账，TERMINATED——槽位随之还给池子。

控制面自己也会挂（比如半夜重启）。重启之后，它靠三招恢复现场：

🔁
重建队列

从持久化存储里把待办队列重新搭起来。

🔍
扫描可恢复的 Run

找到被中断的 Run，逐个评估：还能不能接着做？

🧭
逐个消费恢复计划

按恢复决策执行：能自动接着做的自动恢复，不能的进人工复核。

💡
关键洞察

"释放"不是可选项，而是每个出口的必经程序。飞机备降后腾空跑道、系统终止后释放槽位——把"绝不泄漏"刻进每个退出路径，系统才不会慢慢被掏空。

危险副作用，绝不重复执行

火灾报警响过后最怕什么？怕各层"自作主张重跑"。系统靠 Module 5 的 Checkpoint 与结果分类来兜底：已确认成功的不重做，未知的进人工。

07

从可用，到可度量、可观测、可路由

基础能力跑通之后，一个 Agent 服务还要回答三个问题：跑得好不好？能不能一眼看见？模型调用靠不靠谱？这三个方向把项目从 demo 推向了可面试的 agent infra。

A · 执行质量评测闭环：跑完不是终点

任务跑完了，系统该怎么知道自己「跑得好不好」？如果只看「有没有输出」，很多隐患会被掩盖：排队是不是太频繁？模型成本花在哪？有没有危险工具被放行？Cache 命中率有没有下降？

方向 A 做了一件事：把已经落库的数据重新算一遍指标。既然模型调用事件、工具执行、资源准入决策、Diff、Artifact、输出片段都已经写进数据库，评测就不需要再额外埋点采集，直接读现有表即可。

📊

行业标配

Token、成本、延迟 P95、成功率、完成度——证明「我懂 agent infra 的常规指标」。

🛡️

护城河

背压触发率、无人值守率、危险拦截率、cache 命中率——这些是控制面独有的。

🧮

聚合器

EvaluationAggregator 纯读取现有表，零新增采集。

📈
面试可讲

「我没自己造一套采集，而是复用了 Pi 已经发出的 model_completed 事件，对齐 OpenTelemetry GenAI Semantic Convention。这样既保证指标准确，又避免侵入 agent 执行路径。」

B · 观测驾驶舱：一眼看见执行质量

指标算出来了，还要让人一眼看懂。方向 B 做了一个独立的观测页 /observe：它和任务操作台 / 完全解耦，只读，不会误触任务。数据来自同一个 GET /eval 端点，支持按租户过滤。

关键设计是「用图表说话，而不是堆数字卡片」：

🍩
任务状态环形图

COMPLETED / FAILED / RUNNING / QUEUED 的占比，中心显示任务总数。

📶
租户对比条形

各租户的任务规模 + 成功率横向对比，立刻看出哪个租户质量差。

🌊
资源背压堆叠条

START 和 QUEUE 的比例，叠加背压触发率 / 观测失败率。

📋
任务明细表

租户徽章、状态徽章、Token、成本、排队耗时、危险拦截数。

👁️
面试可讲

「观测页走独立路由 /observe，不动现有任务操作台。注入走 HarnessHttpApi 的可选参数，没有改 HarnessApplication 的构造。这是最小侵入原则：观测只是旁路，不能影响主链路。」
