外面的世界

模型、沙箱和 GPU——你的任务真正「活」的地方，大多在这台电脑之外。

模型住在外面

前几讲，我们一直在系统内部转圈。这一讲推开门——你的任务真正「活」的地方，大多在你电脑之外。

把 模型 想象成一家「随时可调用的外部专家公司」：你把 请求 写成请柬，送到它门口（ 端点 ），它回一封 响应 。你的代码从不需要知道专家住在哪、怎么思考——模型不在本机，任务照样能跑。

Pi 是连接它的 Agent Runtime ： Agent loop 和 工具调用 跑在你这一侧，模型回答从外面回来。

沙箱：真的隔离，不是假装

沙箱不是纸面承诺——它真的是一台 容器 。每个任务都会被请进一间「一次性隔离工作间」：只挂进它自己那份材料（workspace），墙是只读的，没有网线，没有管理员钥匙。

盒子的模板叫 镜像 ，创建、查看盒子靠 Docker ；而真正让盒子跑起来的引擎叫 runtime 。

development 本地调试专用：不做隔离，可联网。它从不是多租户生产档。
default 默认生产档： runsc （ gVisor ），只读 + 断网。
restricted-egress 受控出口档：预留，尚未接入代理，当前拒绝直连公网。
strict 最严档：预留，必须路由到独立 microVM Provider。

这些档位叫 profile 。下面这份施工图纸，把工作间的每项硬性要求编译成 Docker 能听懂的参数——这是真实代码里的原样片段：

CODE 

        const args: string[] = [
            "run", "--detach", "--rm", "--name", name,
            "--user", `${this.config.userId}:${this.config.userId}`,
            "--read-only", "--cap-drop", "ALL",
            "--security-opt", "no-new-privileges", "--pids-limit", "128",
            "--workdir", "/workspace", "--mount",
            `type=bind,src=${workspacePath},dst=/workspace`,
            "--tmpfs", "/tmp:rw,noexec,nosuid,size=64m",
            "--network", networkMode === "none" ? "none" : "bridge",
        ];
大白话

开始建工作间：后台运行、任务结束时自动整个拆除、名字用这次任务的。

用普通用户身份进去——不是管理员，没有钥匙。

墙是 只读 的；把 特权清单 直接撕光（cap-drop ALL）。

禁止再申请任何新特权；最多同时跑 128 个 进程 （pids-limit 128）。

工作目录固定为 /workspace——也就是挂进来的材料箱。

把宿主电脑上的工作区文件夹「插」进来当 U 盘（ bind mount ），只有这一份。

临时目录放内存盘（ tmpfs ）：能写，但禁止执行、禁止挂载，限 64MB。

网络： network none ——工作间没有网线，出不去也进不来。

每一条参数都在回答同一个问题：如果攻击者使坏，他能碰到的东西有多小？答案被压到只剩「他自己那份材料」。

配置 ≠ 事实：先验货，再开工

施工图纸说「用防弹玻璃」。但你不亲手摸一摸，怎么知道装上去的不是普通玻璃？

所以每次沙箱启动后，系统会用 inspect 去「验货」：读真实容器上实际生效的 runtime。这一步的意义是——配置只是 证据 要验证的「意图」，而不是事实本身。

🛡️
防御不静默降级（fail closed）

配置写 runsc，就绝不允许 runc 悄悄顶上。 静默降级 是敌人；隔离是承诺，承诺必须被检查——inspect 对不上就 fail closed 。宁可任务不跑，也不假装安全。

这段真实代码就是「验货」本身——DockerRunscRuntimeAdapter 每次启动后都这么做：

CODE 

        const result = await commands.run([
            docker, "inspect", "--format", "{{.HostConfig.Runtime}}", containerName,
        ]);
        const observedRuntime = result.stdout.trim() || null;
        const verified = result.exitCode === 0 && observedRuntime === this.runtime;
大白话

向 Docker 发一个验货请求：读取这个真实容器的 HostConfig.Runtime 字段——它记录「实际用的是哪个 runtime」。

把读到的值前后空白清干净，这就是「事实」里的 runtime 名字。

只有当命令成功返回、且事实确实等于我们要求的 runsc，才盖上「已验证」的章。

事实与意图一致，任务才准开工；不一致，直接 fail closed。这套代码同时在沙箱一侧的 OciSandboxSpecCompiler 里再拦一道：profile 必须配 runsc，否则抛错拒绝执行。

共享电表：GPU 与显存

还记得前几讲的 GPU 吗？整栋楼的人共用一块「电表」——多租户共享 显存 和带宽。

于是任务开始前，系统先「读电表」： 观察者 采集 资源快照 ，再送进 准入 服务，由策略盖章：放行（START）或排队（QUEUE）。

这是真实策略代码里的一个分支——资源极度紧张时怎么办：

CODE 

            case "CRITICAL":
                return this.createDecision(
                    input,
                    "QUEUE",
                    "RESOURCE_CRITICAL",
                );
大白话

当电表读数进入「红色警戒」（CRITICAL）时……

策略给出决定：

这个任务先 QUEUE （排队），

原因登记为 RESOURCE_CRITICAL：资源极度紧张。

绝不硬跑，也绝不悄悄降低标准。

START RESOURCE_NORMAL —— 电表正常，放行。
START RESOURCE_BUSY_TENANT_AVAILABLE —— 忙，但本租户还有名额。
QUEUE RESOURCE_CRITICAL —— 极度紧张，排队。
QUEUE RESOURCE_UNKNOWN —— 读数失败、不确定，排队。
QUEUE GLOBAL_CONCURRENCY_LIMIT —— 全局并发（同时跑的任务数）满了。
QUEUE RESOURCE_BUSY_TENANT_LIMIT —— 本 租户 已有任务在跑，先让位。
QUEUE RESOURCE_OBSERVATION_FAILED —— 连电表都读不到，宁可排队也不盲跑。
🔍
诚实边界：显存准入是「目标」，不是「已完成」

本演示用的是外部模型 API，没有接 vLLM 的 metrics ，也没有 nvidia-smi 的真实读数。上面这套 START/QUEUE 逻辑是真实代码，但「显存感知调度」要在装有真实 GPU（如 A6000）的机器上、接上真实观察数据，才算验证过。

隔离不是写出来的，是打出来的

这些不是纸面推演——真机上对 runsc 沙箱跑过一轮攻击测试。每一路攻击都被挡在沙箱里，全部 PASS。

🧱

跨租户文件 / Secret

想读别的租户的 workspace 或 Secret ？根文件系统只读、唯一挂载只有自己那份材料——PASS。

🗺️

宿主路径

想摸 宿主 机上的文件？特权清单撕光、禁止新特权，逃逸窗口被焊死——PASS。

🌐

网络

network none：沙箱没有网卡，出不去也进不来，想外传数据没门——PASS。

🧵

PID / tmpfs

最多 128 个进程、/tmp 禁止执行程序，想藏后门难上加难——PASS。

💀

沙箱被杀 → LOST

攻击把沙箱打死？任务标记 LOST （丢失），绝不伪装成功——PASS。

真正拦住攻击的，是 gVisor 那个「安检员」——每个 系统调用 都被拦下来检查。外面世界的危险，到此为止。
