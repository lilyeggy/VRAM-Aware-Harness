聪明的机制

为什么 AI 不能"说做就做、崩了就重跑"——记账、副作用分类、Checkpoint，以及拿不准就拒绝。

为什么执行前要"记账"？

AI 说"帮我干活"的时候，它面对的不是沙盘，而是真实的外部世界：文件真的会被改、请求真的会发出去、钱真的会动。所以系统有一条铁律——副作用发生之前，先记账。

这本账叫双复写记账本：动手前先写下"我准备做X"（工具的复写联），做完了再盖一枚"已完成"章。外部世界一旦被改动，就没有撤回键。

1

工具请求进来

→
2

先记账：PREPARED（复写联）

→
3

执行工具

→
4

成功 → 盖"已完成"章 SUCCEEDED

→
5

崩溃或未知 → 红牌，请人来确认

崩溃了也不慌：翻开账本，盖过章的绝不重做；没盖完又危险的那笔，必须等人点头。这份"先记录、后动手"的坚持，就是系统能恢复的根本原因。

记下这支工具声明的状态之外最重要的东西——副作用类型（下一屏讲三种墨水）。

状态先写成 PREPARED：登记好了、还没动手。

关键一步：先存进账本，再执行工具——顺序绝不能反。

三种墨水：副作用的分类

每支工具进场前都要声明自己是哪一类副作用。账本上有三种墨水颜色，决定它享受什么待遇——能不能自动重试，还是永远要人拍板。

📖

READ_ONLY · 蓝笔

只看不改：读文件、查配置、问状态。重复执行一百次也不会改变任何东西——像翻书翻到同一页。

🔄

幂等IDEMPOTENT_WRITE · 绿笔

重复执行结果和第一次完全相同：盖两次章，还是同一个章。所以系统允许安全重试。

🔥

UNKNOWN_EFFECT · 红笔

可能改外部系统、可能花钱、可能发消息——谁也没法保证重复执行无害。这是热炉子：不确定，就绝不自动重试。

分类决定待遇：蓝笔绿笔可以自动重放，红笔永远要人拍板。真实代码里，这三种墨水就是一组简单的定义：

真实代码 

export type ToolEffect = 
    | "READ_ONLY"
    | "IDEMPOTENT_WRITE"
    | "UNKNOWN_EFFECT";
大白话

给"工具效果"定义一组类型。

只读：只看不动。

幂等写入：重复做结果一样。

未知副作用：后果不明，危险。

这段代码出自 src/tools/tool-execution.ts。注意：分类只是"声明"。系统不会因为一支工具自称"幂等"就完全信任它——真正的安全，还要看后面几屏的机制。

Checkpoint：账本上的装订线

光有账本还不够——每次崩溃都从第一页开始恢复太慢了。所以每隔一段，系统会在账本上画一条装订线，这就是 Checkpoint：到这里为止，一切都确认过。

恢复时从最近的装订线接着走：已经盖过"已完成"章的记录直接复用结果，绝不重做。系统还把"成功结果"和"装订线"两笔写入放进同一个事务里——绝不会出现"账本说成功、却没有装订线"的中间状态。

1
找到最近的装订线

从数据库里读出这个任务最新的 Checkpoint——这是 CheckpointStore 干的活。

2
检查装订线之后有没有"红笔未盖章"

把崩溃时还没完成的工具记录翻出来，逐个问：能安全重放吗？

3
两条路

全部安全 → AUTO_RESUME 自动继续；有红笔 → MANUAL_REVIEW，请人来做决定。

来看真实代码里的恢复决策——只要发现一条不能安全重放的红笔记录，就立刻转人工：

真实代码 

    if (unsafeExecution !== undefined){
        return {
            action:"MANUAL_REVIEW",
            reason:"UNSAFE_TOOL_EFFECT",
            blockingToolExecutionId:unsafeExecution.id,
        }
    }
大白话

只要找到哪怕一条不能安全重放的记录……

恢复决策就是：

动作：交给人工审查。

原因：存在不安全的工具副作用。

并且指明是哪条记录挡住了自动恢复——人一看账本就知道该查哪里。

决策打包完成。

结束。

🔥
热炉子警告

想象厨房里一锅"可能已经在烧的红烧肉"：账本上写着"准备开火"，但没有"已完成"章。肉可能在锅里炖着，也可能还没下锅——这时盲目再开一次火，就是重复扣款、重复发钱。正确做法：让人来看一眼。

Fail-closed：拿不准就拒绝

热炉子哲学：不确定炉子烧没烧，就绝不碰开关。系统的默认答案是拒绝，而不是"先试试看"。这份谨慎体现在每一道关口：

🧩
策略与 profile 冲突

Provider 配置与策略要求的 profile 不一致 → 直接抛错，不硬着头皮建沙箱。

💾
磁盘配额无法落实

bind mount 技术上无法强制磁盘配额 → 干脆拒绝执行，而不是假装限了。

🔍
Runtime 证据不符

Docker inspect 发现实际 runtime 和声明不一致 → 标记 FAILED，先销毁容器再报错。

第三个例子最有代表性——"证据"和声明不符，就按失败处理，绝不睁一只眼闭一只眼。看真实代码里第一个例子怎么拒绝：

真实代码 

        if (policy.resourceLimits.diskMiB !== null) {
            throw new Error("Container bind mount 无法强制磁盘配额，拒绝执行");
        }
大白话

如果策略要求了磁盘配额……

而这套实现根本没法强制配额——那就直接抛错：拒绝执行。

结束。

💡
这是整个系统最重要的工程品格

fail-closed（拿不准就关门），而不是 fail-open（拿不准就放行）。对 AI 干活来说，放行一次可能真金白银地烧掉钱；拒绝一次，最多浪费一次重试。

事件证据链：崩溃后还能回放

除了账本，系统还留了三样东西，组成一条完整的证据链：RunEvent（流水账）、Checkpoint（装订线）、Diff（改过页面的复印件）。重启之后，任务可以像看监控回放一样，把出事前的事重新走一遍。

但回放不等于放行：恢复的任务必须重新过一遍身份、策略、沙箱、资源准入。

🎬
RunEvent

每一个事件的流水记录，崩溃后按顺序回放。

📌
Checkpoint

装订线：标出"确认过的最新位置"，恢复从这里继续。

📄
Diff

改动前后的对比快照，证明"到底改了什么"。

把这一幕串起来，就是一次完整的"崩溃后复活"：

🧭
任务
📒
事件账本
🛂
准入检查
📌
恢复点
任务运行到一半，系统崩溃了

这套"证据链 + 重新准入"的设计，让系统既能看到过去发生了什么，又绝不信任"上次的状态还能直接用"。
