安检口：身份与隔离墙

想进贵宾室，先过安检。系统的 身份 是从密钥派生出来的——请求体里自称的租户，一个字都不信。

🏢

Tenant · 租户

一个客户/团队一个独立空间。所有数据按它 隔离，别的租户看不见。

📁

Workspace · 工作区

每个项目一块受管理的目录，路径由服务器生成，客户端不能乱填宿主机路径。

🎫

密钥 · 安检凭证

密钥不直接存数据库，只存哈希。查得到才算数，查不到就拒绝。

真实代码 

    authenticate(rawKey: string): RequestPrincipal | null {
        const row = this.db.query<CredentialRow, { keyDigest: string }>(`
            SELECT id, key_digest AS keyDigest, subject_id AS subjectId,
                tenant_id AS tenantId, scopes_json AS scopesJson,
                created_at AS createdAt, revoked_at AS revokedAt
            FROM api_credentials
            WHERE key_digest = $keyDigest AND revoked_at IS NULL;
        `).get({ keyDigest: digest(rawKey) });
        if (row === null) return null;
大白话

「验证」：拿客户端递过来的密钥，查出它的身份。名字就叫 authenticate（认证）。

先把密钥做一次哈希处理，然后去数据库里找匹配的记录。

找到就把它的身份信息取出来：属于谁、属于哪个租户、带哪些权限。

查询锁定在两件事上：只按密钥指纹找，而且只找没被吊销的。

执行查询，把「密钥指纹」作为查找条件传进去。

一条都没查到（密钥错了或已吊销）就返回「没有这个人」，直接拒绝。

注意：身份全部来自查表结果，而不是 请求体里客户自己报的。

验证通过后，「登机牌」长这样：你是谁、属于哪个租户、能做什么（ 权限范围）。

真实代码 

export interface RequestPrincipal {
    readonly subjectId: string;
    readonly tenantId: string;
    readonly scopes: readonly string[];

塔台：Run 与 Attempt

Run 是「一次用户任务」，Attempt 是「那一次实际执行」。任务先进入 队列排队，轮到才执行；失败 重试 = 新的 Attempt，绝不覆盖原任务。

✈️

Run · 一次任务

乘客的行程单：用户想要什么、属于哪个会话、当前什么状态。任务可以对应很多次执行。

🛫

Attempt · 一次执行

航班的一次具体起飞：尝试编号、用了哪个沙箱、什么状态、失败原因。重试 = 新 Attempt。

大白话

「给一次执行点火」的函数：把 Attempt 从等待状态推进到运行状态。

参数一：这次执行本身（Attempt）。

参数二：开始时间。

参数三：当时生效的那版规则——策略快照的编号。

参数四：分配好的沙箱（执行舱）编号。

规矩很严：只有还处在「等待中（PENDING）」的 Attempt 才允许启动。

否则直接报错——状态机不许乱跳。

收尾：点火前检查完毕。

停机坪：执行舱与大脑

沙箱是被隔离的「乘客区」，分三个档位，档位由 策略决定；Pi 是真正动脑的机长。谁创建谁？看下面这根接力棒。

🧪

只给本地开发用，跑在自己电脑上，不隔离也安全——因为根本没有别人。

大白话

沙箱服务对外承诺的「合同」——接口。任何提供者都得按这个来。

「创建执行舱」：开舱前必须说清楚三件事。

这个舱给哪个任务用（runId）。

挂在哪个实例下（instanceId）。

舱门对准哪块工作区目录（workspacePath）。

以及舱内要遵守什么规则（policy）——沙箱不是想怎么开就怎么开。

开好了，交回一个操作手柄（SandboxHandle）。

「销毁执行舱」：用完必须收掉，防止垃圾舱残留。

机库：飞行记录仪与记账本

每一次执行、每一步动作，都作为事件写进 SQLite，长期 持久化保存。

0001 RUN_CREATED 任务建档
0002 RUN_QUEUED 进跑道排队
0003 TOOL_STARTED 地勤开始装货（调用工具）
0004 TOOL_COMPLETED 工具完成，结果入账
0005 RUN_COMPLETED 任务收官

每条事件都带着递增的 序号，只 追加、不可 篡改。改动任何一步，后面的时间线就对不上了；网络抖动导致重复上报时，系统靠稳定编号 去重，只记一次。

你的客户要求「只有付费团队能调用敏感工具」。现在的架构是：密钥上挂着权限范围（scope），工具层只负责执行。第一步该改哪里？

Aha！每个主角只干一件事

身份只回答「你是谁」，控制面只管调度，沙箱只负责隔离，记账本只负责记录。把职责拆开、各管一摊，工程师叫它「关注点分离」（separation of concerns）。你越早用这个眼光看系统，就越能对 AI 说出：「这个逻辑放在 X 而不是 Y。」
