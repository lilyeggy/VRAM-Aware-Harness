数据如何流动

Command、Event、State 三种信息，怎样落进 SQLite，又怎样回放——跟着一封信走完整个系统。

三种信息：想干嘛、发生了什么、现在是什么

系统里跑一次任务，会产生三种信息——就像寄一封信：快递单上的指令、每一站盖下的邮戳、信件此刻所在的站点。

把它们记成三个词：Command、Event、State。

✉️

Command · 想让它干嘛

快递单上的指令。用户说「帮我把这个任务跑通」，指令带着目标进入系统。

📮

Event · 刚刚发生了什么

每一站盖下的邮戳：「已排队」「工具已调用」……只追加，不改写。

📍

State · 现在是什么

信件此刻在哪一站。最新状态一查就知，但它只反映「现在」。

快照 vs 历史：一张状态牌 + 一本邮戳册

系统同时维护两张表：快照表 agent_runs 是「当前状态牌」，追加式表 run_events 是「邮戳合订本」。

为什么不能只留一本？因为「现在」会被不断覆盖，而「过去」必须完整保留——排障、回放、审计都靠它。

🪧

agent_runs · 当前状态牌

每封信只占一行，永远是最新状态。像快递页顶部的最新动态，一查就知。

📔

run_events · 邮戳合订本

每一站一条记录，按 sequence 编号，只增不改。像钉在册子里的邮戳，一张张往下加。

PLAIN ENGLISH

状态跳转不是随意的，得遵守规则表——这就是「状态机」。

定义一个「盖章检查员」：想从 A 状态跳到 B 状态时，先叫他来验票。

检查员读规则表，看看这个跳法在不在许可名单里。

不在？直接抛错：报出「从哪跳到哪不合法」——邮戳不能乱盖。

合法才放行，状态才能往前走。

QUEUED → RUNNING 排队中 → 资源到位，开始跑（也可能被打断）
RUNNING → WAITING_TOOL 运行中 → 停下来等工具结果
WAITING_TOOL → RUNNING 工具结果回来了 → 继续跑
RUNNING → COMPLETED / FAILED 正常完成，或失败
INTERRUPTED → QUEUED 被打断 → 重新排队
COMPLETED / FAILED → 终点 到终点后不再跳转

决策也要留证据

任务能不能开始，由策略决定：放行（START）还是排队（QUEUE）。

每一次决策，连同「当时的资源快照」和「给出的理由」，一起写进 policy_decisions 表。

建一张「决策登记簿」，每次决策占一行。

每条决策有自己的身份证号（主键）。

记下这是哪封信（哪个任务）的决策。

结论只有两种：放行或排队——别的值，数据库直接拒收。

还必须写明理由代码：资源正常？全局并发到顶？——证据齐全。

💡
历史决定不能事后篡改

改策略只影响「未来的决策」——已经落库的 START / QUEUE 记录纹丝不动。这正是审计信任的基础：当时用了哪个资源快照、给了什么理由，永远查得到。

落库要像医院病历一样可靠

RunStore 把「更新状态」和「追加事件」放进同一个事务：要么都成功，要么都不发生。

SQLite 再用去重键配唯一索引——同一个事实重复投递，第二次会被安全忽略。

ℹ️
事务的意义：两张表必须同步

如果状态改了、事件没记上，重启后就无法解释「它怎么走到这的」。所以状态牌和邮戳册被绑进同一笔事务——原子性是它们之间的保险绳。

tool:${event.toolCallId}:finished 同一个工具调用只能有一个最终结果——成功失败共用一把钥匙，后到的被忽略
tool:${event.toolCallId}:started 同一个工具调用的开始，只记一次
model:${event.modelCallId}:started 同一次模型调用的开始，只记一次
model:${event.modelCallId}:finished 同一次模型调用的结束，只记一次

任务结束，旅程可以完整回放

任务落库后，run_events 里的事件按sequence 编号——像一本按时间钉好的邮戳册，随时可以回放。

用户看到的「结果」，其实是四样东西拼起来的：最终状态 + 事件时间线 + 工作区 Diff + 产物 Artifact。

PLAIN ENGLISH

邮戳册的表结构：每盖一个戳，就追加一行。

每个邮戳有自己的唯一编号。

记下它属于哪封信（哪个任务）。

sequence 是邮戳的顺序号，从 1 开始，必须大于 0——回放就靠它排序。

盖戳的时间、事件类型、附带数据（payload），一行齐全。

📜

事件时间线

run_events 里的全部邮戳：每一步都查得到。

🔀

工作区 Diff

📦

产物 Artifact

不可变成果快照：事后随时可以核对。
