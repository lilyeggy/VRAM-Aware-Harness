§3 六个算法的真实实现

3.1 claimNext()：轮转 + 原子占位

claimNext(): QueuedRun | null {
    // ① 全局 slot 已满，直接放弃
    if (this.activeTenantByRunId.size >= this.config.maxActiveRuns) return null;

    const tenantsToInspect = this.tenantOrder.length;
    for (let i = 0; i < tenantsToInspect; i++) {
        const tenantId = this.tenantOrder.shift();          // ② 取轮转队首
        const q = this.queuesByTenant.get(tenantId);
        if (!q || q.length === 0) { this.queuesByTenant.delete(tenantId); continue; }

        // ③ 该租户已达单租户上限 → 放回队尾，不阻塞别人
        if (this.getActiveTenantRunCount(tenantId) >= this.config.maxActiveRunsPerTenant) {
            this.tenantOrder.push(tenantId); continue;
        }

        const run = q.shift();
        // ④ 会话串行：同一对话的前一个 Run 还活着 → 原样放回
        if (run.sessionId && this.hasActiveSession(run.sessionId)) {
            q.unshift(run); this.tenantOrder.push(tenantId); continue;
        }

        if (q.length > 0) this.tenantOrder.push(tenantId); else this.queuesByTenant.delete(tenantId);

        // ⑤ 选择与占用 slot 必须在同一个同步动作里完成
        this.activeTenantByRunId.set(run.runId, run.tenantId);
        if (run.sessionId) this.activeSessionByRunId.set(run.runId, run.sessionId);
        return run;
    }
    return null;   // 有等待任务，但所有租户都到自己上限
}
为什么这么写不这么写会发生什么
② 轮转环而非全局 FIFOA 连续提交 A1..A100 时，B1 要等 100 个任务 → 永久饥饿
③ 达上限的租户放回队尾如果 continue 前不 push 回去，该租户会被错误地退出轮转
⑤ 选 + 占同一动作分离后多个调度尝试会同时看到空闲容量 → 超额启动

3.2 drain()：单飞与重入

drain(): Promise<CoordinatorResult[]> {
    this.drainRequested = true;                    // 每次都表示「状态可能变了」
    if (this.drainPromise !== null) return this.drainPromise;   // 复用 in-flight
    this.drainPromise = this.runDrainLoop();
    return this.drainPromise;
}

runDrainLoop() {
    const results = [];
    try {
        while (this.drainRequested) {                 // 执行期间被再次请求 → 多跑一轮
            this.drainRequested = false;
            results.push(...await this.drainOnce());
        }
        return results;
    } finally { this.drainPromise = null; }
}
已知副作用：并发 tick 共享同一个会被 reject 的 promise，于是每个等待者各调一次 onError —— 实测同一次失败被上报 9 次（去重后 1 条）。失效不致命，但计数语义不准。

3.3 reconcileQueuedRuns()：TOCTOU 对账

reconcileQueuedRuns() {
    for (const run of reader.listQueuedRuns()) {        // DB 里所有 QUEUED
        const waitedMs = nowMs - Date.parse(run.updatedAt);

        // ① 超 TTL → 先落库 FAILED，再摘内存队列（顺序不可反）
        if (queueTtlMs !== undefined && waitedMs > queueTtlMs) {
            try { this.runService.failQueuedRun(run.id, "QUEUE_TIMEOUT", …); }
            catch (e) { console.error(…); continue; }   // 落库失败 → 保留，下轮重试
            this.scheduler.removeQueued(run.id);
            this.pendingResumeByRunId.delete(run.id);
            timedOut.push(run.id); continue;
        }

        // ② DB 是 QUEUED 但不在内存队列 = 孤儿 → 重新入队
        if (queuedInMemory.has(run.id)) continue;
        this.scheduler.enqueue({ …, enqueuedAt: run.updatedAt });   // TTL 时钟跨重启累计
        requeued.push(run.id);
    }
}

孤儿窗口来自 claimNext() 与 release + re-enqueue 之间：此时 Run 已离开内存队列，但 DB 仍是 QUEUED。若在这两步之间崩溃，只有对账能把它捞回来。

顺序的关键：必须先 failQueuedRun 落库成功，再 removeQueued 摘内存。反过来一旦落库失败，这个 Run 既不在队列、也不是终态 —— 完全消失。

3.5 canAutomaticallyReplay()：故意保守

canAutomaticallyReplay(status, effect): boolean {
    if (status !== "PREPARED") return false;     // 已有确定结果就不需要重放
    switch (effect) {
        case "READ_ONLY":        return true;    // 无副作用，重试安全
        case "IDEMPOTENT_WRITE": return false;   // ← 见下方注释原文
        case "UNKNOWN_EFFECT":   return false;
    }
}
// 源码注释原文：
// “写入被声明为幂等”本身不足以证明外部系统会使用稳定幂等键。
// 在 ToolExecution 持久化并校验真实幂等证据前保持 fail closed。

注意枚举里没有 NON_IDEMPOTENT —— 它被 UNKNOWN_EFFECT 吸收了。系统关心的不是"这个工具是不是幂等的"，而是"我当前能不能证明这次执行的副作用状态"。

3.6 ToolGateway 两阶段

prepare(input): ToolPrepareDecision {
    this.policyGuard?.assertAllowed(input);                    // ① 策略否决先于一切
    const history = this.store.getByToolCall(input.runId, input.toolCallId);   // ② 稳定业务键
    if (history === null) { this.store.prepare(PREPARED); return PREPARED; }
    switch (history.status) {
        case "SUCCEEDED": return { kind:"REUSE", result: history.result };      // 副作用已发生，直接复用
        case "FAILED":    return { kind:"DENIED", reason:`工具执行失败:…` };
        case "PREPARED":  return canAutomaticallyReplay(history.status, history.effect)
            ? { kind:"PREPARED", execution: history }   // ← 复用原记录，不能再 prepare（唯一约束）
            : { kind:"DENIED", reason:`不允许自动重放：${history.effect}` };
    }
}

complete(input, execution, outcome) {
    if (!outcome.ok) { this.store.fail(FAILED + errorMessage); return; }
    const checkpoint = { id, runId, toolExecutionId: execution.id,
                         runtimeSessionRef, lastEventSequence, createdAt };
    this.store.completeWithCheckpoint(SUCCEEDED, checkpoint);   // ③ 结果与 Checkpoint 原子提交
}
Checkpoint 保存的是「下一次可以安全继续所需的持久信息」——runtimeSessionRef + lastEventSequence，不是进程内存快照。恢复时从这个 sequence 继续追加事件，所以 Day7 的 sequence 能保持 1..8 连续。

§7 不变量与竞态窗口

必须恒成立的不变量

  • 同一 Run 的 sequence 连续且唯一（UNIQUE(run_id, sequence)）
  • QUEUED 的 Run 要么在内存队列，要么可由 reconcileQueuedRuns 补入
  • 每个 RUN_STARTED 之前必有一条 policy_decisions
  • 每个 slot 的占用与释放成对；重复释放幂等
  • 沙箱在 finally 中终止；异常路径不留 ACTIVE
  • QUEUED 的 Run 一旦转终态，必须同时离开内存队列
  • Attempt 从创建起就绑定不可变 policySnapshotId

已知竞态窗口

  • claimNext ↔ release/re-enqueue：中间崩溃 → 孤儿 QUEUED，靠对账补回
  • QUEUED→RUNNING 写入 ↔ 用户 interrupt：真机抓到 INTERRUPTED → RUNNING 非法转换毒丸（docs/known-issues A4）。现由 executeQueuedRun 的两处兜底安全放弃启动
  • drain 单飞 ↔ 多 tick 等待：一次失败被 onError 记 N 次（实测 9）
  • 会话串行：同 session 的 Run 不允许并发，但跨 session 无此约束
必须诚实标注的三条边界
  • development profile 的 runtimeEvidence.verificationReason 自带声明「仅开发/测试生命周期证据；不代表内核隔离」。
  • 本机无 Docker daemon / runsc，smoke:container 系列未执行；真实隔离证据必须在 Linux Docker + runsc 上产生。
  • A6000 真机对照实验未完成，所有性能结论不成立。本次证明的是控制面正确性。
