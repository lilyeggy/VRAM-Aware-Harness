VRAM-Aware Harness 的虚拟机技术讲解

这个项目里，每一次 Agent 执行"不可信的命令"（比如跑 shell、改文件），都不在宿主机上直接执行， 而是在一台用完即毁的小型虚拟机里执行。这页讲清楚：这台虚拟机是怎么造出来的、它由哪几块拼成、 这几块怎么配合把"开机 → 执行 → 导出产物 → 销毁"跑通。

0. 先用 Agent 的语言理解

把它类比成你熟悉的东西：

你的 Agent 视角

一次 Run = 一次任务执行。Run 里 Agent 会调用工具：bash、读写文件。

问题是：这些工具调用不可信。模型可能被提示注入，可能跑出 rm -rf，可能读别人的文件。

所以要给每个 Run 配一个沙箱（Sandbox）：工具调用只能在沙箱里发生，沙箱出事不能殃及宿主和其他用户。

沙箱的三种档位

档位隔离靠什么本项目用途
容器（runc）共享宿主内核，靠命名空间划线已弃用
runsc（gVisor）用户态"翻译层"拦截系统调用开发 / 默认档
microVM（Firecracker）CPU 硬件虚拟化，每个 Run 一个独立内核strict 档（生产）
本文只讲最右边那一行：microVM。 它的核心特点是：Run 里的命令跑在一个有自己内核的小电脑里， 这台"小电脑"由宿主机上的 KVM（Linux 的硬件虚拟化接口）和 Firecracker（一个极简的虚拟机程序）造出来。 对 Agent 来说，它的接口长这样： 
sandbox = create(run, workspace, policy)     # 开一台 VM，挂上这个 Run 的工作区

后面所有内容，都是在回答"这三行 Agent 看到的调用，背后要拼哪些零件"。

2. 每个模块的技术路线与具体实现

每个模块按同一个结构讲：它解决什么问题 → 技术选型 → 我们怎么实现 → 踩过的坑（这些坑解释了为什么代码长成现在这样）。

M1 · Firecracker microVM 与 Guest 镜像

要解决的问题：我们需要一台"独立内核、可以随便执行命令、用完就扔"的机器，启动要快，资源占用要小。

技术选型：

  • KVM：Linux 内核自带的硬件虚拟化接口（依赖 CPU 的 VT-x/AMD-V）。它让一个进程能"隔出"一台假电脑，CPU 指令直接在硬件上跑，只在敏感操作时才陷入宿主。访问入口是 /dev/kvm。
  • Firecracker：AWS 为 Lambda 做的极简 VMM（虚拟机监视器）。它只模拟很少的设备（串口、块设备、vsock），所以启动快（官方口径约 125ms 裸启动）。Firecracker 本身是一个普通的宿主进程，它通过一个 HTTP API（Unix socket）接收配置。

我们怎么实现：

  • 驱动 FirecrackerSandboxDriver 用 HTTP 调 Firecracker API 完成配置：/boot-source（内核与启动参数）→ /drives/rootfs（系统盘）→ /drives/workspace（工作区盘）→ /vsock（通道）→ /machine-config（CPU/内存）→ InstanceStart（开机）。
  • Guest 镜像由 build-guest-rootfs.sh 生成：下载固定版本的 Alpine Linux（3.20.3，带 sha256 校验）作为 rootfs，装入 socat（vsock 桥接工具）和我们自己的 guest/agent，并写 /etc/inittab 让它开机自启。
  • 启动参数里 init=/sbin/init，console=ttyS0（串口保留给内核日志，不再用于命令）。
  • 硬约束：VM 没有网卡。策略里 allowNetwork=true 会被 fail-closed 直接拒绝（三层都有检查：Provider、驱动、产品边界）。
坑 · 为什么不能直接跑 firecracker 命令？ 早期做法是直接 spawn firecracker，socket 放在共享的 /tmp。问题是：Firecracker 的 API 没有鉴权，同机其他用户可以抢先连上它、下发任意磁盘路径。这直接催生了 M2。

M2 · jailer：给 Firecracker 进程上锁

要解决的问题：VM 里的 root 被 KVM 关着，无害；但 Firecracker 进程本身是宿主上的普通进程。如果它被攻破，攻击者拿到的是宿主上的一个进程，而不是一台虚拟机。

技术选型：Firecracker 官方随包提供的 jailer，这也是 AWS Lambda 的生产姿势。它做四件事：

降权每台 VM 分到一个专属 UID/GID（我们的范围 20000–29999）。
chroot把 Firecracker 关进只含必要文件的目录，看不见宿主其他文件。
cgroup 限额内核级限制 CPU 配额与内存上限，由宿主强制，VM 内 root 改不了。
私有目录socket、磁盘副本都放在 chroot 内，路径随机，不再暴露在 /tmp。

我们怎么实现：

  • 分支 useJailer：创建前先跑 checkJailerPrereqs（jailer / firecracker 二进制存在、KVM 可访问），不通过直接报错。
  • 把内核、rootfs、工作区盘复制进 chroot，再 chown -R uid:gid，让降权后的 Firecracker 能读写。
  • cgroup 参数由纯函数 buildJailerCgroupArgs(vcpu, memMb) 生成：cpu.max = vcpu×100000 100000；memory.max = (guest内存 + 64MiB VMM底噪)。
坑 · 为什么内存限额要多加 64MiB？ Firecracker 自己也要占一点内存。如果 cgroup 上限 = guest 内存，Firecracker 会被自己的 cgroup OOM 掉。所以 cgroup 必须严格大于 guest 内存。
坑 · jailer 的 /run 是独立 tmpfs。 把 socket 或快照放在 chroot 的 /run 下，宿主侧完全访问不到。所以所有需要跨边界访问的文件都放 chroot 根目录。

M3 · 私有目录与分配器（UID / CID / 运行目录）

要解决的问题：多台 VM 同时存在，每台要有自己的"身份证件"，互不冲突、互不可见。

资源实现作用
运行目录VmRunDirectoryManager：<runtimeRoot>/<sandboxId>，权限 0700；sandboxId 只允许 [a-zA-Z0-9-] 且 ≤64 字符放 pidfile、磁盘副本、socket；别的用户进不来
UID/GIDVmUidAllocator：20000–29999 中取最小未用值每台 VM 的 Firecracker 进程用不同 UID 跑，同机 VM 之间也互相隔离文件权限
vsock CIDVmCidAllocator：从 3 起，0–2 为系统保留vsock 用 CID 寻址 guest，每台 VM 必须唯一
socket 路径非 jailer 模式下放独立短根目录，用 sandboxId 的 SHA-256 前 16 位做子目录避开 Unix socket 路径 108 字节上限
坑 · SUN_LEN 限制。 Unix domain socket 的路径最长 108 字节。运行目录一旦嵌套得深，Firecracker 启动即报 path must be shorter than SUN_LEN。解决办法是把 socket 放在短路径根下。

M4 · vsock 命令通道：宿主和 VM 的"对讲机"

要解决的问题：宿主要把命令送进 VM、拿回结果。

技术选型：virtio-vsock。这是 host 与 guest 之间专用的 socket 通道，比网络更安全（它不走 IP，没有网卡也能用）。Firecracker 把它映射成宿主上的一个 Unix socket（vsock.sock）。

两端分工：

宿主侧：FirecrackerVsockBridge连接 vsock.sock，发 CONNECT 5000，等 OK，然后用 ping/pong 确认 agent 活着。之后把每条命令包成一个 JSON 帧发出去，用 id 把返回的输出对应到请求上。
Guest 侧：socat + agent开机后 inittab 启动 socat VSOCK-LISTEN:5000,fork EXEC:/agent/main，每个连接 fork 一个 agent。agent 用 child_process.spawn 执行 argv，把 stdout/stderr 切块回传。

协议（JSON 逐行，每行一帧）：

宿主 → agent:  {"v":1,"type":"exec","id":"…","argv":["sh","-c","ls"],"cwd":"/workspace","env":{…},"timeoutMs":…,"maxOutputBytes":…}
agent → 宿主:  {"v":1,"type":"exec_output","id":"…","stream":"stdout","data":"<base64>"}
agent → 宿主:  {"v":1,"type":"exec_result","id":"…","exitCode":0,"timedOut":false,"truncated":false}
  • 命令不经过 shell 拼接：argv 是数组，直接 spawn，没有注入面。
  • 输出 base64 编码：多字节字符和控制字符不会破坏帧结构。
  • 超时双信号：到时先 SIGTERM，2 秒后仍活则 SIGKILL，并在结果里标 timedOut，不吞掉。
  • 宿主侧再截一次：agent 属于不可信面，宿主按字节硬截断 maxOutputBytes 并标 truncated；单帧超过 1 MiB 直接报错。
  • 同一桥串行执行：executionQueue 保证同一 VM 的命令一条接一条。
为什么不用串口？ 串口是"往 VM 的终端打字、在输出里找哨兵字符串"。问题有四个：命令被 shell 二次解释（注入）；哨兵可被恶意进程伪造；stdout/stderr 混在一起；所有命令共享一个 root 会话、环境互相污染。vsock + 结构化帧把这四个问题都消掉了。串口现在只留给内核日志。

M5 · 工作区磁盘：VM 看不见宿主目录，怎么传文件？

要解决的问题：Agent 的工作区（比如它改过的代码）要留下来，但 VM 有独立内核，它的世界里没有宿主目录。

技术选型：不用共享文件系统（virtio-fs 会重新打开一条 guest 直达宿主文件系统的通道，扩大攻击面），而是把工作区做成一块虚拟磁盘，VM 启动时挂上，结束时把磁盘内容拷回来。

  1. 准备：模板 workspace-template.ext4（空白 ext4）→ 每 Run 复制一份 workspace.ext4（放在该 VM 的 chroot 或运行目录里）。
  2. 挂载：作为 Firecracker 的第二块盘 /dev/vdb，guest 的 inittab 执行 mount -t ext4 /dev/vdb /workspace，agent 的工作目录就是 /workspace。
  3. 使用：命令在 /workspace 里读写，实际写到的是那块盘。
  4. 导出：终止时先停机（确保 guest 不再写盘），再用 debugfs rdump 把 ext4 镜像里的文件整棵拷到宿主工作区，并做安全审计（清理指向外部的符号链接）。备选方案是 loop mount 只读挂载。
坑 · 为什么导出要在"停机之后"？ 如果 VM 还在写，宿主读到的 ext4 镜像可能是半新半旧的，文件会损坏。所以顺序是 stopVm → export。
坑 · 为什么 agent 的 cwd 必须是挂载盘？ 如果 cwd 落在 rootfs 副本上，产物写进系统盘，导出时工作区是空的。这一点在 inittab 里有显式注释。
当前是终止时一次性导出。VM 运行期间，宿主侧看不到 VM 里的中间文件。

M6 · 快照加速：把"开好机的 VM"存档

要解决的问题：冷启动一台 VM 要约 1.5 秒（内核启动 + init + agent 就绪）。Agent 每个 Run 都要一台，这个延迟不能每次都付。

技术选型：Firecracker 的 snapshot / restore。思路类似"把一台已经开机、agent 已就绪的电脑连同内存一起冻结成文件"，下次不开机，直接把内存加载进去接着跑。

我们怎么实现：

  1. 模板指纹：computeTemplateHash = sha256(kernel 的 路径/大小/mtime + rootfs 的 路径/大小/mtime + agent 版本号)。镜像或 agent 一变，指纹就变，旧快照自动失效。
  2. 黄金快照制作：第一台冷启动并握手成功后，PATCH /vm {"state":"Paused"} → PUT /snapshot/create（生成 vm.snap 和 mem.snap）→ Resumed。存到快照池 <poolDir>/<templateHash>/。
  3. 快速恢复：之后同模板的 VM 走 PUT /snapshot/load。加载前复制快照进 chroot，并通过 vsock override（uds_path）把快照里固化的 vsock socket 路径改成本 Run 自己的。
  4. 单飞闸门：KeyedSemaphore 按模板指纹串行制作快照。同一模板只让一台制作，其余等它完成后复用。
坑 · snapshot/load 的顺序是硬约束。 Firecracker 要求 load 必须是"新进程里第一个操作"。如果先配了 drive 或 vsock 再 load，会报 Loading a microVM snapshot not allowed after configuring boot-specific resources。所以恢复路径里块设备和 vsock 全部来自快照本身。
坑 · 快照制作会冻结 vCPU，vsock 连接会断。 制作快照后，宿主侧已建立的 vsock 连接被对端关闭。只有本 VM 真的做了 pause/create，才需要重连；如果只是等闸门后复用了别人的快照，连接依然有效。
坑 · 指纹必须含 agent 版本。 否则改了 guest agent 代码却没改版本号，指纹不变，会静默复用含旧 agent 的快照，线上跑的是旧代码。
坑 · 并发会竞态。 10 台 VM 同时首次启动、模板相同，会并发写同一个快照文件，并各自 pause/resume，导致 vsock 超时。真机复现后，才加了这个单飞闸门。

M7 · 生命周期与孤儿回收

要解决的问题：VM 的创建和销毁要按正确顺序做，任何一步失败都不能留下"吃内存却没人管"的 Firecracker 进程。

销毁顺序（MicrovmSandboxProvider.terminate）

  1. flush：让 guest 把文件系统缓存落盘（best-effort）。
  2. stopVm：SIGKILL Firecracker 并等它真的退出；保留运行目录与磁盘。
  3. 导出：把工作区盘导出到宿主工作区。导出失败只记录，不抛出。
  4. terminate：释放 CID、UID，删除 chroot 与运行目录。
  5. dispose：无论前面成功与否都执行，清理不会被导出失败短路。
坑 · 必须先停进程，再删目录。 目录里有 pidfile 和 socket，它们是寻址凭据。先删目录，进程就成了"找不到的孤儿"，会永久占内存，而容量准入完全看不见它。

崩溃后的孤儿回收（reapOrphanVms）

  • 落盘 pidfile：每台 VM 启动时把 pid、进程名、sandboxId 写进 vm.pid。这是跨进程重启唯一的凭据。
  • 启动时回收：Harness 启动后、创建任何新 VM 之前，扫描所有运行目录，逐个 pidfile 验活 → 确认是 Firecracker 才 SIGKILL → 删目录。
  • 验活而非盲杀：先读 /proc/<pid>/cmdline 确认真是我们启动的 Firecracker。pid 可能已被系统复用给别人，盲杀会误伤。
真机上曾经出现过 7 个孤儿 firecracker 进程，这是加这一层的直接原因。

M8 · 接入层：把 VM 伪装成统一的 Sandbox

要解决的问题：上层（RunService、工具网关）不应该关心底下是 runsc 还是 Firecracker。

  • 统一接口：SandboxProvider 定义 create / terminate / 生命周期事件；SandboxCommandExecutor 定义 execute。
  • Broker 进程（生产部署）：Firecracker/jailer 需要 root，不能放在 Master 里。生产由独立的 sandbox-broker 进程持有 Firecracker 与用户 secret；Master 的 BrokerSandboxProvider 通过 Unix socket 调它。Broker 用 SO_PEERCRED 读取对端 uid、用控制 token 拒绝非 Master 的 create，并要求 root 才能启用 jailer。
  • 按档位路由：SandboxProviderRouter 按 profile 分发。strict 走 MicrovmSandboxProvider，default 走 runsc 容器。两条链路可以灰度并存，出问题可回退。
  • 驱动可替换：MicrovmDriver 是接口，实现有 firecracker（真实）、mock（测试桩）、e2b（未实现，声明为不提供硬件隔离）。
  • 诚实的隔离证据：驱动必须声明 providesHardwareIsolation。只有真实 Firecracker 才会把 runtimeEvidence.verified 置为 true；mock 永远是 false。这杜绝了"假隔离被报告为已验证"。
  • fail-closed：模板不存在、驱动不可用、工作区盘没回传路径，都直接拒绝创建，不会降级成无隔离执行。

Sandbox Broker 进程（root，唯一持有 Firecracker/jailer 与用户 secret）
   · SO_PEERCRED 校验对端 uid；拒绝非 Master 的 create
   · 启动时先回收孤儿 VM，再开始服务
   · 内部：MicrovmSandboxProvider → FirecrackerSandboxDriver（即本文 M1–M7）
                                                                                │
                                                                                ▼
                                                              microVM（vsock 命令通道 → guest agent）

注意：Master 和 Worker 不直接持有 Firecracker。这样即使 Master/Worker 被打穿，也拿不到 root 权限或其他用户的 secret。开发环境（非 broker 配置）则直接在同一进程内装配，并通过 SandboxProviderRouter 把 strict 与 default 两条链路并存。

3.2 一次 Run 的时间线

  1. 上层请求沙箱 · M8
    执行链路对 strict 档请求沙箱，Router 转给 Provider（生产为 BrokerSandboxProvider，由 Broker 转给 MicrovmSandboxProvider.create）。Provider 先检查：allowNetwork 必须为 false，模板文件必须存在。通过后解析 Secret（只放内存，入库只存名字），写一条 ACTIVE 记录。
  2. 分配身份 · M3
    在 <runtimeRoot>/<id>/ 建 0700 目录；分配 CID（vsock 地址）。
  3. 准备盘与 chroot · M2 + M5
    复制 rootfs 与工作区模板到 chroot；分配 UID/GID 并 chown -R。
  4. 启动 Firecracker · M2 + M1
    用 jailer 启动（降权、chroot、cgroup 限额）。进程 pid 立即写入 vm.pid（M7 的凭据）。等待 API socket 出现。
  5. 两条路径二选一 · M6
    快速路径：模板指纹命中 → 复制快照进 chroot → /snapshot/load（改写 vsock 路径）→ resume。实测约 0.5 秒。
    冷启动路径：配置内核、两块盘、vsock、机器规格 → InstanceStart。实测约 1.5 秒。首台冷启动握手成功后，经闸门制作黄金快照。
  6. 握手确认就绪 · M4
    宿主桥连接 vsock.sock，发 CONNECT 5000，收到 OK，再发 ping 收 pong。失败会按 250ms 间隔重试，最长 20 秒。
  7. 执行命令 · M4 + M5 + M1
    上层 execute(sandbox, argv) → 桥生成 id，发 exec 帧 → guest socat fork agent → agent 在 /workspace 下 spawn argv → 输出 base64 分块回传 → 宿主按 id 归并，按字节截断，拿到 exitCode / timedOut / truncated。
  8. 可以多次执行 · M4
    同一个 VM 可以接收多条命令，桥内部串行，每条命令独立进程、独立退出码。
  9. 终止：先停后导 · M7 + M6
    flush → SIGKILL 并等待退出 → 此时 guest 不再写盘。
  10. 导出产物 · M5
    debugfs rdump 把 workspace.ext4 的内容拷回宿主工作区，清理危险的符号链接。
  11. 销毁 · M7 + M3 + M2
    driver.terminate 释放 CID、UID，删除 chroot；dispose 删除运行目录；DB 状态改为 TERMINATED。即使导出失败，清理依然执行。

3.3 三层隔离各自负责什么

第 1 层：VM 边界（KVM）

VM 里的代码即使是 root、即使打穿了 guest 内核，也只能影响它自己那台小电脑。

对应：M1

第 2 层：宿主进程边界（jailer）

就算 Firecracker 进程本身被攻破，它也是个降权、被 chroot、被限额的低权限进程。

对应：M2、M3

第 3 层：通道与数据边界

宿主和 VM 之间只有结构化帧，没有网络，没有共享目录。文件只通过"停机后导出"这一条路回到宿主。

对应：M4、M5

3.4 为什么要这样"组装"：各模块互相依赖的关系

依赖关系原因
M4 依赖 M1（agent 必须先开机）vsock 握手要等 guest 内核起来、socat 监听，所以握手有 20 秒重试窗口
M5 依赖 M7（导出必须在停机之后）VM 还在写盘时导出会得到损坏镜像
M6 依赖 M4（快照制作后要重连 vsock）快照会冻结 vCPU，宿主侧连接被断开
M6 依赖 M2（快照要拷进 chroot）降权后的 Firecracker 只能访问 chroot 内的文件
M7 依赖 M3（回收靠运行目录里的 pidfile）pidfile 是进程重启后唯一的寻址凭据
M1 的 Guest 镜像依赖 M5（工作区挂载）inittab 里 mount /dev/vdb /workspace 与宿主侧的盘必须一一对应
M8 依赖所有模块的"诚实声明"Provider 只根据驱动声明的 providesHardwareIsolation 决定是否宣称已隔离

6. 术语速查（按 Agent 工程师能理解的方式）

术语白话类比
VM（虚拟机）一台有独立内核的电脑，由软件造出来云服务器里的一台实例
KVM / /dev/kvmLinux 内核给进程开的"硬件虚拟化门"让 CPU 指令直接跑、又能隔开的执行许可
Firecracker极简的 VM 管理程序，启动快、设备少专为 Lambda 造的小型虚拟化引擎
VMM管理 VM 的那个宿主进程VM 的"管家进程"
Guest / HostVM 内部 / 宿主机容器里的世界 / 容器外的世界
jailer给 Firecracker 降权、chroot、限额的官方工具给管家进程戴上手铐和小笼子
chroot把进程的根目录改成一个子目录，它看不见外面把进程关进一个只含必需文件的文件夹
cgroup内核的资源配额表（CPU、内存）宿主给进程划的预算
UID / GIDLinux 用户/用户组编号，决定文件权限每台 VM 一个员工工号
vsock宿主与 VM 之间的专用 socket 通道，不走 IP宿主和 VM 之间的内线电话
socat一个"把 socket 接到程序 stdin/stdout"的小工具接线员，把电话接到 agent
Guest agentVM 内运行的小程序，负责接收并执行命令VM 里的执行员
rootfsVM 的系统盘（操作系统文件）VM 的"系统分区"
ext4 镜像一个装着文件系统的磁盘文件一个 U 盘的文件版
debugfs rdump不挂载、直接从 ext4 镜像里把文件拷出来不插 U 盘，直接读它的目录
Snapshot / Restore把已开机的 VM（含内存）存档，下次直接接着跑游戏存档，而不是重新开一局
黄金快照同一模板第一次做出来的那份存档，复用给后续 VM母版存档
模板指纹kernel + rootfs + agent 版本的哈希，变了就失效母版的版本号
pidfile记录 VM 进程 pid 的小文件，崩溃后用于找回进程寄存在门口的钥匙登记表
SIGTERM / SIGKILL请求进程退出 / 强制杀死先请你下班，再强制清场
fail-closed出错时拒绝执行，而不是降级成不安全的方式门禁故障时默认关门
