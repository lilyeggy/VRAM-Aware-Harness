# 调度层量化基准

> 回答一个问题：**调度器到底带来了多少收益，怎么证明？**
> 脚本：`scripts/scheduler-benchmark.ts`（纯离线，不依赖模型/沙箱/真机，CI 里每次都会跑）
> 复现：`bun run scripts/scheduler-benchmark.ts`
> 环境：2026-10-22，Apple Silicon macOS，Bun 1.3.13（相对数字，绝对值随机器变化）

## 结果（一次运行）

| 场景 | 指标 | 结果 |
|---|---|---|
| **A. 2 租户、全局 30** | 静态 `cap=10` 的容量利用率 | **66.7%**（20/30，有排队也补不满） |
| | 自动公平份额 `cap=floor(30/N)` | **100%**（30/30） |
| **B. 10 租户、每租户 12 条** | 各租户完成数 | `12×10`，极差 **0** |
| | 排队等待 p50 / p95 | **68.5ms / 130.8ms** |
| **C. 6 slot、60 条混合时长（5~200ms）** | slot 利用率 | **85.7%**（3420ms 忙 / 664.8ms 墙钟 × 6） |
| | 排队等待 p50 / p95 | 204.9ms / 440.4ms |
| **D. 批屏障（6 slot、18 条混合时长）** | 旧「整批等待」墙钟 | 604.8ms |
| | 新「谁先结束谁补位」墙钟 | **248.5ms（提速 58.9%）** |

## 这些数对应哪些代码

| 结论 | 实现 |
|---|---|
| 自动公平份额 | `TenantRunScheduler.effectiveTenantCap()`：`max(1, floor(C / 有需求租户数))`，空闲份额可借用；`HARNESS_MAX_ACTIVE_RUNS_PER_TENANT=0` 为默认 |
| 租户间等权 | RR 环 + 老化（`agingMs`）防饿死，无优先级/档位 |
| 逐槽补位 | `RunScheduler.drainOnce()`：`Promise.race` 等任意一个 attempt 结束就补位，不再 `Promise.allSettled` 整批等待 |
| 等待上界 | 老化插队 + Queue TTL（只对资源/并发阻塞计时，会话锁等待不计入） |

## 怎么读这些数

- **A 是纯收益**：静态上限在租户少时浪费容量、在租户多时又超发份额；动态份额用一行公式同时解决。
- **B 的极差 0** 说明等权轮转在对称负载下没有漂移；p95 是"10 个租户同时 backlog 时，一条 Run 大约等多久"。
- **C 的 85.7%** 不是缺陷：60 条任务在 6 个 slot 上有固有尾部效应（最后一批 200ms 任务独占尾部），负载越大越接近 100%。
- **D 是这次优化的直接证据**：同样 18 条混合时长任务，旧算法要等每批最慢的 Run，新算法空出一个槽就补一个。

## 已知边界

- 这是**调度器层**基准（假 Runtime），不含沙箱启动与模型延迟；端到端延迟见 `docs/vm-lifecycle-benchmark.zh-CN.md`。
- 时长为人为分布，不代表真实 Agent 任务分布；真实分布接入后应重跑并替换本表。
