# 平台并发能力浸泡测试（不依赖 GPU / 模型）

> 问题：**平台能不能扛高并发**——注意这不是"推理吞吐"，而是调度正确性。
> 脚本：`scripts/platform-soak.ts`（纯内存，CI 每次跑）
> 复现：`bun run scripts/platform-soak.ts`

## 测什么

用一个确定性的假 Runtime（每个 Run 固定 5–60ms 的随机时长，固定种子），一次性灌入 N 个 Run，然后断言 6 条不变量：

| 指标 | 断言 |
|---|---|
| 完成率 | 全部 COMPLETED，无丢失/死锁 |
| 并发上限 | 同时在跑的 Run 峰值 ≤ `maxActiveRuns` |
| 会话互斥 | 同一会话同时最多 1 个 Run（违规数 = 0） |
| 租户公平 | 各租户完成数极差 ≤ 2（等权份额） |
| 无泄漏 | 结束后 `activeRunCount = 0`、队列为空 |
| 排队等待 | 输出 p50 / p95 |

## 实测结果

| 场景 | 墙钟 | 排队 p50 | 排队 p95 | 公平极差 | 会话违规 | 泄漏 |
|---|---|---|---|---|---|---|
| 300 runs / 10 租户 / 6 槽 | 1.75s | 871ms | 1.64s | 0 | 0 | 无 |
| 500 runs / 20 租户 / 8 槽 | 2.19s | 1096ms | 2.04s | 0 | 0 | 无 |
| **1000 runs / 20 租户 / 8 槽** | **4.43s** | 2353ms | 4.26s | 0 | 0 | 无 |

（Apple Silicon macOS / Bun 1.3.13；数字是相对值）

## 怎么读

- **1000 个 Run、20 个租户、8 个并发槽，4.4 秒全部完成，零泄漏零违规。**
- 排队等待随负载线性增长（p50 从 0.87s → 2.35s），说明瓶颈是"槽位"而不是调度器本身。
- 公平极差为 0：20 个租户各 50 条，完成数完全一致 —— 等权份额在高压下没有漂移。

## 边界（诚实说明）

- 这测的是**调度与 Run 生命周期**，不含 HTTP 层、沙箱启动、真实模型调用。
- 假 Runtime 的时长是人为分布；真实链路的端到端并发见 `docs/research/model-capacity.zh-CN.md`。
- 它回答的是"平台会不会在高并发下丢任务/超发/串会话/泄漏"，这正是平台该负责的部分；
  推理吞吐是推理服务的事，不在本测试范围。
