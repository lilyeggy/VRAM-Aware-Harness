## 1. 三条硬约束（它们直接决定分工，不是偏好）

**约束 1 — 浏览器只能主智能体做。**
`browser-use:control-browser` 的 skill 描述原文写着 *"Main-agent-only Browser Use. The main agent must perform browser work itself and must not delegate it to a subagent; subagents must not load this skill or use Browser Use."*
→ **所有需要真实页面的场景（U / C09 / X07 的页面部分）只能交给"新对话"（各自是主智能体），绝不能塞给子智能体。** `computer-use` 同为 main-agent-only，同理。

**约束 2 — 容量与长稳只能串行。**
§9 的并发阶梯、稳定吞吐、到达率阶梯、G12/X09 的耐久，测的都是**单系统容量**。两个负载发生器同时跑，测到的是主机竞争而不是 Harness 容量；这类数字拿去面试站不住。
→ **测量跑道全局唯一，一次只跑一个档位。**

**约束 3 — 主机是共享的、且接近饱和。**
RTX A6000 48G 显示已用 ~46.5G，但这**不是实时占用**：vLLM 开机就把权重+KV 池预留掉了（`gpu-memory-utilization≈0.9`），空闲时 GPU 利用率 0%、KV 占用 0%、running/waiting 请求都是 0。**Harness 实例自己不加载模型**，只是 vLLM 的 HTTP 客户端，所以**开几个实例都不会多占显存**。真正的边界是：
- **共享的是 vLLM 的算力与 KV 池** → **同一时刻只能有一个"负载发生源"**（功能类可 2–3 路并行，容量/长稳严格串行）。
- 显存真正卡死的是**不能再起第二个真模型**（余量装不下第二个 7B），G06 多后端 / 换模型对比只能用故障假后端。
- 根盘 97% 满（余 66G），大证据写 `homePLUS`（余 1.6T），实例用软链不复制代码。
- 22 个 `polar-*` 评测容器已运行 11 天，**不可触碰**；load ≈ 31。

| GPU | A6000，48G 显示已用 46.5G = vLLM 预留 44G + llama-server 1.8G；**空闲时 util 0% / KV 0%** | 算力充足；显存余量只够"不再起第二个真模型" |

**校准阈值（否则一定跑不动）**：默认 `BUSY=70 / CRITICAL=90` 是按"显存已用比例"判的，而 vLLM 自己就预占 ~90%，平台会把唯一模型服务判成长期 CRITICAL、所有任务排队后批量熔断（这是已登记的 **N5**）。所以每个新实例的 env 必须写 `HARNESS_BUSY_GPU_MEMORY_PERCENT=93`、`HARNESS_CRITICAL_GPU_MEMORY_PERCENT=98`。`provision-instance.sh` 已内置。

**但要留意 KV 阈值是"实际占用"口径**（空闲实测 0%，不是预占）。`HARNESS_BUSY_KV_CACHE_PERCENT=70` / `CRITICAL=90` 在轻量 UI 操作下不会触发；可**长输入/长任务类（C03/C04/C08、§9 的 20% T6 长输入）如果与别的跑道同时打，会把 KV 占用抬过 70%，导致准入转 BUSY、别的跑道任务排队**。7B / 32k 上下文下单条满长度序列约吃 1.8G KV，而 KV 池约 29G——**满上下文并发上限只有 ~16 条**。所以长输入类场景不要与负载测试并发。

## 4. 阶段排期

| 阶段 | 并行内容 | 退出条件 |
| --- | --- | --- |
| **P0 备夹具**（无需实例，可立即开始） | 子智能体①发压器、子智能体②固定夹具 | 发压器能在 13010 跑通一次 T1 并写出 `requests.jsonl` |
| **P1 主测** | 3 实例并行：A（串行档位）+ B1 + B2 | A 出 `λ*`；B1/B2 各自场景有判定与证据 |
| **P2 功能补测** | B 跑道释放的实例给子智能体跑 C 组 | Q08 / R05+障碍 / X04 / X06 出判定 |
| **P3 长稳** | 跑道 D：`setsid` 起 soaks，脱离会话 | 2h/8h/24h 各自有资源曲线；会话内只认已跑完的档 |
| **P4 收口** | 证据汇总、报告、清理、新任务探针 | 报告 + 机器可读结果 + 清理核对 |

> 全程并发实例 ≤ 3。B 跑道（UI 类）用 `managed-local` 即可，避免容器 churn。

**但 provider 不能随便选——`managed-local` 档用不了 bash。** 已核实（代码 + 真机双向确认）：`src/policies/tool-policy-guard.ts` 对 `bash` 有硬门槛，当策略设了 `workspaceRoots` 而执行环境报不出 `filesystemIsolation=true` 时直接 **DENY**（「执行环境无法隔离 Workspace，拒绝 bash」）。`managed-local-sandbox.ts:115` 报 `false`、`container-sandbox-provider.ts:203` 报 `true`，且 `sandbox-profile.ts:4` 注明 development 档本就不是隔离档——**这是设计上的 fail-closed 安全边界，不是缺陷**。

| provider | bash | 适用 |
| --- | --- | --- |
| `managed-local` | 拒绝 | 读写文件类任务（T1/T2/T3/T6）、纯 UI 场景 |
| `container` | 允许 | 一切需要 bash 的：T4 运行测试、T7 多工具、T8 slow-job、R01/R04/R07、T10 |

→ **跑道 A（负载含 T4/T7/T8）与跑道 D（R07/T8）必须开 `container`**；B 跑道用 `managed-local`，某场景需要 bash 时再换。另注意容器默认镜像 `alpine:3.20` **没有 python**，跑 T4 必须换带解释器的镜像，否则会把"镜像缺依赖"误判成"模型失败"（指南 §3.4 点名）。

**由此推出一条必须如实标注的结论：不存在"E1 且能用 bash"的档位组合。** `HARNESS_SANDBOX_PROVIDER` 只有 `container` / `managed-local` 两个取值（`harness-config.ts:116/154` 是二元判断），bash 被 fail-closed 绑定到 `container`，而 `container`+runsc 就是 E2。因此**一切含 bash 的场景（T4/T7/T8/T10、R01/R04/R07）实际都是 E2，不能标 E1**；指南 §3.1 把 E1 描述成"process Worker"能跑工具任务，与该实现边界不一致，这一点要写进报告。

## 8. 验收与证据规范（所有跑道统一）

- **三份结论**：系统正确性 / 任务能力 / 用户体验，缺一不可。
- **不认 COMPLETED**：必须查 `output`、`workspace-diff`、`artifacts` 与外部验收器；`POST /runs/:id/resume` 返回 202 **不代表已执行**。
- **状态用词**：PASS / FAIL / BLOCKED / INCONCLUSIVE / NOT_RUN / OUT_OF_SCOPE，未执行 ≠ 通过。
- **环境标注**：每条结果附 `E0/E1/E2` 与 `REAL/SIMULATED`；注入的模拟 worker 不能改标成真实模型结论。
- **证据目录**：照指南 §10.1；每场景用 §10.2 模板；每 5s 导资源摘要，每 30–60s 采样进程与磁盘。
- **守恒核对**：报告必须给出 计划发送 / 实际发送 / 202 接受 / 明确拒绝 / 接受未知 / 完成 / 失败 / 中断 / 仍排队 / 正确任务数，且满足守恒；未知接受先对账，不能从分母删。
- **硬性不变量**（违反即阻断，不允许平均）：跨租户泄露；同 Run 并行执行 / 同 Session 并发打开 / 终态被迟到事件覆盖；不安全副作用自动重放；已接受任务无声消失；资源长期不释放；把失败伪装成功或返回他人结果。
